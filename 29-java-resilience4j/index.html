Java Resilience4j — Fault Tolerance Patterns
Panduan lengkap untuk developer PHP/Laravel yang ingin membangun aplikasi Java yang tangguh. Pelajari Retry, Circuit Breaker, Rate Limiter, Bulkhead, Time Limiter, dan cara menyusunnya bersama dengan Decorators!
🔁 Retry ⏬ Circuit Breaker 🚫 Rate Limiter 🔌 Bulkhead ⏱ Time Limiter 🏭 Decorators 📊 Events & Metrics

Project: belajar-java-resilience4j — package programmerzamannow.resilience4j. Semua fitur Resilience4j didemonstrasikan dengan pola yang konsisten: ofDefaults → Config → Registry.

💡 Apa itu Resilience4j?

Resilience4j adalah library fault tolerance untuk Java yang terinspirasi dari Netflix Hystrix. "Fault tolerance" berarti aplikasi tetap berfungsi (atau gagal dengan anggun) meskipun dependency eksternal (API pihak ketiga, database, microservice lain) mengalami masalah. Di PHP/Laravel, kita sering pakai try-catch manual atau package seperti guzzle-retry-middleware. Di Java, Resilience4j menyediakan solusi yang jauh lebih terstruktur dan powerful!

Chapter 1
🔁 Retry: Coba Lagi Otomatis
Saat sebuah operasi gagal karena masalah sementara (network fluke, temporary outage), Retry otomatis mencoba ulang tanpa kode manual. Ini adalah pattern paling dasar dan paling sering dipakai!
Retry dengan Defaults

Pola Resilience4j selalu sama: buat resilience object → wrap kode kamu → jalankan. Default Retry: maksimal 3 percobaan, tunggu 500ms antar percobaan.

// FILE: RetryTest.java

// Contoh 1: Retry untuk Runnable (void, tidak return nilai)
@Test
void createNewRetry() {
    Retry retry = Retry.ofDefaults("pzn");           // Line 1

    Runnable runnable = Retry.decorateRunnable(      // Line 2
        retry,
        () -> callMe()                               // Lambda yang akan di-retry
    );

    runnable.run();                                  // Line 3
}

// Contoh 2: Retry untuk Supplier (return nilai)
@Test
void createRetrySupplier() {
    Retry retry = Retry.ofDefaults("pzn");

    Supplier<String> supplier = Retry.decorateSupplier(  // Line 4
        retry,
        () -> hello()
    );

    supplier.get();                                  // Line 5
}

// Method yang selalu gagal (simulasi unstable service)
void callMe() {
    log.info("Try call me");
    throw new IllegalArgumentException("Ups error");
}

String hello() {
    log.info("Call say hello");
    throw new IllegalArgumentException("Ups error say hello");
}
Line 1

Retry.ofDefaults("pzn") — Buat instance Retry dengan konfigurasi default. "pzn" adalah nama unik (identifier) instance ini — penting untuk logging dan registry. Default: maxAttempts=3, waitDuration=500ms, retry untuk semua Exception.

Line 2

Retry.decorateRunnable(retry, lambda) — "Bungkus" kode kamu dengan Retry. Ini adalah pola Decorator — kode asli (() -> callMe()) dibungkus dengan logika retry. Jika lambda throw exception, Retry otomatis coba lagi sesuai konfigurasi.

Line 3

runnable.run() — Eksekusi! Jika callMe() throw exception: tunggu 500ms, coba lagi. Setelah 3 kali gagal semua, exception terakhir di-propagate ke pemanggil.

Line 4

Retry.decorateSupplier(retry, lambda) — Seperti decorateRunnable tapi untuk operasi yang mengembalikan nilai (String). Supplier<String> = fungsi tanpa parameter yang return String.

Line 5

supplier.get() — Panggil supplier. Jika berhasil, return nilainya. Jika semua retry gagal, throw exception. Kode pemanggil bisa tangkap exception ini dengan try-catch.

🐘 Analogi Laravel/PHP
// PHP tanpa library — retry manual (verbose & error-prone)
$maxAttempts = 3;
$attempt = 0;
while ($attempt < $maxAttempts) {
    try {
        $result = $this->callExternalApi();
        break; // sukses, keluar loop
    } catch (Exception $e) {
        $attempt++;
        if ($attempt >= $maxAttempts) throw $e;
        sleep(1); // tunggu 1 detik
    }
}

// Java dengan Resilience4j — jauh lebih bersih!
Retry retry = Retry.ofDefaults("api");
Supplier<String> supplier = Retry.decorateSupplier(retry, () -> callExternalApi());
String result = supplier.get(); // Retry otomatis! Tidak ada loop manual

Chapter 2
⚙ RetryConfig: Konfigurasi Custom
Default seringkali tidak cukup. Pelajari cara mengkustomisasi Retry: berapa kali coba, berapa lama tunggu, exception apa yang perlu di-retry.
Membuat RetryConfig
// FILE: RetryConfigTest.java

@Test
void retryConfig() {
    RetryConfig config = RetryConfig.custom()         // Line 1
        .maxAttempts(5)                               // Line 2
        .waitDuration(Duration.ofSeconds(2))          // Line 3
        // .ignoreExceptions(IllegalArgumentException.class) // Line 4
        // .retryExceptions(IllegalArgumentException.class)  // Line 5
        .build();                                     // Line 6

    Retry retry = Retry.of("pzn", config);            // Line 7

    Supplier<String> supplier = Retry.decorateSupplier(retry, () -> hello());
    supplier.get();
    // Output log:
    // Call hello()         ← percobaan 1
    // Call hello()         ← retry 1 (setelah 2 detik)
    // Call hello()         ← retry 2 (setelah 2 detik)
    // Call hello()         ← retry 3 (setelah 2 detik)
    // Call hello()         ← retry 4 (setelah 2 detik)
    // MaxRetriesExceededException! (total 5 percobaan)
}
Line 1

RetryConfig.custom() — Builder pattern untuk konfigurasi. Ini idiom Java yang sangat umum: buat builder, chain method konfigurasi, akhiri dengan .build(). Setara dengan array config di PHP: ['max_attempts' => 5, 'wait' => 2].

Line 2

.maxAttempts(5) — Total percobaan (termasuk yang pertama). Artinya: 1 percobaan awal + 4 retry = 5 total. Default: 3.

Line 3

.waitDuration(Duration.ofSeconds(2)) — Tunggu 2 detik antar percobaan. Duration adalah class Java modern untuk merepresentasikan durasi waktu. Bisa: Duration.ofMillis(500), Duration.ofMinutes(1), dll. Default: 500ms.

Line 4

.ignoreExceptions(Class...) — Exception yang tidak perlu di-retry (langsung throw). Misalnya: IllegalArgumentException biasanya berarti input salah — tidak ada gunanya retry.

Line 5

.retryExceptions(Class...) — Kebalikan: hanya retry untuk exception ini. Misalnya: IOException, TimeoutException — ini masalah sementara yang layak di-retry.

Line 6

.build() — Selesaikan builder dan buat object RetryConfig. Tanpa ini, konfigurasi tidak tersimpan.

Line 7

Retry.of("pzn", config) — Buat Retry dengan config custom. Beda dengan ofDefaults() yang pakai default settings.

💡 ignoreExceptions vs retryExceptions
SettingBehaviorKapan Dipakai
Tidak di-set (default)Retry semua ExceptionSaat semua error dianggap transient
retryExceptions(A.class)Hanya retry Exception tipe ASaat hanya error tertentu yang transient (network, timeout)
ignoreExceptions(B.class)Retry semua kecuali tipe BSaat error tipe B tidak perlu di-retry (validation error, not found)
🐘 Analogi Laravel

Di Laravel Queue, kamu bisa set $tries = 5 dan $backoff = 2 di Job class. RetryConfig melakukan hal yang sama tapi untuk operasi programatik (bukan queue job). Konsepnya identik: berapa kali coba, berapa lama tunggu, dan exception apa yang harus di-retry.

b) .retryExceptions(NetworkException.class) — hanya retry NetworkException, semua lainnya langsung throw

Chapter 3
📦 Registry Pattern: Manajemen Terpusat
Registry adalah pusat manajemen semua instance Resilience4j. Sama seperti Singleton pattern — Registry memastikan kamu menggunakan instance yang sama untuk nama yang sama.
RetryRegistry: Satu Instance per Nama
// FILE: RetryRegistryTest.java

@Test
void testRetryRegistry() {
    RetryRegistry registry = RetryRegistry.ofDefaults();  // Line 1

    Retry retry1 = registry.retry("pzn");                 // Line 2
    Retry retry2 = registry.retry("pzn");                 // Line 3

    Assertions.assertSame(retry1, retry2);                // Line 4 — SAMA!
}

@Test
void testRetryRegistryConfig() {
    RetryConfig config = RetryConfig.custom()
        .maxAttempts(5)
        .waitDuration(Duration.ofSeconds(2))
        .build();

    RetryRegistry registry = RetryRegistry.ofDefaults();
    registry.addConfiguration("config", config);          // Line 5

    Retry retry1 = registry.retry("pzn", "config");       // Line 6
    Retry retry2 = registry.retry("pzn", "config");

    Assertions.assertSame(retry1, retry2);                // Masih sama!

    Runnable runnable = Retry.decorateRunnable(retry1, () -> callMe());
    runnable.run();
}
Line 1

RetryRegistry.ofDefaults() — Buat Registry dengan konfigurasi default. Di Spring Boot, Registry biasanya dikonfigurasi sebagai Bean dan di-inject ke seluruh aplikasi — satu Registry untuk semua.

Line 2-3

registry.retry("pzn") dipanggil dua kali dengan nama yang sama. Registry menggunakan pola flyweight/cache: jika sudah ada instance dengan nama itu, kembalikan yang lama. Jika belum, buat baru.

Line 4

assertSame(retry1, retry2) — Membuktikan bahwa keduanya adalah objek yang sama persis (bukan hanya nilainya sama, tapi referensinya sama). Inilah manfaat Registry: satu instance per nama = monitoring metrics terpusat.

Line 5

registry.addConfiguration("config", config) — Daftarkan konfigurasi dengan nama "config". Nama ini bisa digunakan saat membuat instance: registry.retry("nama-instance", "nama-config").

Line 6

registry.retry("pzn", "config") — Buat (atau ambil) instance Retry bernama "pzn" menggunakan konfigurasi bernama "config" yang sudah didaftarkan sebelumnya.

✅ Pola yang Sama untuk Semua Komponen Resilience4j:

// POLA UNIVERSAL: ofDefaults → addConfiguration → ambil instance
XxxRegistry registry = XxxRegistry.ofDefaults();
registry.addConfiguration("nama-config", config);
Xxx instance = registry.xxx("nama-instance", "nama-config");

// Contoh nyata untuk semua komponen:
BulkheadRegistry.ofDefaults()    → registry.bulkhead("name", "config")
CircuitBreakerRegistry.ofDefaults() → registry.circuitBreaker("name", "config")
RateLimiterRegistry.ofDefaults()  → registry.rateLimiter("name", "config")
TimeLimiterRegistry.ofDefaults()  → registry.timeLimiter("name", "config")
RetryRegistry.ofDefaults()        → registry.retry("name", "config")
🐘 Analogi Laravel

Registry mirip dengan Service Container/IoC Container di Laravel (app()->bind() / app()->singleton()). Container memastikan kamu mendapat instance yang benar berdasarkan nama/interface. Perbedaannya: Registry Resilience4j khusus untuk fault tolerance components, bukan general-purpose DI container.

Chapter 4
⏬ Circuit Breaker: Pemutus Arus Otomatis
Pattern paling penting dalam fault tolerance. Seperti MCB listrik di rumah — jika terlalu banyak kegagalan, "arus diputus" agar sistem tidak terus-terusan mencoba sesuatu yang sudah pasti gagal!
Tiga State Circuit Breaker
CLOSED
Normal, request lewat
→ terlalu banyak error →
OPEN
Semua request ditolak langsung
→ setelah wait duration →
HALF-OPEN
Beberapa request dicoba
💡 Analogi MCB Listrik

CLOSED (arus mengalir): Semua request dijalankan normal. CB mencatat berapa banyak yang gagal. → OPEN (arus diputus): Jika error rate melewati threshold, CB terbuka — semua request LANGSUNG ditolak tanpa mencoba (CallNotPermittedException). Ini melindungi service yang sudah kewalahan dari banjir request tambahan. → HALF-OPEN (coba sedikit dulu): Setelah waktu tunggu, CB izinkan beberapa request masuk untuk menguji apakah service sudah pulih. Jika berhasil → kembali CLOSED. Jika masih gagal → kembali OPEN.

Circuit Breaker dengan Defaults
// FILE: CircuitBreakerTest.java

public void callMe() {
    log.info("Call Me");
    throw new IllegalArgumentException("Ups");  // Selalu gagal!
}

@Test
void circuitBreaker() {
    CircuitBreaker cb = CircuitBreaker.ofDefaults("pzn");  // Line 1
    // Default: failureRateThreshold=50%, slidingWindowSize=100

    for (int i = 0; i < 200; i++) {
        try {
            Runnable runnable = CircuitBreaker.decorateRunnable(cb, () -> callMe()); // Line 2
            runnable.run();
        } catch (Exception e) {
            log.error("Error: {}", e.getMessage());
            // Perhatikan: setelah 50+ errors, pesan error berubah!
            // "Ups" → IllegalArgumentException (CB CLOSED, request dijalankan)
            // "CircuitBreaker 'pzn' is OPEN" (CB OPEN, request langsung ditolak)
        }
    }
}
Line 1

CircuitBreaker.ofDefaults("pzn") — Default config: failureRateThreshold=50% (CB OPEN jika 50% dari 100 request terakhir gagal), slidingWindowSize=100, waitDurationInOpenState=60 detik.

Line 2

CircuitBreaker.decorateRunnable(cb, lambda) — Sama dengan Retry, tapi kali ini CB yang membungkus. Perbedaan kunci: jika CB OPEN, lambda tidak dieksekusi sama sekali — langsung throw CallNotPermittedException. Ini yang membuat CB efisien!

Circuit Breaker dengan Config Custom
@Test
void circuitBreakerConfig() {
    CircuitBreakerConfig config = CircuitBreakerConfig.custom()
        .slidingWindowType(                                       // Line A
            CircuitBreakerConfig.SlidingWindowType.COUNT_BASED   // Hitung per N request
        )
        .failureRateThreshold(10f)                               // Line B — 10% error = OPEN
        .slidingWindowSize(10)                                   // Line C — lihat 10 request terakhir
        .minimumNumberOfCalls(10)                                // Line D
        .build();

    CircuitBreaker cb = CircuitBreaker.of("pzn", config);

    for (int i = 0; i < 200; i++) {
        try {
            CircuitBreaker.decorateRunnable(cb, () -> callMe()).run();
        } catch (Exception e) {
            log.error("Error: {}", e.getMessage());
        }
    }
    // CB akan OPEN lebih cepat karena threshold hanya 10%!
    // Dari 200 request: ~10 pertama dijalankan (mengumpulkan data),
    // lalu CB OPEN — 190 request sisanya langsung ditolak tanpa eksekusi
}
Line A

COUNT_BASED vs TIME_BASED: COUNT_BASED menghitung N request terakhir. TIME_BASED menghitung request dalam N detik terakhir. COUNT_BASED lebih mudah diprediksi, TIME_BASED lebih cocok untuk traffic tidak merata.

Line B

.failureRateThreshold(10f) — CB OPEN jika 10% dari sliding window adalah error. Di sini: dari 10 request terakhir, jika 1 atau lebih gagal (10%) → CB OPEN! Threshold yang sangat sensitif — cocok untuk service yang harus sangat reliabel.

Line C

.slidingWindowSize(10) — Hitung 10 request terakhir untuk menentukan error rate. Makin kecil window, makin cepat CB bereaksi (tapi juga makin sensitif terhadap spike sesaat).

Line D

.minimumNumberOfCalls(10) — CB tidak akan OPEN sebelum menerima setidaknya 10 request. Ini mencegah CB langsung OPEN hanya karena 1 dari 2 request pertama gagal (yang akan jadi 50% error rate).

ConfigDefaultPenjelasan
failureRateThreshold50%% error rate untuk buka circuit
slidingWindowSize100Jumlah request/detik untuk dihitung
minimumNumberOfCalls100Min request sebelum CB bisa OPEN
waitDurationInOpenState60sBerapa lama di state OPEN sebelum HALF-OPEN
permittedCallsInHalfOpenState10Berapa request yang diizinkan di HALF-OPEN
slidingWindowTypeCOUNT_BASEDCOUNT_BASED atau TIME_BASED
🐘 Analogi Laravel

Bayangkan kamu punya kode di Laravel yang call ke payment gateway. Tanpa Circuit Breaker: setiap request user tetap mencoba call payment gateway meskipun payment gateway down — setiap request butuh 30 detik timeout, user menunggu 30 detik sebelum dapat error. Dengan Circuit Breaker: setelah beberapa request gagal, CB OPEN dan request berikutnya langsung dapat error dalam milidetik tanpa menunggu timeout. Pengalaman user jauh lebih baik!

Chapter 5
⏱ Time Limiter: Batas Waktu Eksekusi
Time Limiter memastikan operasi async tidak berjalan selamanya. Jika melewati batas waktu, operasi dibatalkan dan TimeoutException dilempar.
Time Limiter dengan Future
// FILE: TimeLimiterTest.java

@SneakyThrows
public String slow() {
    log.info("Slow");
    Thread.sleep(5000L);  // Simulasi operasi lambat 5 detik
    return "Eko";
}

@Test
void timeLimiter() throws Exception {
    ExecutorService executorService =                          // Line 1
        Executors.newSingleThreadExecutor();

    Future<String> future = executorService.submit(           // Line 2
        () -> slow()
    );

    TimeLimiter timeLimiter = TimeLimiter.ofDefaults("pzn"); // Line 3
    // Default: timeoutDuration = 1 detik

    Callable<String> callable =                              // Line 4
        TimeLimiter.decorateFutureSupplier(
            timeLimiter,
            () -> future
        );

    callable.call();  // Line 5 — TIMEOUT! slow() butuh 5s, limit 1s
}

@Test
void timeLimiterConfig() throws Exception {
    ExecutorService executorService = Executors.newSingleThreadExecutor();
    Future<String> future = executorService.submit(() -> slow());

    TimeLimiterConfig config = TimeLimiterConfig.custom()
        .timeoutDuration(Duration.ofSeconds(10))             // Line 6 — beri 10 detik
        .cancelRunningFuture(true)                           // Line 7
        .build();

    TimeLimiter timeLimiter = TimeLimiter.of("pzn", config);
    Callable<String> callable =
        TimeLimiter.decorateFutureSupplier(timeLimiter, () -> future);

    String result = callable.call(); // Berhasil! slow() selesai dalam 5s < 10s
    System.out.println(result); // "Eko"
}
Line 1

ExecutorService — Thread pool untuk menjalankan task secara async. Executors.newSingleThreadExecutor() membuat pool dengan 1 thread. Time Limiter bekerja dengan Future (async task), bukan synchronous method biasa.

Line 2

executorService.submit(() -> slow()) — Kirim task slow() ke thread pool untuk dijalankan async. Return Future<String> yang bisa kita pantau.

Line 3

TimeLimiter.ofDefaults("pzn") — Default timeout: 1 detik. slow() butuh 5 detik → pasti timeout!

Line 4

TimeLimiter.decorateFutureSupplier(timeLimiter, () -> future) — Bungkus Future dengan Time Limiter. Parameter kedua adalah Supplier<Future> — fungsi yang mengembalikan Future.

Line 5

callable.call() — Eksekusi dengan batas waktu. Jika slow() tidak selesai dalam 1 detik → throw TimeoutException.

Line 6

.timeoutDuration(Duration.ofSeconds(10)) — Beri 10 detik. Karena slow() hanya butuh 5 detik, ini berhasil.

Line 7

.cancelRunningFuture(true) — Jika timeout, otomatis cancel Future yang masih berjalan di background. Ini penting untuk resource cleanup! Jika false, task tetap jalan di background meskipun sudah timeout (buang-buang resource).

🐘 Analogi Laravel/PHP

Di PHP, kamu bisa set set_time_limit(30) untuk batas waktu script, atau CURLOPT_TIMEOUT untuk HTTP request. Time Limiter di Java bekerja pada level yang lebih granular: per-operasi async, bukan per-script. Ini sangat berguna saat calling external API — kamu tidak mau satu API yang lambat menghambat seluruh request handling.

🧠 Mini Quiz — Chapter 5

Q: Apa yang terjadi jika cancelRunningFuture(false) dan timeout terjadi?

a) Task langsung berhenti, tidak ada resource yang terbuang
b) TimeoutException dilempar ke pemanggil, tapi task di background thread TETAP berjalan sampai selesai — membuang thread dan resource
c) Task di-retry otomatis setelah timeout
d) Timeout diabaikan dan menunggu task selesai
Chapter 6
🚫 Rate Limiter: Batasi Laju Request
Rate Limiter membatasi berapa banyak request yang boleh dijalankan dalam periode waktu tertentu. Berguna untuk mematuhi API quota pihak ketiga atau melindungi service kamu dari overload.
Rate Limiter: N Request per Periode
// FILE: RateLimiterTest.java

private final AtomicLong counter = new AtomicLong(0L);

@Test
void testRateLimiter() {
    RateLimiter rateLimiter = RateLimiter.ofDefaults("pzn");
    // Default: 50 request per 500ns (sangat longgar untuk test)

    for (int i = 0; i < 10_000; i++) {
        Runnable runnable = RateLimiter.decorateRunnable(rateLimiter, () -> {
            long result = counter.incrementAndGet();
            log.info("Result: {}", result);
        });
        runnable.run();
    }
}

@Test
void testRateLimiterConfig() {
    RateLimiterConfig config = RateLimiterConfig.custom()
        .limitForPeriod(100)                          // Line 1 — max 100 request
        .limitRefreshPeriod(Duration.ofMinutes(1))    // Line 2 — per 1 menit
        .timeoutDuration(Duration.ofSeconds(2))       // Line 3
        .build();

    RateLimiter rateLimiter = RateLimiter.of("pzn", config);

    for (int i = 0; i < 10_000; i++) {
        Runnable runnable = RateLimiter.decorateRunnable(rateLimiter, () -> {
            long result = counter.incrementAndGet();
            log.info("Result: {}", result);
        });
        runnable.run();
        // 100 request pertama langsung jalan,
        // request ke-101 dst: TUNGGU sampai period refresh atau timeout
    }
}
Line 1

.limitForPeriod(100) — Izinkan maksimal 100 request dalam satu periode. Request ke-101 harus menunggu periode berikutnya.

Line 2

.limitRefreshPeriod(Duration.ofMinutes(1)) — Setiap 1 menit, quota di-reset kembali ke 100. Jadi: 100 request/menit.

Line 3

.timeoutDuration(Duration.ofSeconds(2)) — Jika sudah mencapai limit, request berikutnya MENUNGGU maksimal 2 detik untuk quota tersedia. Jika dalam 2 detik tidak ada quota → throw RequestNotPermitted. Jika Duration.ofSeconds(0), langsung throw exception tanpa tunggu.

💡 Perbedaan Rate Limiter vs Bulkhead
AspekRate LimiterBulkhead
MembatasiRequest per periode waktu (throughput)Request yang berjalan bersamaan (concurrency)
ContohMax 100 request/menitMax 10 request berjalan bersamaan
Use caseMematuhi API quota, mencegah overloadIsolasi resource, mencegah resource exhaustion
Error jika limitRequestNotPermittedBulkheadFullException
🐘 Analogi Laravel

Di Laravel, kamu pakai RateLimiter::for() dan throttle middleware untuk membatasi API request dari client. Rate Limiter Resilience4j bekerja di sisi outbound — membatasi seberapa sering aplikasimu memanggil service eksternal, bukan seberapa sering client memanggil aplikasimu. Keduanya adalah rate limiting, tapi arahnya berbeda!

🧠 Mini Quiz — Chapter 6

Q: Rate Limiter dikonfigurasi: limitForPeriod(5), limitRefreshPeriod(1 menit), timeoutDuration(0). Request ke-6 dalam 1 menit pertama akan menghasilkan apa?

a) Request ke-6 menunggu sampai menit berikutnya lalu berjalan

🔌 Bulkhead: Isolasi Concurrency
Bulkhead membatasi jumlah request yang berjalan bersamaan. Ada dua jenis: Semaphore (membatasi concurrent calls) dan ThreadPool (dedicated thread pool per service).
Semaphore Bulkhead: Batasi Concurrent Calls
// FILE: BulkheadTest.java

private AtomicLong counter = new AtomicLong(0L);

@SneakyThrows
public void slow() {
    long value = counter.incrementAndGet();
    log.info("Slow : " + value);
    Thread.sleep(1_000L); // Simulasi operasi 1 detik
}

// Semaphore Bulkhead dengan defaults
@Test
void testSemaphore() throws InterruptedException {
    Bulkhead bulkhead = Bulkhead.ofDefaults("pzn");
    // Default: maxConcurrentCalls=25, maxWaitDuration=0

    for (int i = 0; i < 1000; i++) {
        Runnable runnable = Bulkhead.decorateRunnable(bulkhead, () -> slow());
        new Thread(runnable).start();    // Line 1 — 1000 thread!
    }

    Thread.sleep(10_000L);
    // Dengan default max 25 concurrent: hanya 25 yang jalan bersamaan,
    // sisanya langsung throw BulkheadFullException
}

// Semaphore Bulkhead dengan config custom
@Test
void testSemaphoreConfig() throws InterruptedException {
    BulkheadConfig config = BulkheadConfig.custom()
        .maxConcurrentCalls(5)                          // Line 2 — max 5 bersamaan
        .maxWaitDuration(Duration.ofSeconds(5))         // Line 3 — tunggu 5 detik jika penuh
        .build();

    Bulkhead bulkhead = Bulkhead.of("pzn", config);

    for (int i = 0; i < 10; i++) {
        Runnable runnable = Bulkhead.decorateRunnable(bulkhead, () -> slow());
        new Thread(runnable).start();
    }

    Thread.sleep(10_000L);
    // 5 thread pertama langsung jalan
    // Thread 6-10: tunggu sampai ada slot kosong (max 5 detik)
}
Line 1

1000 thread dibuat sekaligus! Tanpa Bulkhead, semua 1000 thread akan mencoba mengakses service secara bersamaan — ini bisa menyebabkan resource exhaustion (OOM, connection pool habis, dll). Bulkhead membatasi hanya 25 yang bisa masuk bersamaan.

Line 2

.maxConcurrentCalls(5) — Hanya 5 request boleh berjalan bersamaan. Request ke-6 harus menunggu salah satu dari 5 yang berjalan selesai.

Line 3

.maxWaitDuration(Duration.ofSeconds(5)) — Jika Bulkhead penuh, request baru menunggu maksimal 5 detik. Jika dalam 5 detik tidak ada slot yang kosong → throw BulkheadFullException. Default: 0 (langsung throw).

ThreadPool Bulkhead: Dedicated Thread Pool
@Test
void testThreadPoolConfig() throws InterruptedException {
    ThreadPoolBulkheadConfig config = ThreadPoolBulkheadConfig.custom()
        .maxThreadPoolSize(5)       // Line A — max 5 thread aktif
        .coreThreadPoolSize(5)      // Line B — selalu siap 5 thread
        .queueCapacity(1)           // Line C — queue hanya 1 item
        .build();

    ThreadPoolBulkhead bulkhead = ThreadPoolBulkhead.of("pzn", config);

    for (int i = 0; i < 20; i++) {
        Supplier<CompletionStage<Void>> supplier =
            ThreadPoolBulkhead.decorateRunnable(bulkhead, () -> slow());
        supplier.get(); // Kirim ke thread pool
    }
    // Thread pool penuh (5 thread + 1 queue = max 6 bisa ditampung)
    // Request ke-7 dst: BulkheadFullException!

    Thread.sleep(10_000L);
}
Line A

.maxThreadPoolSize(5) — Maksimal 5 thread aktif secara bersamaan di pool. Thread ke-6 tidak dibuat — request yang datang masuk ke queue.

Line B

.coreThreadPoolSize(5) — JVM selalu menjaga 5 thread siap di pool (tidak di-terminate saat idle). Jika core=5 dan max=5, tidak ada thread baru yang dibuat saat beban naik.

Line C

.queueCapacity(1) — Queue sangat kecil (hanya 1 item). Jadi: max 5 thread aktif + 1 di queue = 6 request bisa ditampung. Request ke-7 → BulkheadFullException langsung.

Semaphore Bulkhead mirip dengan setting pm.max_children di PHP-FPM: membatasi berapa PHP process yang bisa berjalan bersamaan. 🏭 Decorators: Gabungkan Semua Pattern
Di dunia nyata, kamu butuh lebih dari satu pattern sekaligus. Decorators API memungkinkan kamu chain Retry + Rate Limiter + Circuit Breaker + Fallback dalam satu baris kode yang elegan!
Chain Multiple Patterns dengan Decorators
// FILE: DecoratorsTest.java

@SneakyThrows
public void slow() {
    log.info("Slow");
    Thread.sleep(1_000L);
    throw new IllegalArgumentException("Error");
}

@SneakyThrows
public String sayHello() {
    log.info("Say hello");
    Thread.sleep(1_000L);
    throw new IllegalArgumentException("Ups");
}

// Contoh 1: Retry + RateLimiter untuk Runnable
@Test
void decorators() throws InterruptedException {
    RateLimiter rateLimiter = RateLimiter.of("pzn-ratelimiter",
        RateLimiterConfig.custom()
            .limitForPeriod(5)
            .limitRefreshPeriod(Duration.ofMinutes(1))
            .build());

    Retry retry = Retry.of("pzn-retry",
        RetryConfig.custom()
            .maxAttempts(10)
            .waitDuration(Duration.ofMillis(10))
            .build());

    Runnable runnable = Decorators.ofRunnable(() -> slow()) // Line 1
        .withRetry(retry)                                   // Line 2
        .withRateLimiter(rateLimiter)                       // Line 3
        .decorate();                                        // Line 4

    for (int i = 0; i < 100; i++) {
        new Thread(runnable).start();
    }
    Thread.sleep(10_000L);
}

// Contoh 2: Retry + RateLimiter + Fallback untuk Supplier
@Test
void fallback() throws InterruptedException {
    RateLimiter rateLimiter = RateLimiter.of("pzn-ratelimiter",
        RateLimiterConfig.custom()
            .limitForPeriod(5)
            .limitRefreshPeriod(Duration.ofMinutes(1))
            .build());

    Retry retry = Retry.of("pzn-retry",
        RetryConfig.custom()
            .maxAttempts(10)
            .waitDuration(Duration.ofMillis(10))
            .build());

    Supplier<String> supplier = Decorators.ofSupplier(() -> sayHello()) // Line 5
        .withRetry(retry)
        .withRateLimiter(rateLimiter)
        .withFallback(throwable -> "Hello Guest")                        // Line 6
        .decorate();

    System.out.println(supplier.get());
    // Output: "Hello Guest" — semua retry gagal, fallback digunakan
}
Line 1

Decorators.ofRunnable(() -> slow()) — Mulai chain dengan kode yang ingin diproteksi. ofRunnable untuk void, ofSupplier untuk return value, ofCallable untuk callable yang throw checked exception.

Line 2

.withRetry(retry) — Tambahkan layer Retry. Jika slow() throw exception, Retry coba lagi sampai maxAttempts.

Line 3

.withRateLimiter(rateLimiter) — Tambahkan Rate Limiter. Urutan penting! Di sini Retry diterapkan lebih dalam dari Rate Limiter — artinya setiap "percobaan" dari Retry masing-masing dihitung sebagai 1 request untuk Rate Limiter.

Line 4

.decorate() — Selesaikan chain dan buat Runnable yang sudah dibungkus semua protection. Runnable ini bisa disimpan dan dijalankan kapan saja.

Line 5

Decorators.ofSupplier(() -> sayHello()) — Sama tapi untuk operasi yang return nilai (String).

Line 6

.withFallback(throwable -> "Hello Guest") — Jika semua retry gagal dan semua protection sudah dilewati, gunakan nilai fallback. Lambda menerima throwable (exception terakhir) sehingga kamu bisa logging atau return nilai berbeda tergantung tipe error.

💡 Urutan Decorator Matters!
// Skenario A: Retry luar, RateLimiter dalam
Decorators.ofRunnable(() -> call())
    .withRateLimiter(rateLimiter)  // dalam
    .withRetry(retry);             // luar

// Flow: Retry (luar) → RateLimiter (dalam) → call()
// Setiap attempt Retry mengalami RateLimiting
// Jika RateLimiter throw → Retry TIDAK coba lagi (RateLimiter bukan transient error)

// Skenario B: RateLimiter luar, Retry dalam
Decorators.ofRunnable(() -> call())
    .withRetry(retry)              // dalam
    .withRateLimiter(rateLimiter); // luar

// Flow: RateLimiter (luar) → Retry (dalam) → call()
// Retry dianggap 1 "slot" dari RateLimiter — semua percobaan retry dihitung sebagai 1 request
// Lebih hemat quota RateLimiter, tapi mungkin retry lebih banyak melewati rate limit
🐘 Analogi Laravel Middleware

Di Laravel, middleware dieksekusi secara berlapis (onion model). Decorators bekerja persis sama — setiap .with*() menambah satu layer middleware di sekeliling kode kamu. Urutan .with*() menentukan urutan eksekusi, seperti urutan middleware di Laravel routes. .withFallback() seperti exception handler di middleware yang mencegah error propagate ke atas.

📊 Events & Metrics: Observability
Resilience4j menyediakan event listener dan metrics API untuk monitoring. Tanpa observability, kamu "buta" terhadap apa yang terjadi di production!
Event Publisher: Listen ke Kejadian
// FILE: EventPublisherTest.java

@Test
void retry() {
    Retry retry = Retry.ofDefaults("pzn");

    // Pasang event listener SEBELUM menjalankan operasi
    retry.getEventPublisher().onRetry(event -> {       // Line 1
        log.info("try to retry");
    });

    try {
        Supplier<String> supplier =
            Retry.decorateSupplier(retry, () -> hello());
        supplier.get();
    } catch (Exception e) {
        // Metrics setelah semua selesai
        System.out.println(
            retry.getMetrics()
                 .getNumberOfFailedCallsWithRetryAttempt()        // Line 2
        );
        System.out.println(
            retry.getMetrics()
                 .getNumberOfFailedCallsWithoutRetryAttempt()     // Line 3
        );
        System.out.println(
            retry.getMetrics()
                 .getNumberOfSuccessfulCallsWithRetryAttempt()    // Line 4
        );
        System.out.println(
            retry.getMetrics()
                 .getNumberOfSuccessfulCallsWithoutRetryAttempt() // Line 5
        );
    }
}

// Event Publisher pada Registry
@Test
void registry() {
    RetryRegistry registry = RetryRegistry.ofDefaults();

    registry.getEventPublisher().onEntryAdded(event -> { // Line 6
        log.info("Add new entry {}",
                 event.getAddedEntry().getName());
    });

    registry.retry("pzn");   // → log: "Add new entry pzn"
    registry.retry("pzn");   // → tidak ada log (sudah ada)
    registry.retry("pzn2");  // → log: "Add new entry pzn2"
}
Line 1

retry.getEventPublisher().onRetry(callback) — Subscribe ke event "sedang retry". Callback dipanggil setiap kali retry terjadi. Event lain yang tersedia: onSuccess(), onError(), onIgnoredError(). Berguna untuk logging, alerting, atau increment custom metrics.

Line 2

getNumberOfFailedCallsWithRetryAttempt() — Jumlah call yang akhirnya gagal setelah semua retry habis. Misal: 5 maxAttempts, semua gagal → ini = 1 (satu "call" secara keseluruhan).

Line 3

getNumberOfFailedCallsWithoutRetryAttempt() — Jumlah call yang gagal di percobaan pertama dan TIDAK di-retry (misalnya karena exception masuk di ignoreExceptions).

Line 4

getNumberOfSuccessfulCallsWithRetryAttempt() — Jumlah call yang akhirnya berhasil setelah beberapa kali retry (gagal di awal, berhasil belakangan).

Line 5

getNumberOfSuccessfulCallsWithoutRetryAttempt() — Jumlah call yang berhasil di percobaan pertama tanpa perlu retry (happy path!).

Line 6

registry.getEventPublisher().onEntryAdded(callback) — Event saat instance baru ditambahkan ke registry. Berguna untuk audit: tahu kapan dan instance apa yang dibuat dalam aplikasi.

Chapter 10 — Final
🏆 Summary, Best Practice & Kapan Pakai Apa
Rekap semua pattern Resilience4j, kapan menggunakannya, pola registry yang konsisten, dan panduan langkah selanjutnya.
Arsitektur Pola Resilience4j
1
🔁 Retry — Coba Lagi Otomatis
Untuk: masalah sementara (transient faults) — network blip, temporary service unavailability. Config: maxAttempts, waitDuration, retryExceptions, ignoreExceptions. Jangan gunakan untuk: validation error, not found (bukan masalah transient).
Transient Fault Handling
2
⏬ Circuit Breaker — Pemutus Arus
Untuk: dependency yang sering gagal / lambat. Mencegah cascade failure — jika payment gateway down, stop panggil payment gateway, jangan biarkan semua user thread menunggu timeout 30 detik. Config: failureRateThreshold, slidingWindowSize, waitDurationInOpenState.
Cascade Failure Prevention
3
🚫 Rate Limiter — Batas Throughput
Untuk: mematuhi API quota pihak ketiga (contoh: Stripe API 100 req/s), melindungi service dari overload. Config: limitForPeriod, limitRefreshPeriod, timeoutDuration. Beda dengan Bulkhead: Rate Limiter mengontrol throughput (per waktu), Bulkhead mengontrol concurrency (bersamaan).
Throughput Control
4
🔌 Bulkhead — Isolasi Concurrency
Untuk: mencegah satu service lambat menghabiskan semua thread/connection pool. Semaphore untuk concurrency limit sederhana. ThreadPool untuk isolasi penuh — service A tidak bisa "mencuri" thread dari service B. Config: maxConcurrentCalls (Semaphore) atau maxThreadPoolSize + queueCapacity (ThreadPool).
Concurrency Isolation
5
⏱ Time Limiter — Batas Waktu
Untuk: operasi async yang harus selesai dalam batas waktu. Bekerja dengan Future/CompletableFuture. Config: timeoutDuration, cancelRunningFuture. Gunakan bersama ThreadPool Bulkhead untuk isolasi dan timeout dalam satu paket.
Async Timeout
6
🏭 Decorators — Gabungkan Semua
API builder untuk chain multiple pattern. withRetry + withCircuitBreaker + withRateLimiter + withFallback dalam satu deklarasi yang mudah dibaca. Urutan penting! Komponen yang didaftarkan pertama adalah yang "paling luar" dalam eksekusi.
