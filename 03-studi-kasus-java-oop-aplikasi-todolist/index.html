Chapter 0
🧠 Mindset Shift — Java vs PHP
Sebelum menyentuh satu baris kode pun, kita perlu meluruskan ekspektasi. Java dan PHP bukan hanya beda sintaks — mereka punya cara berpikir yang fundamental berbeda.
Mengapa Java Terasa "Lebih Ketat"?

Kamu mungkin sudah terbiasa dengan PHP di mana variabel bisa berpindah tipe sesuka hati. Di Java, compiler adalah penjaga gerbang yang sangat tegas. Ini bukan hambatan — ini adalah jaring pengaman yang menangkap bug sebelum sampai ke production.

🐘 PHP — Loosely Typed
// PHP: variabel bisa berubah tipe kapan saja
$value = 10;       // integer
$value = "hello";  // sekarang jadi string — VALID!
$value = true;     // sekarang boolean — masih VALID!

// Bahaya tersembunyi:
echo 10 + "5 apples"; // = 15, PHP convert otomatis
☕ Java — Strongly Typed
// Java: tipe harus konsisten, dideklarasikan eksplisit
int value = 10;
// value = "hello"; // ❌ ERROR kompilasi!

// Java MENOLAK compile jika tipe tidak cocok
String result = value + " items"; // ✅ OK, int → String otomatis
// int x = "5"; // ❌ ERROR: tipe tidak kompatibel
💡 Keuntungan buat kamu: Bug tipe terdeteksi saat kompilasi, bukan saat user pakai aplikasimu di production. Ini menghemat berjam-jam debugging.
1
Tulis .java
2
Compile → .class (bytecode)

JVM jalankan bytecode

PHP bisa langsung dijalankan tanpa compile. Java harus dikompilasi dulu dengan javac. Tapi hasilnya: performa lebih kencang, dan error tertangkap lebih awal.

⚠️ Ingat: Kalau kamu dapat pesan "Cannot find symbol" atau "incompatible types" — itu bukan error runtime. Itu compile-time error. Perbaiki sebelum program bisa jalan.

Di Java, segala sesuatu harus berada di dalam class. Bahkan method main() yang menjadi titik masuk program pun ada di dalam class. Tidak ada fungsi top-level seperti di PHP.

❌ Tidak Bisa di Java
// TIDAK VALID — tidak ada class pembungkus
public static void main(String[] args) {
    System.out.println("Hello");
}
✅ Benar di Java
// WAJIB ada class pembungkus
public class HelloWorld {
    public static void main(String[] args) {
        System.out.println("Hello");
    }
}
🐘 Analogi Laravel

Di Laravel kamu punya App\Models\User, App\Services\UserService. Di Java itu persis sama: entity.Todolist, service.TodoListService. Package = namespace, tapi juga mencerminkan struktur folder fisik di disk.

// File: src/entity/Todolist.java

// File: src/service/TodoListServiceImpl.java

import repository.TodoListRepository;

Chapter 2
📦 Entity Class — Todolist.java
Entity adalah representasi data dalam bentuk object. Di sinilah kita belajar tentang encapsulation, constructor, getter, dan setter — fondasi OOP Java.
Source Code
package entity;                        // Line 1

public class Todolist {                // Line 3

  private String todo;                 // Line 5

  public Todolist() {                  // Line 7
  }

  public Todolist(String todo) {       // Line 11
    this.todo = todo;
  }

  public String getTodo() {            // Line 15
    return todo;
  }

  public void setTodo(String todo) {   // Line 19
    this.todo = todo;
  }
}
Penjelasan Baris per Baris
Line 1 package entity; — Mendeklarasikan bahwa class ini berada di dalam package entity. Ini harus cocok dengan nama folder di filesystem. Analoginya: namespace App\Entity; di PHP. Line 3 public class Todolist — Keyword public artinya class ini bisa diakses dari package lain. Di Java, nama file harus sama persis dengan nama class public (case-sensitive!). File bernama Todolist.java harus punya class Todolist. Line 5 private String todo; — Field private = encapsulation. Dari luar class, properti ini tidak bisa diakses langsung. Ini berbeda dari PHP di mana kamu mungkin sering bikin public $todo. Di Java, default best practice adalah selalu private. Line 7-9 No-arg constructor (constructor tanpa parameter). Di Java, jika kamu sudah mendefinisikan constructor berparameter, Java tidak otomatis menyediakan no-arg constructor. Kamu harus menulisnya eksplisit jika masih dibutuhkan. Line 11-13 Constructor berparameter. this.todo = todo; — kata kunci this merujuk ke field instance (bukan parameter). Ini perlu karena nama parameter sama dengan nama field. Di PHP: $this->todo = $todo; Line 15-17 Getter — Method getTodo() adalah satu-satunya cara "resmi" untuk membaca nilai field private dari luar class. Ini adalah standar POJO (Plain Old Java Object) / JavaBean. Line 19-21 Setter — Method setTodo() untuk mengubah nilai. Return type void berarti tidak mengembalikan nilai apapun.
🏛️ Insight — Encapsulation: Membuat field private dan menyediakan getter/setter adalah prinsip encapsulation. Manfaatnya: kamu bisa menambahkan validasi di setter tanpa mengubah semua kode yang menggunakan class ini. Contoh: di setter, kamu bisa validasi todo tidak boleh kosong.
Common Mistakes (❌ Salah vs ✅ Benar)
❌ Salah — Public Field
public class Todolist {
  // JANGAN ini — field publik
  public String todo;
}

// Akibat: siapapun bisa ubah langsung
todolist.todo = ""; // tidak ada validasi!

Rawan bug karena tidak ada kontrol atas siapa yang bisa mengubah nilai, dan tidak ada tempat untuk validasi.

✅ Benar — Private + Getter/Setter
public class Todolist {
  private String todo;

  public void setTodo(String todo) {
    // Bisa tambah validasi di sini
    if (todo == null || todo.isBlank()) {
      throw new IllegalArgumentException("Todo kosong!");
    }
    this.todo = todo;
  }
}

Enkapsulasi yang benar. Setter adalah satu-satunya pintu masuk untuk mengubah data.

🐘 Analogi Laravel

Class Todolist.java ini persis seperti Eloquent Model di Laravel — ini adalah representasi data. Bedanya, di Eloquent kamu pakai $fillable dan magic method, sedangkan di Java POJO semua harus eksplisit: field, constructor, getter, setter. Tidak ada magic $model->attribute — kamu harus memanggil model.getAttribute().

📋 V1 Prosedural — AplikasiTodolist.java
Versi pertama aplikasi ini ditulis dalam satu class besar dengan static methods. Ini adalah titik awal yang bagus untuk memahami array, static, dan alur logika Java sebelum masuk ke OOP penuh.
Deklarasi Static di V1
public class AplikasiTodolist {

  public static String[] model = new String[10];  // Line 3
  public static java.util.Scanner scanner =        // Line 5
      new java.util.Scanner(System.in);

  public static void main(String[] args) {         // Line 8
    viewShowTodoList();
  }
}
Line 3 public static String[] model = new String[10]; — Di Java, array punya ukuran TETAP saat dibuat. new String[10] membuat array berisi 10 slot, semua bernilai null. Ini berbeda dari PHP di mana array bisa tumbuh otomatis. Line 5 java.util.Scanner — Scanner adalah class bawaan Java untuk membaca input user. Ditulis dengan fully-qualified name (termasuk package) karena tidak ada import di atas. Cara lebih bersih: tambahkan import java.util.Scanner; di atas. static Keyword static artinya field/method ini milik class, bukan milik instance. Di V1, semua method static sehingga bisa dipanggil langsung tanpa membuat object. Analoginya di PHP: static function.
Dynamic Array Resize — Logika Krusial

Karena Java array statis, V1 mengimplementasikan logika resize manual ketika array penuh:

public static void addTodoList(String todo) {
  // STEP 1: Cek apakah semua slot terisi (tidak ada null)
  var isFull = true;
  for (int i = 0; i < model.length; i++) {
    if (model[i] == null) {
      isFull = false;
      break;
    }
  }

  // STEP 2: Jika penuh, buat array baru 2x lebih besar
  if (isFull) {
    var temp = model;                          // simpan referensi lama
    model = new String[model.length * 2];      // array baru ukuran 2x

    for (int i = 0; i < temp.length; i++) {   // copy semua elemen
      model[i] = temp[i];
    }
  }

  // STEP 3: Masukkan data ke slot null pertama
  for (var i = 0; i < model.length; i++) {
    if (model[i] == null) {
      model[i] = todo;
      break;
    }
  }
}
var Keyword var (Java 10+) untuk type inference. Compiler mendeteksi tipe otomatis. var isFull = true; sama dengan boolean isFull = true;. Mirip PHP tapi berbeda — Java tetap strongly-typed, hanya inferensinya otomatis. Step 2 Strategi "double when full" ini adalah pola klasik Dynamic Array, persis seperti cara kerja ArrayList di Java dan PHP's built-in array secara internal. Kenapa 2x? Amortized O(1) time complexity untuk operasi tambah. break Menghentikan loop segera setelah kondisi terpenuhi. Penting untuk performa — tanpa break, loop terus berjalan bahkan setelah data sudah ditemukan/dimasukkan.
Logika Remove — Shift Kiri
public static boolean removeTodoList(Integer number) {
  // Guard clause: validasi input
  if ((number - 1) >= model.length) {
    return false;  // nomor melebihi panjang array
  } else if (model[number - 1] == null) {
    return false;  // slot sudah kosong
  } else {
    // Geser semua elemen ke kiri mulai dari posisi yang dihapus
    for (int i = (number - 1); i < model.length; i++) {
      if (i == (model.length - 1)) {
        model[i] = null;        // elemen terakhir dikosongkan
      } else {
        model[i] = model[i + 1]; // geser kiri
      }
    }
    return true;
  }
}
⚠️ Catatan Penting — Integer vs int: Parameter ditulis Integer number (bukan int). Integer (huruf kapital) adalah wrapper class — versi object dari primitive int. Wrapper class bisa bernilai null, primitive tidak. Ini perbedaan Java yang sering bikin bingung developer PHP.
💡 Insight — Guard Clause: Pola if kondisi salah → return false di awal method disebut Guard Clause. Ini membuat kode lebih mudah dibaca karena kasus edge ditangani dulu, logika utama di akhir. Sangat direkomendasikan!
❌ Salah — Nested if Deep
// Susah dibaca, deeply nested
if (number - 1 < model.length) {
  if (model[number-1] != null) {
    // logika utama di dalam 2 level if
    for (int i = ...) {
      // ...
    }
    return true;
  }
}
return false;
✅ Benar — Guard Clause
// Mudah dibaca, langsung ke inti
if ((number - 1) >= model.length)
    return false;
if (model[number - 1] == null)
    return false;

// Logika utama tanpa nesting berlebihan
for (int i = (number-1); i < model.length; i++) {
  // ...
}
return true;
🐘 Analogi Laravel

Di Laravel/PHP, array bisa push data kapan saja tanpa khawatir ukuran. Di Java, kalau pakai array biasa, kamu harus kelola sendiri seperti di atas. Itulah mengapa di Java modern kita lebih sering pakai ArrayList<T> — ini adalah dynamic array yang sudah built-in, mirip dengan array PHP. Studi kasus ini sengaja menggunakan array biasa agar kamu memahami mekanismenya.

Chapter 4
🗄️ Repository Pattern — Interface & Implementasi
Di sinilah kekuatan OOP Java mulai terasa. Repository Pattern memisahkan "apa yang bisa dilakukan" (interface) dari "bagaimana melakukannya" (implementasi). Ini adalah pola yang juga ada di Laravel!
Interface — Kontrak, Bukan Implementasi
// File: src/repository/TodoListRepository.java
package repository;

import entity.Todolist;

public interface TodoListRepository {  // ← "interface", bukan "class"!

  Todolist[] getAll();          // Metode tanpa body — hanya kontrak

  void add(Todolist todolist);

  boolean remove(Integer number);

}
interface Interface di Java adalah kontrak murni — mendefinisikan apa yang bisa dilakukan, tapi tidak bagaimana. Tidak ada implementasi di sini, hanya signature method. Siapa pun yang ingin menjadi TodoListRepository wajib mengimplementasikan semua method ini. Todolist[] Return type Todolist[] artinya method ini mengembalikan array dari object Todolist. Ini menunjukkan penggunaan Entity di dalam Repository. void Method add bertipe void — tidak mengembalikan nilai apapun. Di PHP, kamu bisa skip return type; di Java harus eksplisit bahkan jika tidak mengembalikan apa-apa.
Implementasi — Cara Konkret Bekerja
// File: src/repository/TodoListRepositoryImpl.java
package repository;

import entity.Todolist;

public class TodoListRepositoryImpl implements TodoListRepository {
//                                       ↑ keyword "implements" = "saya memenuhi kontrak interface ini"

  public Todolist[] data = new Todolist[10]; // penyimpanan data internal

  @Override
  public Todolist[] getAll() {
    return data;           // kembalikan seluruh array
  }

  public boolean isFull() {  // ← method helper, tidak ada di interface
    var isFull = true;
    for (int i = 0; i < data.length; i++) {
      if (data[i] == null) {
        isFull = false;
        break;
      }
    }
    return isFull;
  }

  public void resizeIfFull() {
    if (isFull()) {
      var temp = data;
      data = new Todolist[data.length * 2];
      for (int i = 0; i < temp.length; i++) {
        data[i] = temp[i];
      }
    }
  }

  @Override
  public void add(Todolist todolist) {
    resizeIfFull();          // resize otomatis jika penuh
    for (var i = 0; i < data.length; i++) {
      if (data[i] == null) {
        data[i] = todolist;  // simpan object Todolist, bukan String!
        break;
      }
    }
  }

  @Override
  public boolean remove(Integer number) {
    // ... logika sama dengan V1, tapi untuk Todolist[]
  }
}
implements Keyword implements TodoListRepository artinya class ini berjanji memenuhi semua kontrak di interface. Jika ada satu method interface yang tidak diimplementasikan, program TIDAK BISA dikompilasi. @Override Annotation @Override memberitahu compiler "method ini saya override dari interface/parent class." Ini opsional tapi sangat direkomendasikan — compiler akan error jika kamu salah ketik nama method, sehingga override tidak terjadi secara diam-diam. isFull() & resizeIfFull() Method helper yang tidak ada di interface. Ini adalah implementasi detail yang tidak perlu diketahui oleh layer lain. Ini adalah enkapsulasi logika internal.
🏛️ Mengapa Interface + Implementasi Terpisah? Kekuatan pattern ini: kamu bisa swap implementasi tanpa mengubah kode yang menggunakan Repository. Contoh: TodoListRepositoryImpl simpan data di array → kamu bisa buat TodoListRepositoryDatabase yang simpan ke MySQL → tanpa ubah Service/View sama sekali! Ini prinsip Open/Closed Principle (SOLID).
❌ Salah — Pakai Class Langsung
// Service langsung bergantung pada class konkret
public class TodoListServiceImpl {
  private TodoListRepositoryImpl repo; // ← terikat erat!
  // ...
}
// Kalau ganti implementasi repo, Service harus ikut diubah
✅ Benar — Pakai Interface
// Service bergantung pada interface (abstraksi)
public class TodoListServiceImpl {
  private TodoListRepository repo; // ← fleksibel!
  // ...
}
// Bisa inject implementasi apapun: array, DB, API, dll.
🐘 Analogi Laravel

Di Laravel, kamu bisa binding interface ke implementasi di AppServiceProvider: $this->app->bind(TodoRepositoryInterface::class, TodoRepositoryImpl::class). Lalu di Controller, kamu type-hint interface-nya. Di Java (tanpa Spring), kita lakukan "binding" ini secara manual di method main() — kita akan lihat ini di Chapter 8. Di Spring Boot, prosesnya mirip dengan Laravel DI container: pakai @Autowired / constructor injection.

Chapter 5
⚙️ Service Layer — Logika Bisnis
Service layer adalah "otak" aplikasi. Di sinilah logika bisnis tinggal — bukan di View (yang hanya urusan tampilan), bukan di Repository (yang hanya urusan data). Di sini juga kita belajar Constructor Injection, pola DI yang paling direkomendasikan.
Interface Service
// File: src/service/TodoListService.java
package service;

public interface TodoListService {

  void showTodoList();

  void addTodoList(String todo);

  void removeTodoList(Integer number);

}
💡 Kenapa Interface Service juga diperlukan? Sama dengan Repository — memungkinkan penggantian implementasi service (misal: versi dengan caching, versi dengan logging, dll.) tanpa mengubah View. Ini juga memudahkan unit testing dengan mock.
Implementasi Service — Constructor Injection
// File: src/service/TodoListServiceImpl.java
package service;

import entity.Todolist;
import repository.TodoListRepository;

public class TodoListServiceImpl implements TodoListService {

  private TodoListRepository todoListRepository;  // Line 8: dependency

  public TodoListServiceImpl(TodoListRepository todoListRepository) {  // Line 10: constructor injection
    this.todoListRepository = todoListRepository;
  }

  @Override
  public void showTodoList() {
    Todolist[] model = todoListRepository.getAll();  // Line 16: pakai repository

    System.out.println("TODOLIST");
    for (var i = 0; i < model.length; i++) {
      var todolist = model[i];
      var no = i + 1;

      if (todolist != null) {
        System.out.println(no + ". " + todolist.getTodo()); // Line 23: pakai getter!
      }
    }
  }

  @Override
  public void addTodoList(String todo) {
    Todolist todolist = new Todolist(todo);  // Line 29: buat object entity
    todoListRepository.add(todolist);        // Line 30: simpan via repository
    System.out.println("SUKSES MENAMBAH TODO : " + todo);
  }

  @Override
  public void removeTodoList(Integer number) {
    boolean success = todoListRepository.remove(number);
    if (success) {
      System.out.println("SUKSES MENGHAPUS TODO : " + number);
    } else {
      System.out.println("GAGAL MENGHAPUS TODO : " + number);
    }
  }
}
Line 8 Field private TodoListRepository todoListRepository — perhatikan tipenya TodoListRepository (interface), bukan TodoListRepositoryImpl. Service ini tidak peduli implementasi spesifiknya. Line 10-12 Constructor Injection — dependency diberikan melalui constructor, bukan dibuat di dalam class. Service tidak tahu "cara buat repository" — itu bukan urusannya. Pihak luar (entry point di main) yang bertanggung jawab menciptakan dan menyerahkan repository. Line 16 Service memanggil todoListRepository.getAll() melalui interface. Ini adalah penggunaan polymorphism — service tidak perlu tahu apakah di baliknya ada array, database, atau API. Line 23 todolist.getTodo() — mengakses data entity melalui getter, bukan langsung ke field. Ini konsekuensi encapsulation yang kita pelajari di Chapter 2. Line 29-30 Service membuat object Todolist (entity) lalu menyerahkannya ke repository. Ini alur data yang bersih: String input → Entity object → disimpan di Repository.
❌ Salah — Field Injection (@Autowired)
// Ini pola yang ada di Spring — tapi BUKAN best practice
public class TodoListServiceImpl {
  @Autowired  // ← langsung inject ke field
  private TodoListRepository repo;

  // Masalah: class tidak bisa di-test tanpa Spring context,
  // dependency tidak visible dari luar
}
✅ Benar — Constructor Injection
public class TodoListServiceImpl {
  private final TodoListRepository repo; // final!

  // Dependency jelas, wajib disediakan saat dibuat
  public TodoListServiceImpl(TodoListRepository repo) {
    this.repo = repo;
  }
  // Mudah di-test: tinggal inject mock di test
}
🐘 Analogi Laravel

Constructor Injection di Java = Constructor Injection di Laravel Service. Kalau di Laravel kamu punya:

class TodoService {

        private TodoRepository $repository
    ) {}
}

Di Java itu persis sama strukturnya! Bedanya di Laravel ada DI container yang inject otomatis; di Java (tanpa framework) kita inject manual di main().

Chapter 6
🖥️ View Layer — Interaksi User
View layer hanya bertanggung jawab pada interaksi dengan user: membaca input dan menampilkan output. Tidak ada logika bisnis di sini. View hanya "berbicara" dengan Service.
Source Code — TodoListView.java
// File: src/view/TodoListView.java
package view;

import service.TodoListService;
import util.InputUtil;

public class TodoListView {

  private TodoListService todoListService;  // dependency ke service

  public TodoListView(TodoListService todoListService) {  // constructor injection
    this.todoListService = todoListService;
  }

  public void showTodoList() {
    while (true) {                          // loop menu utama
      todoListService.showTodoList();       // delegasi ke service

      System.out.println("MENU : ");
      System.out.println("1. Tambah");
      System.out.println("2. Hapus");
      System.out.println("x. Keluar");

      var input = InputUtil.input("Pilih");  // baca input user

      if (input.equals("1")) {              // equals() bukan ==!
        addTodoList();
      } else if (input.equals("2")) {
        removeTodoList();
      } else if (input.equals("x")) {
        break;
      } else {
        System.out.println("Pilihan tidak dimengerti");
      }
    }
  }

  public void addTodoList() {
    System.out.println("MENAMBAH TODOLIST");
    var todo = InputUtil.input("Todo (x Jika Batal)");
    if (todo.equals("x")) {
      // batal — tidak melakukan apa-apa
    } else {
      todoListService.addTodoList(todo);  // serahkan ke service
    }
  }

  public void removeTodoList() {
    System.out.println("MENGHAPUS TODOLIST");
    var number = InputUtil.input("Nomor yang Dihapus (x Jika Batal)");
    if (number.equals("x")) {
      // batal
    } else {
      todoListService.removeTodoList(Integer.valueOf(number));
      //                             ↑ String → Integer conversion
    }
  }
}
equals() PENTING SEKALI: Di Java, == untuk String membandingkan referensi memori, bukan isi. Selalu gunakan .equals() untuk membandingkan konten String. Ini adalah salah satu jebakan terbesar pindahan dari PHP, di mana == sudah cukup untuk membandingkan string. Integer.valueOf() Konversi dari String ke Integer object. Di PHP, PHP cast otomatis "2" jadi 2. Di Java, kamu harus eksplisit: Integer.valueOf("2") atau Integer.parseInt("2"). Jika string bukan angka valid, akan throw NumberFormatException. while(true) Loop tak terbatas yang hanya berhenti ketika user memasukkan "x" dan break dieksekusi. Ini pola umum untuk menu CLI interaktif. Di PHP: while(true) { ... break; } — persis sama!
🚨 Jebakan Klasik PHP → Java: String Comparison!
❌ Jangan — Pakai ==
String input = scanner.nextLine();
if (input == "1") {
  // Mungkin TIDAK PERNAH true meski input = "1"
  // Membandingkan referensi, bukan nilai!
}
✅ Selalu — Pakai .equals()
String input = scanner.nextLine();
if (input.equals("1")) {
  // BENAR — membandingkan isi string
}
// Atau lebih aman dari NullPointerException:
if ("1".equals(input)) { ... }

TodoListView ini adalah Controller di Laravel. Controller tidak boleh berisi logika bisnis — tugasnya hanya menerima request (input user), memanggil service yang tepat, dan mengembalikan response (output). Chapter 7
🔧 Utility Class — InputUtil.java
Utility class berisi helper method yang bisa dipakai di mana saja. Di sini kita belajar tentang static method di konteks yang tepat, dan DRY (Don't Repeat Yourself) principle.
Source Code
// File: src/util/InputUtil.java
package util;

import java.util.Scanner;

public class InputUtil {

  private static Scanner scanner = new Scanner(System.in);  // Line 7: satu instance Scanner

  public static String input(String info) {   // Line 9: static method
    System.out.print(info + " : ");
    String data = scanner.nextLine();
    return data;
  }

}
Line 7 private static Scanner scanner — Scanner adalah resource yang mahal (terhubung ke System.in). Dibuat satu kali sebagai static field agar di-share oleh semua panggilan input() tanpa perlu membuat instance baru setiap kali. Ini adalah singleton sederhana. Line 9 public static String input(String info) — Static method bisa dipanggil tanpa membuat instance class: InputUtil.input("Nama"). Ini tepat untuk utility method yang bersifat stateless (tidak bergantung pada state object). System.out.print Perhatikan print (bukan println). print tidak menambahkan newline sehingga cursor tetap di baris yang sama dengan prompt, dan input user ada di baris yang sama. println akan ke baris baru.
💡 Kapan Pakai static? Gunakan static untuk:
  • Method yang tidak bergantung pada state object (stateless helper)
  • Utility/helper class seperti InputUtil, Math, Arrays
  • Constants (public static final)
Hindari static untuk logika bisnis — karena membuat unit testing lebih sulit.
🐘 Analogi Laravel

InputUtil ini mirip Laravel Helper functions (str_pad(), now()) atau static facade seperti Str::slug(). Semuanya adalah utility stateless yang bisa dipanggil dari mana saja tanpa instansiasi. Di Java, kita pakai InputUtil.input() persis seperti Str::slug().

🚀 Entry Point — V1 vs V2, Manual DI
Entry point adalah titik masuk program. Di sini kita melihat perbedaan dramatis antara V1 (langsung panggil static method) dan V2 (manual dependency injection — wiring semua komponen secara eksplisit).
V1 Entry Point — Sederhana, Langsung

  public static String[] model = new String[10];  // state global
  public static java.util.Scanner scanner = new java.util.Scanner(System.in);

  public static void main(String[] args) {
    viewShowTodoList();  // langsung panggil static method
  }

}
V2 Entry Point — Manual Dependency Injection
// File: src/AplikasiTodolistV2.java
import repository.TodoListRepository;
import repository.TodoListRepositoryImpl;
import service.TodoListService;
import service.TodoListServiceImpl;
import view.TodoListView;

public class AplikasiTodolistV2 {

  public static void main(String[] args) {

    // Step 1: Buat Repository (layer terdalam)
    TodoListRepository todoListRepository = new TodoListRepositoryImpl();

    // Step 2: Buat Service, inject Repository ke dalamnya
    TodoListService todoListService = new TodoListServiceImpl(todoListRepository);

    // Step 3: Buat View, inject Service ke dalamnya
    TodoListView todoListView = new TodoListView(todoListService);

    // Step 4: Jalankan aplikasi
    todoListView.showTodoList();
  }
}
Step 1 TodoListRepository todoListRepository = new TodoListRepositoryImpl(); — Variabel bertipe interface (TodoListRepository), tapi diisi dengan implementasi konkret (TodoListRepositoryImpl). Ini disebut programming to interface. Step 2 Repository "diinjeksikan" ke Service melalui constructor. Service sendiri tidak pernah tahu "cara membuat" repository — dia hanya menerima apa yang diberikan. Step 3 Service "diinjeksikan" ke View. Dependency chain: View → Service → Repository → Entity. Pola Ini adalah Composition Root — satu tempat di mana semua dependency dirakit. Ini adalah best practice: wiring dependency hanya terjadi di satu titik, bukan tersebar di seluruh codebase.
🏛️ Ini adalah Spring Boot secara manual! Ketika kamu nanti belajar Spring Boot, framework ini melakukan semua "wiring" di atas secara otomatis melalui @Component, @Service, @Repository, dan @Autowired. Tapi sekarang kamu sudah mengerti apa yang terjadi di balik layar.

Prinsip SOLID yang Diterapkan
S
Single Responsibility Principle
Setiap class punya satu tanggung jawab: Entity = data, Repository = penyimpanan, Service = logika bisnis, View = UI. Tidak ada class yang "tahu terlalu banyak".
O
Open/Closed Principle
Bisa menambah implementasi baru (misal: TodoListRepositoryDatabase) tanpa mengubah Service atau View. Open for extension, closed for modification.
D
Dependency Inversion Principle
High-level modules (Service, View) tidak bergantung pada low-level modules (Impl). Keduanya bergantung pada abstraksi (Interface). Inilah kenapa semua dependency bertipe interface.
