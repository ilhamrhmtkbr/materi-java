Chapter 1
🔧 JUnit 5 Dasar: @Test, @DisplayName, @Disabled
Pengenalan JUnit 5 Jupiter — framework unit testing standar di ekosistem Java. Pelajari perbedaannya dengan PHPUnit dan anatomi test class pertamamu!
Subject Under Test: Calculator.java

Sebelum nulis test, kita butuh class yang ingin di-test. Ini disebut Subject Under Test (SUT) atau System Under Test.

// FILE: Calculator.java
public class Calculator {

    public Integer divide(Integer first, Integer second) {
        if (second == 0) {                                   // Line 1
            throw new IllegalArgumentException(
                "Can not divide by zero"
            );
        } else {
            return first / second;
        }
    }

    public Integer add(Integer first, Integer second) {      // Line 2
        return first + second;
    }
}
Line 1

throw new IllegalArgumentException(...) — Melempar exception saat input tidak valid. Di PHP ini setara dengan throw new \InvalidArgumentException('...'). Ini adalah Guard Clause yang akan kita test dengan assertThrows().

Line 2

Method add() sangat simpel — ideal untuk mulai belajar testing. Di dunia nyata, method yang di-test bisa jauh lebih kompleks, melibatkan database, API call, dll.

Anatomi Test Class: CalculatorTest.java
// FILE: CalculatorTest.java
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

@DisplayNameGeneration(SimpleDisplayNameGenerator.class)    // Line 1
public class CalculatorTest {

    private Calculator calculator = new Calculator();       // Line 2

    @BeforeAll                                              // Line 3
    public static void beforeAll() {
        System.out.println("Before all");
    }

    @AfterAll                                               // Line 4
    public static void afterAll() {
        System.out.println("After all");
    }

    @BeforeEach                                             // Line 5
    public void setUp() {
        System.out.println("Before each");
    }

    @AfterEach                                              // Line 6
    public void tearDown() {
        System.out.println("After each");
    }

    @Test                                                   // Line 7
    public void testAddSuccess() {
        var result = calculator.add(10, 10);
        assertEquals(20, result);
    }

    @Test
    @Disabled                                               // Line 8
    public void testComingSoon() {
        // Test ini di-skip
    }
}
Line 1

@DisplayNameGeneration — Menggunakan custom generator untuk nama tampilan test. SimpleDisplayNameGenerator menghasilkan nama seperti "Test CalculatorTest.testAddSuccess". Di PHPUnit, nama test method langsung menjadi label.

Line 2

private Calculator calculator = new Calculator(); — Instance SUT dibuat sebagai field. Penting: JUnit 5 default membuat instance test class baru untuk setiap test method (PER_METHOD lifecycle). Artinya calculator selalu fresh untuk setiap test!

Line 3

@BeforeAll — Dijalankan SEKALI sebelum semua test method di class ini. Harus static karena JUnit memanggil method ini sebelum membuat instance class. Setara dengan setUpBeforeClass() di PHPUnit.

Line 4

@AfterAll — Dijalankan SEKALI setelah semua test selesai. Harus static juga. Setara dengan tearDownAfterClass() di PHPUnit.

Line 5

@BeforeEach — Dijalankan sebelum SETIAP test method. Setara dengan setUp() di PHPUnit. Gunakan untuk inisialisasi yang dibutuhkan setiap test.

Line 6

@AfterEach — Dijalankan setelah setiap test method. Setara dengan tearDown() di PHPUnit. Gunakan untuk cleanup: close connection, delete temp files, dll.

Line 7

@Test — Menandai method sebagai test case. Setara dengan /** @test */ atau prefix test di PHPUnit. Tidak ada parameter return — jika tidak throw exception, test dianggap LULUS.

Line 8

@Disabled — Skip test ini. Setara dengan @test @skip atau markTestSkipped() di PHPUnit. Berguna saat feature belum siap tapi test sudah ditulis.

🐘 Analogi PHPUnit

Di PHPUnit, kamu membuat class yang extend TestCase. Di JUnit 5, class tidak perlu extend apapun! JUnit 5 menggunakan annotation + reflection untuk mendeteksi test method. Ini jauh lebih fleksibel — kamu bisa extend class lain untuk reuse setup code (lihat AbstractCalculatorTest di Chapter 9).

a) Karena method static berjalan lebih cepat di JVM
b) Karena JUnit memanggil method ini sebelum membuat instance class — hanya method static yang bisa dipanggil tanpa instance
c) Karena aturan Java mengharuskan method test selalu static
d) Tidak ada alasan khusus, itu hanya konvensi JUnit 5
Chapter 2
📋 Assertions: Verifikasi Hasil Test
Assertions adalah jantung dari setiap test — ini cara kamu "mengklaim" bahwa kode berjalan sesuai ekspektasi. JUnit 5 menyediakan API Assertions yang kaya.
Assertions yang Digunakan dalam Project
import static org.junit.jupiter.api.Assertions.*;

// 1. assertEquals — paling sering dipakai
@Test
public void testAddSuccess() {
    var result = calculator.add(10, 10);
    assertEquals(20, result);             // expected, actual
}                                         // PHP: $this->assertEquals(20, $result)

// 2. assertThrows — test bahwa exception dilempar
@Test
public void testDivideFailed() {
    assertThrows(IllegalArgumentException.class, () -> {
        calculator.divide(10, 0);         // Lambda yang harus throw exception
    });
}                                         // PHP: $this->expectException(\InvalidArgumentException::class)

// 3. assertNotNull — pastikan hasil tidak null
@Test
void testRegisterSuccess() {
    var person = personService.register("Eko");
    assertNotNull(person);               // person tidak boleh null
    assertNotNull(person.getId());       // id juga tidak boleh null
    assertEquals("Eko", person.getName());
}

💡 Insight: var di Java (Java 10+)

Kamu pasti melihat var result = calculator.add(10, 10);. var adalah Local Variable Type Inference di Java 10+. Java menginfer tipe dari sisi kanan assignment: karena add() return Integer, maka result otomatis bertipe Integer. Ini mirip $result = ... di PHP tapi Java tetap strongly-typed — tipe sudah ditentukan saat kompilasi, hanya kamu tidak perlu menulisnya eksplisit.

Assumptions: Conditionally Run Test
import static org.junit.jupiter.api.Assumptions.*;
import org.opentest4j.TestAbortedException;

// Cara 1: Manual throw TestAbortedException
@Test
public void testAborted() {
    var profile = System.getenv("PROFILE");
    if (!"DEV".equals(profile)) {
        throw new TestAbortedException(       // Line A
            "Test dibatalkan karena bukan DEV"
        );
    }
    // Test ini hanya berjalan jika PROFILE=DEV
}

// Cara 2: Menggunakan assumeTrue (lebih ringkas)
@Test
public void testAssumptions() {
    assumeTrue("DEV".equals(System.getenv("PROFILE"))); // Line B
    // Jika asumsi false → test di-ABORT (bukan FAIL, bukan PASS)
    // unit test untuk DEV saja
}
Line A

TestAbortedException — Exception khusus JUnit yang menandai test sebagai ABORTED (bukan FAILED). Di report test, ini muncul sebagai "skipped" atau "aborted". Berbeda dengan assertion failure yang muncul sebagai "failed".

Line B

assumeTrue(condition) — Jika condition false, test langsung di-abort dengan TestAbortedException. Analoginya: "Saya mengasumsikan bahwa kita di environment DEV. Jika tidak, skip saja test ini."

🐘 Analogi PHPUnit

assumeTrue() di JUnit mirip dengan $this->markTestSkipped('alasan') di PHPUnit, tapi lebih elegan karena menggunakan kondisi. Di PHPUnit kamu juga bisa gunakan @requires annotation untuk kondisi PHP version, extension, dsb.

🧠 Mini Quiz — Chapter 2

Q: Apa perbedaan antara test yang FAILED dan test yang ABORTED di JUnit 5?

a) Tidak ada perbedaan — keduanya berarti test gagal
b) FAILED berarti assertion gagal (bug ditemukan), ABORTED berarti prasyarat tidak terpenuhi sehingga test di-skip (bukan bug)
c) ABORTED berarti JVM crash, FAILED berarti test timeout
d) ABORTED berarti test lulus, FAILED berarti test di-skip
Chapter 3
♻ Test Lifecycle: PER_METHOD vs PER_CLASS
JUnit 5 default membuat instance test class baru untuk setiap test method. Ini penting dipahami untuk mengerti mengapa field test tidak bisa dibagikan antar test secara default!
Default Lifecycle: PER_METHOD (Isolasi Maksimal)
// FILE: LifecycleTest.java
public class LifecycleTest {

    private String temp;      // Field instance

    @Test
    void testA() {
        temp = "Eko";         // Set field
        System.out.println("testA: temp = " + temp); // "Eko"
    }

    @Test
    void testB() {
        System.out.println("testB: temp = " + temp); // null !
    }
}

// JUnit 5 menjalankan seperti ini (PER_METHOD):
// new LifecycleTest().testA()  → temp = "Eko" lalu dibuang
// new LifecycleTest().testB()  → temp = null (instance baru!)
💡 Kenapa PER_METHOD?

Test yang saling bergantung adalah test smell — tanda test yang buruk. Jika testB bergantung pada state yang diset testA, maka testB tidak bisa dijalankan secara independen. JUnit 5 memaksa isolasi dengan membuat instance baru per test, sehingga kamu tidak bisa "tidak sengaja" membagikan state antar test. Ini mendorong penulisan test yang independent dan idempotent.

Mengubah ke PER_CLASS: @TestInstance
// FILE: OrderedTest.java
@TestInstance(TestInstance.Lifecycle.PER_CLASS)  // Line 1
@TestMethodOrder(MethodOrderer.OrderAnnotation.class)
public class OrderedTest {

    private int counter = 0;   // Field shared antar test!

    @BeforeAll
    void beforeAll() {         // TIDAK perlu static!
        System.out.println("Before all");
    }

    @AfterAll
    void afterAll() {          // TIDAK perlu static!
        System.out.println("After all");
    }

    @Test
    @Order(1)
    void test3() {
        counter++;
        System.out.println(counter); // Output: 1
    }

    @Test
    @Order(2)
    void test1() {
        counter++;
        System.out.println(counter); // Output: 2
    }

    @Test
    @Order(3)
    void test2() {
        counter++;
        System.out.println(counter); // Output: 3
    }
}
Line 1

@TestInstance(PER_CLASS) — Satu instance class digunakan untuk semua test method. Efeknya: (1) field counter tidak di-reset antar test, (2) @BeforeAll dan @AfterAll TIDAK perlu static — karena instance sudah ada saat method dipanggil.

Nested Tests: @Nested
// FILE: QueueTest.java
@DisplayName("A Queue")
public class QueueTest {

    private Queue<String> queue;

    @Nested                                   // Line A
    @DisplayName("when new")
    public class WhenNew {

        @BeforeEach
        void setUp() {
            queue = new LinkedList<>();        // Setup untuk nested class
        }

        @Test
        @DisplayName("when offer, size must be 1")
        void offerNewData() {
            queue.offer("Eko");
            Assertions.assertEquals(1, queue.size());
        }

        @Test
        @DisplayName("when offer 2 data, size must be 2")
        void offerMoreData() {
            queue.offer("Eko");
            queue.offer("Kurniawan");
            Assertions.assertEquals(2, queue.size());
        }
    }
}
Line A

@Nested — Memungkinkan kamu mengelompokkan test yang berkaitan ke dalam inner class. Sangat berguna untuk mendeskripsikan berbagai konteks test (saat kosong, saat ada data, saat error, dll). Di report, test muncul terindentasi: "A Queue > when new > when offer, size must be 1". Ini membuat test report mudah dibaca seperti spesifikasi!

🐘 Analogi PHPUnit

Di PHPUnit, kamu bisa bikin multiple test class untuk satu fitur, tapi tidak ada konsep "nested" secara native. Beberapa developer pakai Pest PHP yang punya describe()/it() untuk struktur serupa. @Nested di JUnit 5 memberikan struktur BDD-like yang sangat rapi tanpa library tambahan.

🧠 Mini Quiz — Chapter 3

Q: Di OrderedTest.java dengan @TestInstance(PER_CLASS), field counter dimulai dari 0. Setelah ketiga test dijalankan (dengan @Order 1,2,3), nilai counter adalah?

a) Selalu 1 — karena instance baru dibuat setiap test (PER_METHOD)
b) 3 — karena PER_CLASS menggunakan instance yang sama, counter++ dijalankan tiga kali akumulatif
c) 0 — karena @BeforeEach mereset counter setiap kali
d) Error — field tidak bisa di-share antar test di JUnit 5
Chapter 4
🏗 Conditional Tests: @Enabled & @Disabled
JUnit 5 menyediakan annotations untuk menjalankan test hanya pada kondisi tertentu — OS, versi JRE, system property, atau environment variable. Sangat powerful untuk CI/CD!
Jenis-Jenis Conditional Annotations
// FILE: ConditionTest.java
import org.junit.jupiter.api.condition.*;

public class ConditionTest {

    // ===== OS-based =====
    @Test
    @EnabledOnOs({OS.WINDOWS})                   // Line 1
    public void testRunOnlyOnWindows() { }

    @Test
    @DisabledOnOs({OS.WINDOWS})                  // Line 2
    public void testDisabledOnWindows() { }

    // ===== JRE Version-based =====
    @Test
    @EnabledOnJre({JRE.JAVA_8})
    void testEnabledOnJava8() { }

    @Test
    @EnabledForJreRange(min = JRE.JAVA_11, max = JRE.JAVA_15) // Line 3
    void testEnabledOnJava11To15() { }

    // ===== System Property-based =====
    @Test
    @EnabledIfSystemProperties({
        @EnabledIfSystemProperty(
            named = "java.vendor",
            matches = "Oracle Corporation"         // Line 4
        )
    })
    void testEnabledOnJavaVendorOracle() { }

    // ===== Environment Variable-based =====
    @Test
    @EnabledIfEnvironmentVariables({
        @EnabledIfEnvironmentVariable(
            named = "PROFILE",
            matches = "DEV"                        // Line 5
        )
    })
    void testEnabledOnProfileDev() { }

    @Test
    @DisabledIfEnvironmentVariables({
        @DisabledIfEnvironmentVariable(named = "PROFILE", matches = "DEV")
    })
    void testDisabledOnProfileDev() { }
}
Line 1

@EnabledOnOs({OS.WINDOWS}) — Test hanya jalan di Windows. Berguna saat kamu punya kode yang menggunakan Windows-specific API (file path separator, registry, dll). OS yang tersedia: WINDOWS, LINUX, MAC, SOLARIS.

Line 2

@DisabledOnOs — Kebalikan dari @EnabledOnOs. Setiap annotation @Enabled* punya pasangan @Disabled* yang melakukan hal sebaliknya.

Line 3

@EnabledForJreRange(min=JAVA_11, max=JAVA_15) — Test hanya jalan di Java 11 sampai 15 (inklusif). Sangat berguna saat testing fitur yang hanya ada di versi Java tertentu.

Line 4

named="java.vendor", matches="Oracle Corporation" — named adalah nama system property, matches adalah regex pattern. Lihat semua system property dengan System.getProperties().

Line 5

named="PROFILE", matches="DEV" — PROFILE adalah environment variable. Ini sangat berguna di CI/CD: set PROFILE=INTEGRATION di server CI untuk menjalankan hanya integration test, atau PROFILE=DEV untuk test tertentu yang hanya relevan di development.

💡 Insight: Melihat Semua System Properties
@Test
void testSystemProperties() {
    Properties properties = System.getProperties();
    properties.forEach((key, value) ->
        System.out.println(key + ": " + value)
    );
    // Output contoh:
    // java.vendor: Eclipse Adoptium
    // java.version: 17.0.9
    // os.name: Linux
    // user.home: /home/user
    // ... dsb
}

Ini setara dengan phpinfo() atau php_uname() di PHP. Jalankan test ini untuk melihat semua system properties yang tersedia di environment kamu — berguna saat menulis @EnabledIfSystemProperty.

TestInfo & Tags
// FILE: InformationTest.java
@DisplayName("information test")
public class InformationTest {

    @Test
    @Tags({@Tag("one"), @Tag("two")})     // Line A
    @DisplayName("this is test1")
    void test1(TestInfo info) {           // Line B — inject TestInfo
        System.out.println(info.getDisplayName());   // "this is test1"
        System.out.println(info.getTags());          // [one, two]
        System.out.println(info.getTestClass()
            .orElse(null));                          // class InformationTest
        System.out.println(info.getTestMethod()
            .orElse(null));                          // void test1(TestInfo)
    }
}

// FILE: SampleIntegrationTest.java
@Tags({@Tag("integration-test")})         // Line C — Tag di level class
public class SampleIntegrationTest {
    @Test void test1() { }
    @Test void test2() { }
}
Line A

@Tag — Label yang bisa digunakan untuk filter test saat menjalankan. Misalnya: jalankan hanya test berlabel "integration-test" di server CI: mvn test -Dgroups=integration-test. Setara dengan @group di PHPUnit.

Line B

TestInfo info — JUnit 5 bisa inject TestInfo sebagai parameter method test! Ini adalah Dependency Injection native JUnit — framework otomatis menyediakan object TestInfo yang berisi metadata test yang sedang berjalan.

Line C

Tag bisa ditaruh di level class — semua test di class itu otomatis mendapat tag tersebut. Berguna untuk memisahkan unit test dari integration test.

🐘 Analogi PHPUnit

Di PHPUnit, kamu bisa skip test berdasarkan kondisi dengan @requires annotation atau markTestSkipped(). @Tag di JUnit setara dengan @group di PHPUnit yang bisa digunakan untuk menjalankan subset test: phpunit --group integration.

🧠 Mini Quiz — Chapter 4

Q: Kamu punya test yang hanya relevan di environment CI/CD dan tidak perlu dijalankan di local dev. Annotation apa yang paling tepat?

a) @Disabled — skip selamanya
b) @EnabledIfEnvironmentVariable(named="CI", matches="true") — hanya jalan jika environment variable CI=true (umumnya di-set otomatis oleh CI/CD runner)
c) @EnabledOnJre(JRE.JAVA_8) — jalankan hanya di Java 8
d) @DisabledOnOs(OS.WINDOWS) — nonaktifkan di Windows
Chapter 5
🔄 Parameterized Test: Satu Test, Banyak Data
Daripada menulis 10 test method yang hampir identik, gunakan Parameterized Test! Satu test method dijalankan berulang dengan data berbeda.
@ValueSource: Data Langsung di Annotation
// FILE: RandomCalculatorTest.java

@DisplayName("Test calculator")
@ParameterizedTest(name = "{displayName} dengan parameter {0}")  // Line 1
@ValueSource(ints = {1, 2, 3, 4, 5, 6, 7, 8, 45, 34, 56})      // Line 2
void testWithParameter(int value) {                              // Line 3
    var expected = value + value;
    var result = calculator.add(value, value);
    Assertions.assertEquals(expected, result);
}
// JUnit akan menjalankan test ini 11 kali:
// "Test calculator dengan parameter 1" → add(1,1) == 2  ✅
// "Test calculator dengan parameter 2" → add(2,2) == 4  ✅
// ... dst
Line 1

@ParameterizedTest(name=...) — Mengganti @Test. Parameter name adalah template nama untuk setiap iterasi: {displayName} = nama dari @DisplayName, {0} = nilai parameter pertama. Setiap iterasi muncul sebagai test terpisah di report.

Line 2

@ValueSource(ints = {...}) — Source data berupa array literal. Tersedia untuk: ints, longs, doubles, strings, booleans, classes, dll.

Line 3

Parameter int value diisi otomatis oleh JUnit dari @ValueSource. Tidak perlu melakukan apa-apa — JUnit mengurus injeksi nilainya.

@MethodSource: Data dari Method
// Method yang menyediakan data — harus static!
public static List<Integer> parameterSource() {        // Line A
    return List.of(1, 2, 34, 56, 33, 65, 67, 35);
}

@DisplayName("Test calculator")
@ParameterizedTest(name = "{displayName} dengan parameter {0}")
@MethodSource({"parameterSource"})                      // Line B
void testWithMethodSource(Integer value) {
    var expected = value + value;
    var result = calculator.add(value, value);
    Assertions.assertEquals(expected, result);
}
// Menjalankan test 8 kali dengan nilai dari List
Line A

public static List<Integer> parameterSource() — Method sumber data harus static dan namanya cocok dengan string di @MethodSource. Bisa return Stream, List, Iterable, atau array. Berguna saat data perlu di-generate secara programatik atau dibaca dari file/database.

Line B

@MethodSource({"parameterSource"}) — Referensikan nama method sumber data sebagai String. Bisa lebih dari satu method: @MethodSource({"source1","source2"}).

💡 Insight: Kapan Pakai Parameterized Test?

Gunakan Parameterized Test saat kamu punya:

  • Boundary values: test input 0, 1, -1, MAX_INT, MIN_INT
  • Multiple valid inputs: semua harus menghasilkan hasil yang sama
  • Data-driven test: data dibaca dari CSV/database/API
  • Equivalence classes: kelompok input yang diperlakukan sama oleh kode

Ini setara dengan @dataProvider di PHPUnit!

🐘 Analogi PHPUnit
// PHPUnit @dataProvider
public function additionProvider(): array {
    return [[1,1,2], [2,2,4], [3,3,6]];
}

/** @dataProvider additionProvider */
public function testAdd(int $a, int $b, int $expected): void {
    $this->assertEquals($expected, $this->calculator->add($a, $b));
}

// JUnit 5 @MethodSource — konsep identik!
public static Stream<Arguments> additionProvider() {
    return Stream.of(
        Arguments.of(1, 1, 2),
        Arguments.of(2, 2, 4),
        Arguments.of(3, 3, 6)
    );
}
@ParameterizedTest
@MethodSource("additionProvider")
void testAdd(int a, int b, int expected) {
    assertEquals(expected, calculator.add(a, b));
}
🧠 Mini Quiz — Chapter 5

Q: Jika @ValueSource(ints = {1, 2, 3, 4, 5}), berapa kali test method akan dijalankan oleh JUnit?

a) 1 kali — semua nilai dipass sekaligus sebagai array
b) 5 kali — satu kali untuk setiap nilai dalam array, masing-masing sebagai test terpisah
c) Sesuai jumlah assertion di dalam test method
d) 0 kali — @ParameterizedTest butuh @MethodSource, tidak bisa pakai @ValueSource
Chapter 6
🔁 Repeated Test & Test Order
@RepeatedTest untuk menjalankan test berulang kali (berguna untuk test random/flaky), dan @TestMethodOrder untuk mengontrol urutan eksekusi test.
@RepeatedTest: Ulang Test N Kali
// FILE: RandomCalculatorTest.java

@DisplayName("Test random calculator")
@RepeatedTest(                                           // Line 1
    value = 10,
    name = "{displayName} ke {currentRepetition} dari {totalRepetitions}"
)
void testRandomRepeat(TestInfo info, Random random) {    // Line 2
    var a = random.nextInt();
    var b = random.nextInt();
    var result = calculator.add(a, b);
    var expected = a + b;
    Assertions.assertEquals(expected, result);
}
// Output di test report:
// "Test random calculator ke 1 dari 10"
// "Test random calculator ke 2 dari 10"
// ... sampai ke 10

// Versi dengan RepetitionInfo:
@RepeatedTest(value = 10, name = "{displayName}")
void testRandomRepeatInfo(
    TestInfo info,
    Random random,
    RepetitionInfo repetitionInfo           // Line 3
) {
    System.out.println(
        info.getDisplayName() + " ke "
        + repetitionInfo.getCurrentRepetition()
        + " dari " + repetitionInfo.getTotalRepetitions()
    );
    // ...
}
Line 1

@RepeatedTest(value=10) — Jalankan test ini 10 kali. Template name bisa menggunakan: {displayName}, {currentRepetition}, {totalRepetitions}. Berguna untuk test yang melibatkan randomness atau untuk mendeteksi flaky test (test yang kadang lulus kadang gagal).

Line 2

void testRandomRepeat(TestInfo info, Random random) — JUnit 5 inject parameter TestInfo dan Random otomatis! Random bisa di-inject karena ada RandomParameterResolver extension (lihat Chapter 9).

Line 3

RepetitionInfo repetitionInfo — Object yang berisi informasi repetisi saat ini. Berguna jika kamu perlu perilaku berbeda di repetisi tertentu (misal: inisialisasi berbeda di repetisi pertama).

@TestMethodOrder: Urutan Eksekusi Test
// FILE: OrderedTest.java
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
@TestMethodOrder(MethodOrderer.OrderAnnotation.class)    // Line A
public class OrderedTest {

    private int counter = 0;

    @Test @Order(1)       // Dijalankan PERTAMA
    void test3() { counter++; System.out.println(counter); } // Output: 1

    @Test @Order(2)       // Dijalankan KEDUA
    void test1() { counter++; System.out.println(counter); } // Output: 2

    @Test @Order(3)       // Dijalankan KETIGA
    void test2() { counter++; System.out.println(counter); } // Output: 3
}
// Perhatikan: nama method tidak harus sesuai urutan @Order!
Line A

@TestMethodOrder(MethodOrderer.OrderAnnotation.class) — Aktifkan pengurutan berdasarkan @Order. Alternatif lain: MethodOrderer.MethodName.class (urut by nama), MethodOrderer.Random.class (urutan random), MethodOrderer.DisplayName.class (urut by display name).

⚠ Peringatan: Hindari Test yang Bergantung Urutan!
Test yang saling bergantung (test coupling) adalah praktik yang buruk. Jika test2 hanya lulus karena test1 sudah dijalankan sebelumnya, kamu punya masalah desain. Gunakan @TestMethodOrder hanya untuk kasus yang sangat spesifik, misalnya integration test yang mensimulasikan alur user (login → create → read → delete).

🐘 Analogi PHPUnit

@RepeatedTest tidak ada padanannya langsung di PHPUnit vanilla. Paling dekat adalah loop di dalam test method: for($i=0;$i<10;$i++). Di JUnit, setiap repetisi muncul sebagai test terpisah di report — lebih informatif. Urutan test di PHPUnit tidak dijamin kecuali menggunakan @depends.

🧪 Mockito: Isolasi Dependency dengan Mock
Mockito adalah library mocking paling populer di Java. Gunakan saat ingin mengisolasi SUT dari dependency eksternal (database, API, service lain).
Arsitektur yang Akan Kita Test
// FILE: PersonRepository.java — Interface (kontrak)
public interface PersonRepository {
    Person selectById(String id);
    void insert(Person person);
}

// FILE: PersonService.java — Service yang bergantung pada Repository
public class PersonService {

    private PersonRepository personRepository;      // Dependency!

    public PersonService(PersonRepository personRepository) {
        this.personRepository = personRepository;   // Constructor Injection
    }

    public Person get(String id) {
        Person person = personRepository.selectById(id);
        if (person != null) {
            return person;
        } else {
            throw new IllegalArgumentException("Person not found");
        }
    }

    public Person register(String name) {
        var person = new Person(UUID.randomUUID().toString(), name);
        personRepository.insert(person);            // Panggil repository!
        return person;
    }
}
💡 Mengapa Butuh Mock?

Saat testing PersonService, kita ingin test logika service-nya saja — bukan logika database. Masalahnya: PersonService butuh PersonRepository untuk berjalan. Solusi: buat mock (objek palsu) dari PersonRepository yang kita kontrol sendiri perilakunya. Kita tidak perlu database sungguhan!

Membuat Mock Secara Manual
// FILE: MockTest.java — Mock manual tanpa Spring context

@Test
void testMock() {
    List<String> list = Mockito.mock(List.class);   // Line 1

    // Define behavior (stubbing)
    Mockito.when(list.get(0)).thenReturn("Eko");     // Line 2
    Mockito.when(list.get(100)).thenReturn("Khannedy");

    // Use the mock
    System.out.println(list.get(0));    // "Eko"
    System.out.println(list.get(100));  // "Khannedy"
    System.out.println(list.get(999));  // null (tidak di-stub)

    // Verify interaction
    Mockito.verify(list, Mockito.times(1)).get(0);   // Line 3
}
Line 1

Mockito.mock(List.class) — Buat objek mock dari List. Mock ini adalah objek palsu yang mengimplementasikan interface List tapi semua method-nya return nilai default (null, 0, false) kecuali yang di-stub.

Line 2

Mockito.when(list.get(0)).thenReturn("Eko") — Stubbing: "Ketika method get(0) dipanggil, kembalikan "Eko"". Ini mendefinisikan perilaku mock. Sintaks: when(kondisi).thenReturn(nilai). Bisa juga: thenThrow(exception), thenAnswer(callback).

Line 3

Mockito.verify(list, Mockito.times(1)).get(0) — Verification: "Pastikan method get(0) dipanggil tepat 1 kali". Ini memverifikasi interaction dengan mock, bukan hanya nilai return. Opsi lain: never(), atLeast(n), atMost(n).

Line C

Line D

when(personRepository.selectById("eko")).thenReturn(...) — Stub hanya diperlukan untuk test yang membutuhkan nilai spesifik. Di test testGetPersonNotFound, tidak ada stub — mock secara default return null untuk method yang mengembalikan object.

Line E

verify(personRepository, times(1)).insert(new Person(person.getId(),"Eko")) — Verifikasi bahwa insert() dipanggil tepat sekali dengan Person yang sama (menggunakan equals()). Inilah mengapa Person mengimplementasikan equals() — tanpanya, verifikasi ini akan gagal!

💡 Kenapa Person Perlu Override equals() & hashCode()?
// FILE: Person.java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    Person person = (Person) o;
    if (id != null ? !id.equals(person.id) : person.id != null) return false;
    return name != null ? name.equals(person.name) : person.name == null;
}

@Override
public int hashCode() {
    int result = id != null ? id.hashCode() : 0;
    result = 31 * result + (name != null ? name.hashCode() : 0);
    return result;
}
// Mockito.verify() menggunakan equals() untuk mencocokkan argument
// Java default: equals() membandingkan REFERENSI object (bukan nilai!)
// Tanpa override: new Person("eko","Eko") != new Person("eko","Eko") ❌
// Dengan override: new Person("eko","Eko") == new Person("eko","Eko") ✅
🐘 Analogi PHPUnit/Mockery
// PHPUnit dengan Mockery
$personRepo = Mockery::mock(PersonRepository::class);
$personRepo->shouldReceive('selectById')
           ->with('eko')

       .thenReturn(new Person("eko", "Eko"));

⏱ Timeout & Parallel Execution
Pastikan kode kamu cukup cepat dengan @Timeout, dan percepat test suite kamu dengan Parallel Execution!
@Timeout: Test Harus Selesai Dalam Batas Waktu
// FILE: SlowTest.java
import org.junit.jupiter.api.Timeout;
import java.util.concurrent.TimeUnit;

@Execution(ExecutionMode.CONCURRENT)            // Line 1
public class SlowTest {

    @Test
    @Timeout(value = 5, unit = TimeUnit.SECONDS) // Line 2
    void testSlow1() throws InterruptedException {
        Thread.sleep(4_000);  // 4 detik — masih dalam batas 5 detik ✅
    }

    @Test
    @Timeout(value = 5, unit = TimeUnit.SECONDS)
    void testSlow2() throws InterruptedException {
        Thread.sleep(4_000);  // 4 detik ✅
    }

    @Test
    @Timeout(value = 5, unit = TimeUnit.SECONDS)
    void testSlow3() throws InterruptedException {
        Thread.sleep(4_000);  // 4 detik ✅
    }
}
// Tanpa CONCURRENT: 3 × 4 detik = ~12 detik total
// Dengan CONCURRENT: berjalan paralel = ~4 detik total ✅
Line 1

@Execution(ExecutionMode.CONCURRENT) — Aktifkan eksekusi paralel untuk test-test di class ini. Tanpa ini, semua test dijalankan secara berurutan (sequential). Hasilnya: ketiga test yang masing-masing sleep(4 detik) akan berjalan bersamaan, total waktu ~4 detik bukan ~12 detik.

Line 2

@Timeout(value=5, unit=TimeUnit.SECONDS) — Jika test tidak selesai dalam 5 detik, JUnit akan fail test tersebut dengan TimeoutException. Unit bisa: SECONDS, MILLISECONDS, MINUTES, dll. Berguna untuk mendeteksi deadlock atau operasi yang terlalu lambat.

Konfigurasi Parallel Global (junit-platform.properties)
# src/test/resources/junit-platform.properties

# Aktifkan parallel execution secara global
junit.jupiter.execution.parallel.enabled=true

# Strategi: semua test class berjalan paralel (default: sequential)
junit.jupiter.execution.parallel.mode.default=concurrent

# Ukuran thread pool
junit.jupiter.execution.parallel.config.strategy=fixed
junit.jupiter.execution.parallel.config.fixed.parallelism=4
💡 Kapan Pakai Parallel Execution?

Parallel execution mempercepat test suite secara signifikan tapi ada syaratnya:

  • Test harus thread-safe: tidak ada shared mutable state antar test
  • Test harus independent: tidak bergantung pada hasil test lain
  • Tidak ada race condition: test yang mengakses resource yang sama (DB, file) bisa konflik

Untuk integration test yang pakai database: hati-hati! Parallel bisa menyebabkan data race. Gunakan isolated database per thread atau rollback transaction setelah setiap test.

🐘 Analogi PHPUnit

PHPUnit tidak punya parallel execution native. Untuk test paralel di PHP, orang biasanya pakai paratest (library terpisah) atau menjalankan test suite secara terpisah di CI. Di JUnit 5, parallel execution adalah fitur built-in — jauh lebih mudah dikonfigurasi.

ParameterResolver: Inject Custom Object ke Test
// FILE: RandomParameterResolver.java
import org.junit.jupiter.api.extension.*;
import java.util.Random;

public class RandomParameterResolver implements ParameterResolver { // Line 1

    private Random random = new Random();

    @Override
    public boolean supportsParameter(
        ParameterContext parameterContext,
        ExtensionContext extensionContext
    ) throws ParameterResolutionException {
        return parameterContext.getParameter().getType() == Random.class; // Line 2
    }

    @Override
    public Object resolveParameter(
        ParameterContext parameterContext,
        ExtensionContext extensionContext
    ) throws ParameterResolutionException {
        return random;     // Line 3
    }
}
Line 1

implements ParameterResolver — Interface yang harus diimplementasikan untuk membuat custom parameter injector. JUnit 5 sudah built-in resolver untuk: TestInfo, RepetitionInfo, TestReporter. Kita extend dengan resolver kustom untuk tipe apapun.

Line 2

parameterContext.getParameter().getType() == Random.class — "Apakah parameter yang diminta bertipe Random?" Jika true, extension ini akan menangani injeksi. JUnit memanggil supportsParameter() untuk setiap parameter yang tidak bisa di-resolve secara built-in.

Line 3

Return random — instance Random yang akan di-inject ke parameter test. Karena random adalah field instance (bukan baru dibuat tiap kali), semua test mendapat instance yang sama.

// Pola ARRANGE - ACT - ASSERT (AAA)

@Test
void testGetPersonSuccess() {
    // === ARRANGE ===
    // Setup mock behavior
    Mockito.when(personRepository.selectById("eko"))
           .thenReturn(new Person("eko", "Eko"));

    // === ACT ===
    // Jalankan kode yang ingin ditest
    var person = personService.get("eko");

    // === ASSERT ===
    // Verifikasi hasil
    Assertions.assertNotNull(person);
    Assertions.assertEquals("eko", person.getId());
    Assertions.assertEquals("Eko", person.getName());
    // Optional: verifikasi interaksi dengan mock
    Mockito.verify(personRepository, Mockito.times(1))
           .selectById("eko");
}

@Test
