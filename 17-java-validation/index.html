✅ Java Bean Validation

Modul pembelajaran interaktif untuk developer PHP/Laravel yang migrasi ke Java.
Materi: Jakarta Validation (JSR-380) + Hibernate Validator — dari setup dasar hingga custom constraint, groups, payload, method validation, dan value extractor.

jakarta.validation Hibernate Validator ConstraintViolation Custom Constraint Groups & Sequence Method Validation Value Extractor

Bean Validation di Java adalah standar resmi (JSR-380 / Jakarta Validation) untuk memvalidasi object. Berbeda dengan validasi manual, kamu cukup menambahkan annotation pada field dan biarkan framework menangani sisanya.

Jakarta Validation adalah spesifikasi (JSR-380) — sekumpulan interface dan annotation standar, tapi tanpa implementasi. Hibernate Validator adalah implementasi resminya — library yang benar-benar menjalankan validasi. Keduanya dibutuhkan:

Chapter 01
⚙️ Setup Validator
ValidatorFactory · Validator · AbstractValidatorTest

Sebelum bisa memvalidasi apapun, kamu perlu membuat objek Validator. Caranya melalui ValidatorFactory — semacam pabrik yang mengkonfigurasi dan membangun validator.

Cara Paling Sederhana
@Test
void testCreateValidator() {
    ValidatorFactory factory =
        Validation.buildDefaultValidatorFactory(); // (1)

    Validator validator = factory.getValidator();     // (2)

    Assertions.assertNotNull(validator);

    factory.close();                                  // (3)
}
(1) buildDefaultValidatorFactory() Membuat factory dengan konfigurasi default — Hibernate Validator akan otomatis terdeteksi sebagai implementasi (via Java ServiceLoader). Ini adalah entry point utama ke seluruh ecosystem Bean Validation.
(2) getValidator() Mendapatkan instance Validator siap pakai. Validator adalah thread-safe dan bisa di-reuse — tidak perlu membuat baru setiap kali validasi.
(3) factory.close() ValidatorFactory mengimplementasikan Closeable — harus ditutup saat tidak digunakan untuk melepas resource. Di Spring Boot, factory ini dikelola oleh Spring container dan otomatis di-close.
Setup dengan Value Extractor (Konfigurasi Lanjut)
// AbstractValidatorTest.java — base class untuk semua test
@BeforeEach
void setUp() {
    validatorFactory = Validation.byDefaultProvider().configure() // (A)
        .addValueExtractor(new DataValueExtractor())         // (B)
        .addValueExtractor(new EntryValueExtractorKey())
        .addValueExtractor(new EntryValueExtractorValue())
        .addValueExtractor(new DataIntegerValueExtractor())
        .buildValidatorFactory();

    validator = validatorFactory.getValidator();
    executableValidator = validator.forExecutables();       // (C)
    messageInterpolator = validatorFactory.getMessageInterpolator(); // (D)
}

@AfterEach
void tearDown() { validatorFactory.close(); }             // selalu close!
(A) byDefaultProvider().configure() Cara konfigurasi lanjutan — Builder Pattern yang memungkinkan penambahan Value Extractor, Message Interpolator, dan pengaturan lain sebelum factory dibangun.
(B) addValueExtractor() Mendaftarkan custom Value Extractor untuk tipe container kustom (Data<T>, Entry<K,V>). Tanpa ini, validator tidak tahu cara "mengintip" ke dalam container custom untuk memvalidasi isinya. Dibahas detail di Chapter 13.
(C) forExecutables() Mendapatkan ExecutableValidator — sub-validator khusus untuk memvalidasi parameter dan return value dari method/constructor. Dibahas di Chapter 9.
(D) getMessageInterpolator() Mendapatkan engine interpolasi pesan — mengubah template seperti {order.id.invalid} menjadi pesan yang bisa dibaca manusia dengan dukungan i18n. Dibahas di Chapter 11.
⚡ Analogi Laravel

ValidatorFactory di Java ≈ Validator::make() facade di Laravel. Bedanya: di Laravel, kamu membuat validator baru setiap kali dengan data dan rules yang diberikan langsung. Di Java, Validator adalah objek stateless yang bisa di-reuse — kamu memberikan objek yang ingin divalidasi, dan ia membaca annotation dari class tersebut. Tidak ada "rules array" terpisah.

🧪 Mini Quiz — Chapter 1

Q: Mengapa ValidatorFactory harus ditutup dengan .close() setelah selesai digunakan?

A. Karena Validator tidak thread-safe dan bisa menyebabkan race condition
B. Karena ValidatorFactory memegang resource (thread pool, cache) yang harus dilepas agar tidak terjadi memory/resource leak
C. Karena setelah close, validator tidak bisa membaca annotation lagi
D. Hanya formalitas coding style, tidak ada efek nyata
Chapter 02
✅ ConstraintViolation — Membaca Hasil Validasi
ConstraintViolationTest.java · validator.validate() · ConstraintViolation API

Hasil validasi di Java adalah Set<ConstraintViolation<T>> — himpunan semua pelanggaran constraint yang ditemukan. Jika set kosong → semua valid. Jika tidak kosong → ada error.

Anatomy: Model Person
public class Person {
    @Size(max = 20, message = "first name length max must 20 characters")
    @NotBlank(message = "first name can not blank")
    private String firstName;

    @Size(max = 20, message = "first name length max must 20 characters")
    @NotBlank(message = "last name can not blank")
    private String lastName;

    @NotNull(message = "address can not null")
    @Valid
    private Address address;

    private List<@NotBlank(message = "hobby can not blank") String> hobbies;
}
Validasi Dasar & Membaca ConstraintViolation
@Test
void testValidationFailedNotBlank() {
    Person person = new Person(); // firstName=null, lastName=null

    Set<ConstraintViolation<Person>> violations =
        validator.validate(person);        // (1)

    Assertions.assertEquals(2, violations.size()); // (2)

    for (ConstraintViolation<Person> v : violations) {
        System.out.println("Message : "    + v.getMessage());             // (3)
        System.out.println("Bean : "       + v.getLeafBean());           // (4)
        System.out.println("Constraint : " + v.getConstraintDescriptor()
                                            .getAnnotation());           // (5)
        System.out.println("Value : "      + v.getInvalidValue());       // (6)
        System.out.println("Path : "       + v.getPropertyPath());      // (7)
    }
}
(1) validator.validate(object) Satu method untuk memvalidasi seluruh object. Validator membaca semua annotation constraint dari class Person via Reflection, lalu menjalankan setiap constraint. Hasilnya adalah Set — urutan violations tidak dijamin (bukan List).
(2) violations.size() == 2 Person baru (null firstName, null lastName) → 2 violations: satu untuk firstName, satu untuk lastName. @NotBlank juga menangani null — tidak perlu dua annotation terpisah seperti di Laravel (required|string).
(3) getMessage() Pesan error yang sudah diinterpolasi — siap ditampilkan ke user. Ini yang kamu set di atribut message annotation.
(4) getLeafBean() Object yang mengandung field yang invalid. Untuk validasi langsung, ini sama dengan object yang divalidasi. Berguna saat ada nested validation.
(5) getConstraintDescriptor().getAnnotation() Annotation constraint yang dilanggar — lengkap dengan semua atributnya. Berguna untuk membedakan apakah violation karena @NotBlank atau @Size pada field yang sama.
(6) getInvalidValue() Nilai aktual yang menyebabkan violation. Untuk null firstName → hasilnya null. Untuk string terlalu panjang → string aslinya.
(7) getPropertyPath() Path ke field yang bermasalah, dalam format dot notation. Untuk field langsung: firstName. Untuk nested: address.street. Untuk element list: hobbies[0]. Ini yang kamu gunakan untuk menampilkan error di posisi form yang tepat.

Throw Exception jika Ada Violation
// AbstractValidatorTest.java
void validateWithException(Object o) {
    Set<ConstraintViolation<Object>> violations = validator.validate(o);
    if (!violations.isEmpty()) {
        throw new ConstraintViolationException(violations); // (A)
    }
}

// ExceptionTest.java — cara menggunakan di production code
@Test
void testException() {
    Assertions.assertThrows(ConstraintViolationException.class, () -> {
        Person person = new Person();
        validateWithException(person);
    });
}
✅ Pola Umum di Service Layer Spring Boot
Di production Spring Boot, kamu tidak perlu menulis validateWithException() manual. Cukup tambahkan @Validated di class dan Spring akan otomatis melempar ConstraintViolationException jika ada violation. Atau di Controller, gunakan @Valid pada parameter — Spring akan melempar MethodArgumentNotValidException yang bisa di-handle oleh @ExceptionHandler.
❌ Salah — Iterasi violation sebagai List
// violations adalah SET, bukan LIST
// Urutan tidak dijamin!
violations.get(0); // → tidak ada method get()
// → CompileError: Set has no get(int)

// Jangan asumsikan firstName selalu index 0!
✅ Benar — Iterasi via for-each atau stream
// Iterasi semua violations
for (var v : violations) {
    System.out.println(v.getPropertyPath()
        + ": " + v.getMessage());
}

// Atau convert ke Map untuk API response
violations.stream().collect(
    Collectors.groupingBy(v ->
        v.getPropertyPath().toString()));
⚡ Analogi Laravel

Set<ConstraintViolation> di Java ≈ MessageBag di Laravel. violation.getPropertyPath() ≈ $errors->keys() (nama field). violation.getMessage() ≈ $errors->first('field'). Perbedaan: di Laravel MessageBag hasilnya sudah terstruktur per field; di Java kamu perlu group violations by property path sendiri jika ingin format yang sama.

Chapter 03
🔧 Custom Constraint — Buat Validasi Sendiri
CheckCase · CheckCaseValidator · ConstraintValidator interface

Annotation bawaan kadang tidak cukup. Ketika butuh logic validasi custom, kamu bisa membuat constraint annotation sendiri beserta validator-nya. Inilah cara Spring's @UniqueEmail, @ValidPassword, dll bekerja.

Step 1 — Buat Annotation Constraint
// CheckCase.java — validasi apakah string semua UPPER atau LOWER case
@Documented
@Constraint(validatedBy = { CheckCaseValidator.class })  // (1)
@Target({ FIELD, ANNOTATION_TYPE })
@Retention(RUNTIME)
public @interface CheckCase {

    CaseMode mode();                           // (2) required attribute
    String   message() default "invalid case format"; // (3) wajib ada
    Class<?>[] groups() default {};             // (4) wajib ada
    Class<? extends Payload>[] payload() default {}; // (5) wajib ada
}
(1) @Constraint(validatedBy) Meta-annotation yang menandai ini sebagai constraint annotation. Wajib ada. validatedBy menunjuk ke class yang mengimplementasikan logic validasi. Bisa lebih dari satu (untuk berbagai tipe).
(2) CaseMode mode() Custom attribute yang wajib diisi saat menggunakan annotation: @CheckCase(mode = CaseMode.UPPER). Ini seperti parameter di PHP rule custom.
(3-5) message, groups, payload Ketiga atribut ini WAJIB ada di setiap custom constraint — ini adalah kontrak yang ditetapkan oleh Jakarta Validation spec. Tanpa salah satunya, validator factory akan throw exception saat startup.
Step 2 — Implementasi ConstraintValidator
public class CheckCaseValidator
    implements ConstraintValidator<CheckCase, String> { // (A)

    private CaseMode caseMode;

    @Override
    public void initialize(CheckCase constraintAnnotation) {  // (B)
        caseMode = constraintAnnotation.mode();
    }

    @Override
    public boolean isValid(String value,
                            ConstraintValidatorContext context) { // (C)
        if (value == null) return true;  // (D) null ditangani @NotNull

        if (caseMode == CaseMode.UPPER) {
            return value.equals(value.toUpperCase());
        } else if (caseMode == CaseMode.LOWER) {
            return value.equals(value.toLowerCase());
        }
        return false;
    }
}
(A) ConstraintValidator<A,T> Interface generik dengan dua type parameter: A = annotation yang divalidasi (CheckCase), T = tipe nilai yang divalidasi (String). Kamu bisa membuat beberapa validator untuk annotation yang sama dengan tipe berbeda.
(B) initialize() Dipanggil sekali saat validator diinisialisasi. Tempat yang tepat untuk membaca atribut annotation (seperti mode) dan menyimpannya sebagai field untuk digunakan di isValid().
(C) isValid(value, context) Dipanggil setiap kali validasi dijalankan. Return true = valid, false = violation. context digunakan untuk kustomisasi pesan violation (dibahas di Chapter 8).
(D) if null → return true Best practice Jakarta Validation: Biarkan null lolos di custom constraint — biarkan @NotNull/@NotBlank yang menanganinya. Ini memisahkan tanggung jawab dengan bersih dan menghindari duplikasi logic.
Step 3 — Menggunakan Custom Constraint
// Di Payment.java
@CheckCase(mode = CaseMode.UPPER, message = "order id must be uppercase",
    groups = { CreditCardPaymentGroup.class })
private String orderId;
❌ Salah — Validasi null di dalam custom constraint
public boolean isValid(String value, ...) {
    // Validasi null di sini = duplikasi
    if (value == null) {
        return false; // ← jangan lakukan ini!
    }
    // Sekarang butuh DUA annotation: @NotNull + @CheckCase
    // Padahal @CheckCase sudah "menggantikan" @NotNull
}
✅ Benar — Biarkan null lolos, delegate ke @NotNull
public boolean isValid(String value, ...) {
    if (value == null) return true; // ← delegate
    // Logic sebenarnya di sini
}

// Di field: kombinasikan annotation
@NotBlank  // tangani null + empty
@CheckCase(mode = UPPER) // tangani case
private String orderId;
⚡ Analogi Laravel

Membuat CheckCaseValidator di Java persis seperti membuat custom Rule class di Laravel:
php artisan make:rule CheckCase → mengimplementasikan method passes($attribute, $value) dan message(). Di Java, isValid() ≈ passes(), dan pesan dikonfigurasi di annotation bukan di validator class. Kelebihan Java: satu validator bisa digunakan di banyak class hanya dengan annotation, tanpa perlu mendaftarkan rule secara manual.

Chapter 04
🔗 Constraint Composition — Menggabungkan Constraint
CheckOrderId · @ReportAsSingleViolation · Composed Annotation

Daripada menumpuk banyak annotation di setiap field, kamu bisa membuat satu annotation yang menggabungkan beberapa constraint. Ini prinsip DRY (Don't Repeat Yourself) di level annotation.

Masalah: Annotation Berulang di Banyak Field
// Tanpa composition — harus repeat di setiap field orderId di seluruh project
@CheckCase(mode = CaseMode.UPPER, message = "order id must be uppercase", ...)
@NotBlank(message = "order id cannot be blank", ...)
@Size(min = 1, max = 10, message = "order id size 1-10", ...)
private String orderId; // → 3 annotation setiap kali pakai orderId!
Solusi: @CheckOrderId — Composed Constraint
// CheckOrderId.java — menggabungkan 3 constraint menjadi 1
@CheckCase(groups = {...}, mode = CaseMode.UPPER, message = "{order.id.upper}")
@NotBlank(groups = {...}, message = "{order.id.notblank}")
@Size(groups = {...}, min = 1, max = 10, message = "{order.id.size}")
@Documented
@Constraint(validatedBy = {})     // (1) kosong — pakai constraint di atas
@Target({FIELD})
@Retention(RUNTIME)
@ReportAsSingleViolation          // (2) semua error jadi satu
public @interface CheckOrderId {
    String   message() default "invalid order id";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// Sekarang di Payment.java cukup:
@CheckOrderId(groups = {...}, message = "{order.id.invalid}")
private String orderId; // ← 1 annotation, 3 validasi berjalan
(1) @Constraint(validatedBy = {}) Array kosong — annotation ini tidak punya validator sendiri. Validasinya dilakukan oleh annotation-annotation yang menempel di atasnya (@CheckCase, @NotBlank, @Size).
(2) @ReportAsSingleViolation Jika salah satu dari 3 constraint gagal, hanya satu violation yang dilaporkan — violation dari @CheckOrderId itu sendiri (menggunakan pesan dari message()). Tanpa ini, bisa ada 3 violations terpisah yang membingungkan user. Pilihan yang lebih user-friendly.
Tanpa @ReportAsSingleViolation (orderId = "eko-yang-sangat-panjang") checkCase: order id must be uppercase
size: order id size 1-10
→ 2 violations terpisah
Dengan @ReportAsSingleViolation checkOrderId: invalid order id
→ 1 violation gabungan
⚡ Analogi Laravel

Constraint Composition di Java ≈ membuat custom Rule yang di dalamnya memanggil banyak rule lain, atau membuat macro validasi dengan Validator::extend(). Keuntungan Java: tidak perlu kode PHP apapun — cukup susun annotation. @ReportAsSingleViolation seperti mengembalikan satu pesan error yang dirangkum, bukan satu per rule.

Chapter 05
🏷️ Validation Groups — Validasi Bersyarat
GroupTest.java · CreditCardPaymentGroup · VirtualAccountPaymentGroup

Sebuah object sering perlu divalidasi secara berbeda tergantung konteks. Contoh: field creditCard hanya relevan saat metode pembayaran adalah kartu kredit. Validation Groups memungkinkan ini dengan cara yang elegan.

Mendefinisikan Groups (Cukup Interface Kosong)
// Cukup interface kosong — bertindak sebagai marker/tag
public interface CreditCardPaymentGroup {}
public interface VirtualAccountPaymentGroup {}
Menggunakan Groups pada Annotation
public class Payment {

    // orderId: wajib valid di KEDUA metode pembayaran
    @CheckOrderId(groups = { CreditCardPaymentGroup.class,
                              VirtualAccountPaymentGroup.class })
    private String orderId;

    // creditCard: HANYA divalidasi untuk group CreditCard
    @LuhnCheck(groups = { CreditCardPaymentGroup.class })
    @NotBlank(groups = { CreditCardPaymentGroup.class })
    private String creditCard;

    // virtualAccount: HANYA divalidasi untuk group VirtualAccount
    @NotBlank(groups = { VirtualAccountPaymentGroup.class })
    private String virtualAccount;
}
Menjalankan Validasi dengan Group Tertentu
@Test
void testCreditCardGroup() {
    Payment payment = new Payment();
    payment.setOrderId("0111");
    payment.setAmount(20_000L);
    payment.setCreditCard("123");   // nomor CC tidak valid (Luhn check)

    // Validasi HANYA constraint yang punya group CreditCardPaymentGroup
    validateWithGroups(payment, CreditCardPaymentGroup.class); // (1)
    // → violation: creditCard (LuhnCheck gagal)
    // → virtualAccount TIDAK divalidasi (beda group)
}

// Implementasi validateWithGroups:
void validateWithGroups(Object o, Class<?>... groups) {
    Set<...> violations = validator.validate(o, groups); // (2) varargs!
    // ...
}
(1) validateWithGroups(obj, Group.class) Dengan menyertakan group, hanya constraint yang memiliki group tersebut yang akan dijalankan. Constraint tanpa group (Default group) TIDAK ikut dijalankan kecuali kamu include Default.class.
(2) validator.validate(o, groups) Parameter kedua varargs — bisa menyertakan lebih dari satu group: validator.validate(o, GroupA.class, GroupB.class). Semua constraint dari kedua group akan dijalankan.
💡 Default Group
Constraint yang tidak mendeklarasikan groups secara otomatis masuk ke Default.class (dari jakarta.validation.groups.Default). Saat kamu memanggil validator.validate(obj) tanpa group → hanya constraint dengan Default group yang dijalankan. Constraint dengan custom group (seperti CreditCardPaymentGroup) tidak akan dijalankan.
❌ Salah — Lupa sertakan group saat validasi
// Payment punya constraint dengan group CreditCard
// Tapi divalidasi tanpa group:
validator.validate(payment); // ← tidak ada group!
// → 0 violations, meski creditCard kosong!
// → karena @NotBlank(groups=CreditCard) tidak ikut
✅ Benar — Sertakan group yang sesuai konteks
// Saat user memilih pembayaran CC:
validator.validate(payment,
    CreditCardPaymentGroup.class);
// → constraint dengan group CreditCard dijalankan ✓

// Saat user memilih VA:
validator.validate(payment,
    VirtualAccountPaymentGroup.class);
⚡ Analogi Laravel

Validation Groups di Java ≈ sometimes() dan required_if di Laravel, tapi jauh lebih terstruktur. Di Laravel kamu menulis kondisi di dalam rules() method: 'credit_card' => 'required_if:method,credit_card'. Di Java, kondisi itu dikodekan sebagai "group" — terpisah dari annotation itu sendiri. Keuntungan: annotation lebih bersih dan reusable, logic kondisional ada di layer service yang memanggil validate().

🧪 Mini Quiz — Chapter 5

Q: Kamu memanggil validator.validate(payment) tanpa group pada object Payment yang semua constraint-nya menggunakan custom group. Apa yang terjadi?

Chapter 06
🔄 Group Convert & Group Sequence
@ConvertGroup · @GroupSequence · validasi berurutan & cascade

Dua fitur lanjutan Groups: Group Sequence untuk menjalankan group secara berurutan (berhenti di error pertama), dan Group Convert untuk mengubah group saat cascade ke nested object.

@GroupSequence — Validasi Berurutan
// PaymentGroup.java — mendefinisikan urutan validasi
@GroupSequence(value = {
    Default.class,                   // (1) jalankan Default group dulu
    CreditCardPaymentGroup.class,   // (2) jika OK, jalankan ini
    VirtualAccountPaymentGroup.class // (3) jika OK, jalankan ini
})
public interface PaymentGroup {}

// Penggunaan — cukup gunakan PaymentGroup sebagai group
validateWithGroups(payment, PaymentGroup.class);
💡 Behavior Group Sequence: Short-circuit pada Error
Jika ada violation di group pertama (Default), validator berhenti dan tidak melanjutkan ke group berikutnya. Ini berguna untuk memvalidasi "prasyarat" dulu sebelum validasi yang lebih kompleks — mirip seperti validation chain di Laravel yang berhenti di bail.
@ConvertGroup — Ubah Group Saat Cascade
// Payment.java — cascade ke Customer dengan group conversion
@Valid
@NotNull(groups = { CreditCardPaymentGroup.class,
                     VirtualAccountPaymentGroup.class })
@ConvertGroup(from = VirtualAccountPaymentGroup.class,
              to = Default.class)                 // (A)
@ConvertGroup(from = CreditCardPaymentGroup.class,
              to = Default.class)                 // (B)
private Customer customer;
(A-B) @ConvertGroup Saat validasi Payment menggunakan group VirtualAccountPaymentGroup (atau CreditCard), dan validator melakukan cascade ke object Customer via @Valid, group akan dikonversi menjadi Default. Ini penting karena Customer tidak tahu tentang Payment groups — ia hanya punya constraint dengan Default group. Tanpa ini, cascade tidak akan memvalidasi apapun di Customer (karena tidak ada constraint Customer dengan Payment groups).
⚡ Analogi Laravel

@GroupSequence ≈ Laravel's bail rule — berhenti di error pertama. Contoh Laravel: 'email' => 'bail|required|email|unique:users' — jika required gagal, email dan unique tidak dicek. Di Java, group sequence melakukan hal yang sama tapi di level group, bukan field individual. @ConvertGroup tidak ada padanan langsung di Laravel.

Chapter 07
📦 Nested & Container Validation
@Valid · NestedValidationTest · ContainerDataTest · List<@NotBlank>

Validation otomatis berhenti di batas object — tidak otomatis masuk ke nested object atau elemen collection. Untuk itu, ada @Valid (cascade validation) dan container element constraints.

@Valid — Cascade ke Nested Object
// Person.java
@NotNull(message = "address can not null")
@Valid        // (1) tanpa ini, Address tidak divalidasi lebih dalam
private Address address;

// NestedValidationTest.java
@Test
void testNested() {
    Person person = new Person();
    person.setFirstName("Eko");
    person.setLastName("Kurniawan");

    Address address = new Address();  // street, city, country = null
    person.setAddress(address);

    Set<ConstraintViolation<Person>> violations = validator.validate(person);
    // Violations: address.street, address.city, address.country (null → NotBlank gagal)
    // propertyPath: "address.street", "address.city", "address.country"
}
(1) @Valid Tanpa @Valid: validator hanya mengecek apakah address null atau tidak (via @NotNull). Dengan @Valid: jika address tidak null, validator akan masuk ke dalam object Address dan menjalankan constraint-constraintnya. @Valid bisa diletakkan di field, parameter method, atau constructor parameter.
Container Element Constraints — Validasi di Dalam Collection
// Person.java — validasi SETIAP ELEMEN di dalam List
private List<@NotBlank(message = "hobby can not blank") String> hobbies;

// ContainerDataTest.java
@Test
void testContainerData() {
    person.setHobbies(new ArrayList<>());
    person.getHobbies().add("");       // → violation: hobbies[0]
    person.getHobbies().add("   ");    // → violation: hobbies[1]

}
✅ Container Element Constraints — Didukung Secara Bawaan
Sejak Jakarta Validation 2.0+, annotation di dalam type argument generic (List<@NotBlank String>, Map<String, @Size(min=3) String>, Optional<@Email String>) didukung secara native. Validator otomatis mengiterasi elemen dan menvalidasi tiap elemen. Property path bahkan menyertakan index: hobbies[0].

⚡ Analogi Laravel

@Valid pada nested object ≈ validasi nested di Laravel: 'address.street' => 'required'. Container element constraint List<@NotBlank> ≈ 'hobbies.*' => 'required|string' di Laravel. Di Java lebih deklaratif — annotation ditulis langsung di definisi field, bukan di file validasi terpisah.

Chapter 08
🏛️ Class-Level Validation — Validasi Antar Field
@CheckPassword · CheckPasswordValidator · ClassLevelValidationTest

Kadang validasi membutuhkan perbandingan antara lebih dari satu field — misalnya memastikan password dan retypePassword sama. Ini tidak bisa dilakukan di field level. Solusinya: class-level constraint.

Annotation di Level Class
// Register.java — annotation di class, bukan di field
@CheckPassword(message = "password and retype password must same")
public class Register {
    @NotBlank private String username;
    @NotBlank private String password;
    @NotBlank private String retypePassword;
}

// @CheckPassword annotation — @Target include TYPE
@Constraint(validatedBy = { CheckPasswordValidator.class })
@Target({ FIELD, ANNOTATION_TYPE, TYPE }) // ← TYPE penting!
@Retention(RUNTIME)
public @interface CheckPassword { ... }
Validator dengan Custom Violation Node
public class CheckPasswordValidator
    implements ConstraintValidator<CheckPassword, Register> { // (A)

    @Override
    public boolean isValid(Register value,
                            ConstraintValidatorContext context) {
        if (value.getPassword() == null
            || value.getRetypePassword() == null) {
            return true; // skip — @NotBlank yang tangani
        }

        boolean isValid = value.getPassword()
                               .equals(value.getRetypePassword());

        if (!isValid) {
            context.disableDefaultConstraintViolation();         // (B)

            context.buildConstraintViolationWithTemplate(
                    context.getDefaultConstraintMessageTemplate())
                .addPropertyNode("password")                    // (C)
                .addConstraintViolation();

            context.buildConstraintViolationWithTemplate(
                    context.getDefaultConstraintMessageTemplate())
                .addPropertyNode("retypePassword")
                .addConstraintViolation();
        }
        return isValid;
    }
}
(A) ConstraintValidator<CheckPassword, Register> Type parameter kedua adalah Register (bukan String) — karena kita memvalidasi seluruh object. Dari dalam isValid(), kita bisa mengakses semua field Register.
(B) disableDefaultConstraintViolation() Menonaktifkan violation default (yang property path-nya mengacu ke root object / class). Tanpa ini, violation akan muncul di level class tanpa property path yang jelas — menyulitkan frontend untuk menampilkan error di field yang tepat.
(C) addPropertyNode("password") Membuat violation dengan property path yang spesifik. Hasil: violation dengan path password dan retypePassword — frontend tahu persis di field mana harus menampilkan error.
⚡ Analogi Laravel

Class-level validation ≈ rule confirmed di Laravel ('password' => 'confirmed') yang otomatis mengecek field password_confirmation. Bedanya: di Java, logikanya kamu tulis sendiri dan bisa dikustomisasi sepenuhnya. Fungsi addPropertyNode("password") ≈ menambahkan pesan error ke key spesifik di MessageBag Laravel: $validator->errors()->add('password', 'message').

🧪 Mini Quiz — Chapter 8

Q: Mengapa di CheckPasswordValidator kita memanggil context.disableDefaultConstraintViolation() sebelum menambahkan violation baru?

A. Untuk menghindari exception saat menambahkan property node
B. Agar violation default (di level class tanpa property path) tidak muncul — kita ingin violation hanya di field "password" dan "retypePassword" saja
C. Karena tanpa ini, constraint validator akan dijalankan dua kali
D. Untuk menonaktifkan semua violation sebelumnya dari constraint lain

⚡ Method & Constructor Validation
ExecutableValidator · validateParameters · validateReturnValue · CrossParameter

Bean Validation tidak hanya untuk field — kamu juga bisa memvalidasi parameter method, return value method, dan parameter constructor. Ini adalah fondasi dari Spring's @Validated yang otomatis memvalidasi parameter service method.

Model: Person dengan Method yang Divalidasi
public class Person {
    // Validasi PARAMETER method
    public void sayHello(@NotBlank(message = "name can not blank") String name) {
        System.out.println("Hello " + name);
    }

    // Validasi RETURN VALUE method
    @NotBlank(message = "full name can not blank")
    public String fullName() {
        return firstName + " " + lastName;
    }
}
Validasi Parameter Method
@Test
void testSayHello() throws NoSuchMethodException {
    Person person = new Person();
    String name = ""; // invalid

    Method method = Person.class.getMethod("sayHello", String.class); // (1)

    Set<ConstraintViolation<Person>> violations = executableValidator
        .validateParameters(person, method, new Object[]{ name }); // (2)

    // violations: sayHello.arg0 → "name can not blank"
}
Validasi Return Value
@Test
void testFullName() throws NoSuchMethodException {
    Person person = new Person();
    person.setFirstName("");
    person.setLastName("");

    String returnValue = person.fullName(); // " " (spasi doang)

    Method method = Person.class.getMethod("fullName");
    Set<ConstraintViolation<Person>> violations = executableValidator
        .validateReturnValue(person, method, returnValue); // (3)

    // violations: fullName.<return value> → "full name can not blank"
}
(1) Reflection untuk Method Method validation menggunakan Reflection — perlu mendapatkan Method object terlebih dahulu. Ini karena ExecutableValidator perlu membaca annotation yang ada di parameter/return type method tersebut.
(2) validateParameters(obj, method, args[]) Memvalidasi argumen yang akan diberikan ke method, sebelum method dipanggil. Argumen pertama: instance. Kedua: Method object. Ketiga: array argumen yang ingin divalidasi.
(3) validateReturnValue(obj, method, returnValue) Memvalidasi nilai yang dikembalikan method, setelah method dipanggil. Di production dengan Spring @Validated, ini dijalankan otomatis via AOP setelah method selesai.
Cross-Parameter Validation — Password vs RetypePassword di Method
// UserService.java
@CheckPasswordParameter(passwordParam = 1, retypePasswordParam = 2)
public void register(
    @NotBlank String username,
    @NotBlank String password,
    @NotBlank String retypePassword) { ... }

// CheckPasswordParameterValidator — validator untuk SEMUA parameter sekaligus
@SupportedValidationTarget(ValidationTarget.PARAMETERS)   // (A)
public class CheckPasswordParameterValidator
    implements ConstraintValidator<CheckPasswordParameter, Object[]> { // (B)

    @Override
    public boolean isValid(Object[] value, ...) {
        // value[0] = username, value[1] = password, value[2] = retypePassword
        String password       = (String) value[passwordParam];
        String retypePassword = (String) value[retypePasswordParam];
        if (password == null || retypePassword == null) return true;
        return password.equals(retypePassword);
    }
}
(A) @SupportedValidationTarget(PARAMETERS) Menandai bahwa validator ini bekerja pada array parameter method (bukan pada satu nilai field). Tanpa ini, Jakarta Validation tidak tahu bahwa ini adalah cross-parameter validator dan akan error.
(B) ConstraintValidator<..., Object[]> Type parameter kedua adalah Object[] — menerima array semua parameter method. Index di dalam array sesuai urutan parameter method: value[0] = username, value[1] = password, dst.
✅ Di Production Spring Boot: Tidak Perlu Manual!
Semua ini dilakukan secara otomatis saat kamu menggunakan @Validated di Spring: 
@Service
@Validated  // ← aktifkan method validation via AOP
public class UserService {
    public void register(@NotBlank String username, ...) {
        // Spring otomatis validateParameters sebelum method ini berjalan
        // Jika ada violation → ConstraintViolationException dilempar otomatis
    }
}
Chapter 10
📬 Payload — Metadata Tambahan pada Violation
EmailErrorPayload · PayloadTest.java · violation.getConstraintDescriptor().getPayload()

Payload adalah cara menambahkan metadata tambahan ke sebuah constraint — tanpa mengubah logic validasinya. Payload digunakan oleh consumer violation (bukan validator itu sendiri) untuk memutuskan tindakan apa yang harus diambil saat violation terjadi.

Mendefinisikan Payload Class
// EmailErrorPayload.java — action yang diambil saat ada violation
public class EmailErrorPayload implements Payload {

    public void sendEmail(ConstraintViolation<?> violation) {
        System.out.println("Sending alert email for: "
            + violation.getMessage());
    }
}
Menggunakan Payload di Annotation
// Payment.java
@LuhnCheck(
    groups  = { CreditCardPaymentGroup.class },
    message = "invalid credit card number",
    payload = { EmailErrorPayload.class }  // (1)
)
private String creditCard;
Membaca Payload saat Memproses Violations
@Test
void testPayload() {
    // ... setup payment ...

    Set<ConstraintViolation<Object>> violations = validator.validate(payment, ...);

    for (ConstraintViolation<Object> violation : violations) {
        Set<Class<? extends Payload>> payloads =
            violation.getConstraintDescriptor().getPayload(); // (2)

        for (Class<? extends Payload> p : payloads) {
            if (p == EmailErrorPayload.class) {                  // (3)
                new EmailErrorPayload().sendEmail(violation);
            }
        }
    }
}
(1) payload = {EmailErrorPayload.class} Mendaftarkan payload ke constraint. Payload tidak mempengaruhi logika validasi — ia adalah "tag" yang memberi tahu consumer "jika constraint ini dilanggar, lakukan sesuatu yang spesifik".
(2) getConstraintDescriptor().getPayload() Membaca payload yang terdaftar dari violation. Mengembalikan Set class payload — bisa ada lebih dari satu payload per constraint.
(3) instanceof check via == Cek apakah payload adalah tipe yang kamu tangani, lalu buat instance-nya dan jalankan action. Pattern ini memisahkan "apa yang salah" (constraint) dari "apa yang harus dilakukan" (payload action).
💡 Use Case Payload di Dunia Nyata
  • ErrorSeverityPayload — menandai apakah ini error kritis, warning, atau info
  • AlertEmailPayload — kirim email notifikasi ke admin jika constraint ini dilanggar
  • AuditLogPayload — catat ke audit log saat ada pelanggaran constraint tertentu
⚡ Analogi Laravel

Payload tidak ada padanan langsung di Laravel standar. Konsep yang paling dekat adalah membuat event khusus (Event::dispatch(new ValidationFailed(...))) saat validasi gagal, lalu listener yang melakukan berbagai tindakan. Di Java, payload adalah cara yang lebih deklaratif: kamu "tag" constraint dengan tindakan yang harus dilakukan, lalu consumer yang membacanya — tanpa perlu event system terpisah.

Chapter 11
💬 Messages, Interpolation & i18n
ValidationMessages.properties · {key} syntax · MessageInterpolator · Locale

Pesan error tidak harus di-hardcode di dalam annotation. Dengan sistem pesan Bean Validation, pesan bisa diambil dari file .properties, mendukung variabel dinamis, dan bahkan dilocalize ke berbagai bahasa.

Sistem Pesan: Dari Annotation ke File Properties
// 1. Di annotation: gunakan {key} syntax
@CheckOrderId(message = "{order.id.invalid}")
private String orderId;

// 2. File: src/main/resources/ValidationMessages.properties
order.id.invalid=invalid order id
order.id.notblank=order id cannot be blank
order.id.size=order id size must be between {min} and {max} characters ← variabel!
order.id.upper=order id must be uppercase
order.amount.range=amount must be between {min} and {max}
💡 Tiga Sumber Pesan (Prioritas Tertinggi ke Terendah)
  1. Atribut message langsung: @NotBlank(message = "Cannot be blank")
  2. File ValidationMessages.properties custom: {my.custom.key}
  3. Pesan default dari library: {jakarta.validation.constraints.NotBlank.message}

Variabel dinamis seperti {min} dan {max} otomatis diisi dari atribut annotation — kamu tidak perlu menulis ulang nilainya.

Internationalization — Pesan Berbeda per Bahasa
// File: ValidationMessages_in_ID.properties (Bahasa Indonesia)
order.id.invalid=id pesanan tidak valid
order.amount.range=jumlah harus antara {min} dan {max}

// MessageInternationalizationTest.java
@Test
void testI18N() {
    Locale.setDefault(new Locale("in", "ID"));   // (1) set locale Indonesia

    Payment payment = new Payment();
    payment.setOrderId("324098239...terlalu panjang");
    payment.setAmount(10L);

    validateWithGroups(payment, CreditCardPaymentGroup.class);
    // Pesan muncul dalam Bahasa Indonesia ✓
}
Manual Interpolation per Locale
@Test
void testMessageInterpolator() {
    Locale locale = new Locale("in", "ID");

    Set<ConstraintViolation<Object>> violations = validator.validate(payment, ...);
    for (ConstraintViolation<Object> violation : violations) {
        MessageInterpolator.Context context = new MessageInterpolatorContext(
            violation.getConstraintDescriptor(),
            violation.getInvalidValue(),
            violation.getRootBeanClass(),
            violation.getPropertyPath(),
            violation.getConstraintDescriptor().getAttributes(),
            violation.getConstraintDescriptor().getAttributes(),
            ExpressionLanguageFeatureLevel.VARIABLES, true
        );
        String message = messageInterpolator
            .interpolate(violation.getMessageTemplate(), context, locale); // (2)
        System.out.println(message); // pesan dalam bahasa Indonesia
    }
}
(1) Locale.setDefault() Cara paling sederhana — set locale global untuk seluruh JVM. Cocok untuk aplikasi single-language. Untuk multi-language (misalnya API yang melayani banyak negara sekaligus), gunakan manual interpolation per request seperti di (2).
(2) messageInterpolator.interpolate(template, context, locale) Interpolasi pesan secara manual dengan locale spesifik. Ini adalah cara yang benar untuk aplikasi multi-language — setiap request bisa menyertakan locale preferensi user (dari header Accept-Language) tanpa mengubah setting global.
⚡ Analogi Laravel

File ValidationMessages.properties di Java ≈ file lang/en/validation.php di Laravel. Syntax {order.id.invalid} ≈ :custom.order_id.required di Laravel. Variabel dinamis seperti {min} ≈ :min di Laravel validation messages. Perbedaan: di Laravel translasi diatur via app()->setLocale(); di Java via Locale.setDefault() atau per-request interpolation.

Chapter 12
📊 Metadata API — Introspeksi Constraint
BeanDescriptor · PropertyDescriptor · ConstraintDescriptor · MetadataTest

Bean Validation menyediakan API untuk menginspeksi constraint yang terdaftar pada sebuah class — tanpa harus melakukan validasi. Berguna untuk generate dokumentasi API, UI form generation, atau tooling lainnya.

Membaca Metadata Constraint
@Test
void testPerson() {
    BeanDescriptor beanDescriptor =
        validator.getConstraintsForClass(Person.class);  // (1)

    for (PropertyDescriptor property :
            beanDescriptor.getConstrainedProperties()) {  // (2)

        System.out.println(property.getPropertyName());     // "firstName", "lastName", "address"

        for (ConstraintDescriptor<?> constraint :
                property.getConstraintDescriptors()) {    // (3)
            System.out.println(constraint);
            // @NotBlank(message=..., groups=[...], payload=[...])
        }
    }
}
(1) getConstraintsForClass() Mendapatkan deskriptor bean — overview semua constraint yang ada di class tersebut. Tidak menjalankan validasi, hanya membaca metadata.
(2) getConstrainedProperties() Hanya property yang memiliki constraint yang dikembalikan (bukan semua field). Berguna untuk generate form validation di frontend secara otomatis berdasarkan model Java.
(3) getConstraintDescriptors() Semua constraint di property ini, lengkap dengan atributnya (message, groups, payload, custom attributes). ConstraintDescriptor ini sama dengan yang bisa kamu baca dari violation.getConstraintDescriptor().
✅ Use Case: Auto-generate OpenAPI Validation Schema
Dengan Metadata API, kamu bisa scan semua constraint di request DTO dan otomatis menghasilkan schema validasi untuk dokumentasi Swagger/OpenAPI — tanpa menduplikasi informasi. Library seperti Springdoc OpenAPI sudah melakukan ini secara otomatis.
Chapter 13
🧩 Value Extractor — Validasi di Container Custom
DataValueExtractor · DataIntegerValueExtractor · EntryValueExtractor · @UnwrapByDefault

Secara default, Bean Validation tahu cara mengekstrak nilai dari List, Set, Map, dan Optional. Tapi untuk container custom seperti Data<T> atau Entry<K,V>? Kamu perlu membuat Value Extractor sendiri.

Masalah: Container Custom Tidak Dikenali Validator
// SampleData.java
public class SampleData {
    @NotNull
    private Data<@NotBlank @Size(min = 10) String> data;
    // → Tanpa ValueExtractor, @NotBlank dan @Size pada String TIDAK dijalankan!
}
Solusi: Implementasi ValueExtractor
// DataValueExtractor.java — mengajarkan validator cara "buka" Data<T>
public class DataValueExtractor
    implements ValueExtractor<Data<@ExtractedValue ?>> {   // (1)

    @Override
    public void extractValues(Data<?> originalValue,
                               ValueReceiver receiver) {
        Object data = originalValue.getData();
        receiver.value(null, data);                            // (2)
    }
}

// DataIntegerValueExtractor.java — untuk tipe non-generic (DataInteger)
@UnwrapByDefault                                             // (3)
public class DataIntegerValueExtractor
    implements ValueExtractor<@ExtractedValue(type = Integer.class) DataInteger> {

    @Override
    public void extractValues(DataInteger originalValue,
                               ValueReceiver receiver) {
        receiver.value(null, originalValue.getData());
    }
}

// EntryValueExtractorKey.java — extractor untuk KEY dari Entry<K,V>
public class EntryValueExtractorKey
    implements ValueExtractor<Entry<@ExtractedValue ?, ?>> {

    @Override
    public void extractValues(Entry<?, ?> originalValue,
                               ValueReceiver receiver) {
        receiver.keyedValue(null, "key",
                            originalValue.getKey());          // (4)
    }
}
(1) @ExtractedValue Menandai type argument mana yang akan diekstrak untuk divalidasi. Data<@ExtractedValue ?> berarti "ekstrak nilai dari type parameter pertama T".
(2) receiver.value(node, value) Memberikan nilai yang diekstrak ke validator. Parameter pertama adalah nama node (untuk property path) — null berarti gunakan nama field aslinya. Parameter kedua adalah nilai yang akan divalidasi.
(3) @UnwrapByDefault Untuk container non-generic (DataInteger yang selalu berisi Integer), tandai dengan ini agar validator otomatis "membuka" container dan langsung memvalidasi nilai di dalamnya. Constraint di field langsung diterapkan ke Integer yang diekstrak — bukan ke object DataInteger.
(4) receiver.keyedValue("key", value) Untuk container multi-nilai seperti Entry<K,V>, gunakan keyedValue dengan identifier (seperti "key" atau "value") yang akan muncul di property path violation: entry[key], entry[value].
💡 Mendaftarkan Value Extractor
Value Extractor harus didaftarkan ke ValidatorFactory: 
Validation.byDefaultProvider().configure()
    .addValueExtractor(new DataValueExtractor())
    .addValueExtractor(new DataIntegerValueExtractor())
    .buildValidatorFactory();
Atau otomatis via Java ServiceLoader: buat file META-INF/services/jakarta.validation.valueextraction.ValueExtractor berisi nama fully qualified class extractor-mu.
⚡ Analogi Laravel

Value Extractor tidak ada padanan langsung di Laravel karena PHP tidak punya sistem container generic yang se-kompleks Java. Konsep yang paling dekat: kamu menulis custom rule yang tahu cara "membuka" sebuah object khusus dan mengekstrak nilai di dalamnya untuk divalidasi. Bedanya: di Java, ini adalah extension point resmi yang terintegrasi dengan ekosistem validasi.
