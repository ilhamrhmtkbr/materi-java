🧠 Konteks: Mengapa Ini Penting?

Bayangkan aplikasi web yang harus melayani 10.000 request sekaligus. Setiap request butuh membaca database (ada latensi I/O ~50ms). Masalah ini adalah masalah konkurensi — bagaimana menangani banyak pekerjaan secara bersamaan tanpa membuang-buang resource?

💡 Virtual Thread adalah bagian dari Project Loom

Project Loom adalah inisiatif OpenJDK untuk membawa konkurensi ringan ke Java. Virtual Thread masuk sebagai fitur preview di Java 19, stabil di Java 21 (LTS). Jika kamu menggunakan Spring Boot 3.2+ dengan Java 21, Virtual Thread bisa diaktifkan hanya dengan satu baris konfigurasi.

1
Era Platform Thread (Java 1.0 – sekarang)
Satu Java Thread = satu OS Thread. Setiap thread memakai ~1MB stack memory. Membuat ribuan thread = memori meledak. Thread pool (ExecutorService) hadir sebagai mitigasi, tapi masih terbatas.
Java 1.0+
2
Era Reactive Programming (Java 8–20)
Framework seperti Project Reactor / WebFlux muncul sebagai solusi. Kode ditulis secara non-blocking dengan callback/Mono/Flux. Efisien tapi sangat sulit dibaca, di-debug, dan di-maintain.
Java 8–20
3
Era Virtual Thread (Java 21+)
JVM mengelola ribuan "virtual thread" di atas sejumlah kecil OS thread. Kode ditulis blocking seperti biasa, tapi JVM yang handle scheduling secara non-blocking di balik layar. The best of both worlds.
Java 21 (LTS) ✨
4
Spring Boot 3.2 + Virtual Thread
Spring Boot 3.2 langsung mendukung Virtual Thread dengan konfigurasi minimal. Seluruh request handling web bisa berjalan di atas Virtual Thread secara otomatis.
Spring Boot 3.2+
Chapter 1
😵 Masalah Konkurensi di Java

Sebelum memahami solusinya, kita perlu benar-benar paham masalahnya. Kenapa banyak thread itu mahal? Apa itu blocking I/O? Mengapa ini problem besar untuk aplikasi web?

Bagaimana Thread Bekerja di Java (Sebelum Java 21)

Secara default, setiap Java Thread adalah Platform Thread — artinya satu Java Thread dipetakan langsung ke satu OS Thread. OS Thread adalah entitas yang dikelola langsung oleh sistem operasi, dan sangat mahal:

BiayaPlatform ThreadDampak pada 10.000 Thread
Stack Memory~512KB – 1MB per thread~5–10 GB RAM hanya untuk stack!
Context SwitchOS harus simpan/restore CPU registerOverhead CPU besar, latensi meningkat
Thread CreationSystem call ke OS, relatif lambatStartup time aplikasi lambat
SchedulingDikelola OS (preemptive)OS kewalahan mengelola ribuan thread
Apa itu Blocking I/O?

Masalah terbesar bukan jumlah komputasi, tapi waktu menunggu. Saat thread melakukan operasi I/O (query database, HTTP call, baca file), thread tersebut memblokir — hanya duduk menunggu, tidak melakukan apa-apa, tapi tetap memakai memori dan slot OS thread.

Visualisasi: Thread yang Sedang Menunggu I/O (Blocking)
Thread-1 (DB query)
RUN
⏳ BLOCKED — menunggu DB response (50ms)
RUN
Thread-2 (HTTP call)
RUN
⏳ BLOCKED — menunggu API response (100ms)
RUN
Thread-3 (baca file)
RUN
⏳ BLOCKED — menunggu disk I/O (30ms)
RUN

Selama BLOCKED: thread duduk diam, tidak bisa dipakai untuk pekerjaan lain, tapi tetap memakan ~1MB RAM. Bayangkan 10.000 thread seperti ini sekaligus.

Solusi Lama: Thread Pool

Untuk mengatasi mahalnya pembuatan thread, dikembangkan Thread Pool melalui ExecutorService. Thread dibuat sekali, disimpan dalam pool, dan digunakan ulang. Tapi ini tetap tidak menyelesaikan masalah blocking — saat thread di pool sedang menunggu I/O, thread tersebut tidak bisa dipakai untuk request lain.

// Cara lama: Thread Pool dengan ukuran tetap
ExecutorService pool = Executors.newFixedThreadPool(200);
// Hanya bisa menangani 200 request concurrent!
// Request ke-201 harus ANTRI sampai ada thread yang selesai.
// Jika setiap thread blocking 50ms untuk DB, throughput sangat terbatas.
🔗 Analogi PHP/Laravel

Di PHP tradisional (FPM), setiap request mendapat satu proses/worker. Jika konfigurasi kamu pm.max_children = 100, artinya hanya 100 request yang bisa berjalan bersamaan. Request ke-101 harus menunggu. Masalah di Java Platform Thread mirip persis: jumlah thread = kapasitas concurrent request. Virtual Thread memecah batasan ini — seperti kalau PHP bisa menangani 1.000.000 request bersamaan dengan resource yang sama.

Chapter 2
🖥️ Platform Thread — Cara Lama

Platform Thread adalah thread Java klasik yang dipetakan langsung ke OS Thread. Di Java 21, API-nya diperbarui dengan builder pattern yang lebih ekspresif melalui Thread.ofPlatform().

Kode — PlatformThreadApp.java
// PlatformThreadApp.java
package belajar.virtual.thread;

import java.time.Duration;

public class PlatformThreadApp {

  public static void main(String[] args) {
    for (int i = 0; i < 10_000; i++) {

      // Thread.ofPlatform() → Builder pattern baru di Java 21 untuk Platform Thread
      Thread thread = Thread.ofPlatform()
          .name("eko-" + i)     // Beri nama thread untuk debugging
          .daemon(false)         // Bukan daemon thread — JVM tidak keluar sebelum ini selesai
          .unstarted(() -> {     // Buat thread tapi JANGAN langsung jalankan
            try {
              Thread.sleep(Duration.ofSeconds(2)); // Simulasi I/O blocking 2 detik
              System.out.println("Hello " + Thread.currentThread() + "!");
            } catch (InterruptedException e) {
              throw new RuntimeException(e);
            }
          });

      thread.start(); // Mulai thread secara eksplisit
    }
    // Tidak ada System.in.read() → main thread selesai, tapi non-daemon thread masih berjalan
    // JVM TIDAK akan keluar sampai semua 10.000 thread selesai (karena daemon=false)
  }
}
// ⚠️ PERINGATAN: Menjalankan ini akan membuat 10.000 OS Thread sekaligus
// Ini bisa membuat server/laptop kehabisan memory atau crash!
Bedah Baris per Baris
KodePenjelasanUnder the Hood
Thread.ofPlatform() Static factory method baru di Java 21 yang mengembalikan Thread.Builder.OfPlatform. Ini adalah cara modern membuat Platform Thread. Cara lama: new Thread(runnable) masih valid tapi kurang ekspresif. Tidak langsung membuat OS Thread — hanya membuat builder object.
.name("eko-" + i) Set nama thread. Sangat penting untuk debugging: saat melihat thread dump di tools seperti JVisualVM atau IntelliJ, nama thread membantu identifikasi thread mana yang bermasalah. Nama disimpan sebagai field di objek Thread. OS juga bisa menerima nama ini (platform-dependent).
.daemon(false) Daemon thread: thread yang dianggap "pembantu" — JVM boleh keluar meski daemon thread masih berjalan. Non-daemon thread: JVM menunggu sampai semua selesai. Main thread adalah non-daemon. Default thread baru mengikuti parent-nya. JVM memonitor jumlah non-daemon thread aktif. Saat jumlahnya 0, JVM akan shutdown.
.unstarted(runnable) Buat thread tapi belum dijalankan. Berbeda dengan .start(runnable) yang langsung menjalankan. Berguna saat kamu butuh konfigurasi thread sebelum menjalankannya. Setelah unstarted(), OS Thread belum dibuat. Baru dibuat saat thread.start() dipanggil.
Thread.sleep(Duration.ofSeconds(2)) Cara modern menentukan durasi sleep (Java 9+): pakai Duration object, lebih readable dari Thread.sleep(2000) (millisecond). Thread akan blocking selama 2 detik. Saat sleep: OS thread masuk state TIMED_WAITING. OS tidak memberi CPU time, tapi slot OS thread tetap terpakai.
10_000 Underscore di angka literal adalah fitur Java 7+ untuk keterbacaan. 10_000 = 10000. Ini hanya sugar syntax — compiler mengabaikan underscore. Tidak ada perbedaan bytecode antara 10000 dan 10_000.
⚠️ Jangan Jalankan Ini di Production!

Membuat 10.000 Platform Thread sekaligus sangat berbahaya: bisa menghabiskan ~10GB RAM hanya untuk stack thread, menyebabkan context switch storm, dan berpotensi crash JVM atau OS. Kode ini ada untuk tujuan demonstrasi perbedaan dengan Virtual Thread — bukan pola yang dianjurkan.

API Builder Lengkap: Thread.ofPlatform()
// Semua opsi builder Platform Thread (Java 21+)
Thread thread = Thread.ofPlatform()
    .name("worker-", 0)         // Nama dengan prefix dan counter auto-increment
    .daemon(true)               // Set sebagai daemon thread
    .priority(Thread.MAX_PRIORITY) // Set prioritas (1-10, default 5)
    .stackSize(512 * 1024)      // Custom stack size dalam bytes (hati-hati!)
    .inheritInheritableThreadLocals(false) // Jangan inherit ThreadLocal dari parent
    .unstarted(runnable);       // Buat belum start, atau .start(runnable) langsung start

// Versi singkat — buat dan langsung start
Thread.ofPlatform().start(() -> System.out.println("running!"));
🔗 Analogi PHP Worker

Platform Thread di Java mirip dengan proses PHP-FPM worker. Setiap worker memiliki memori tersendiri, bisa berjalan mandiri, dan dikelola langsung oleh OS. Di PHP: jika pm.max_children = 100 berarti 100 worker = 100 proses OS. Di Java: 10.000 Platform Thread = 10.000 OS Thread — sama-sama mahal per-unit-nya. Itulah mengapa keduanya butuh pooling: PHP FPM pool, Java Thread Pool (ExecutorService).

🧪 Mini Quiz

Apa perbedaan antara .unstarted(runnable) dan .start(runnable) pada Thread builder?

A. Tidak ada perbedaan, keduanya langsung menjalankan thread
B. unstarted() membuat thread tapi belum menjalankannya — perlu panggil .start() secara eksplisit; start() langsung menjalankan
C. unstarted() untuk daemon thread, start() untuk non-daemon
D. unstarted() adalah cara lama, start() adalah cara baru
Chapter 3
⚡ Virtual Thread — Revolusi Java 21

Virtual Thread adalah thread yang dikelola sepenuhnya oleh JVM, bukan OS. Mereka sangat ringan, murah dibuat, dan ribuan bisa berjalan di atas sejumlah kecil OS thread. Satu perubahan kecil dari Thread.ofPlatform() ke Thread.ofVirtual() — dampaknya luar biasa.

Kode — VirtualThreadApp.java
// VirtualThreadApp.java
package belajar.virtual.thread;

import java.io.IOException;
import java.time.Duration;

public class VirtualThreadApp {

  public static void main(String[] args) throws IOException {
    for (int i = 0; i < 10_000; i++) {

      // Thread.ofVirtual() → HAMPIR IDENTIK dengan ofPlatform()
      // Perubahan: ofPlatform() → ofVirtual()
      // TIDAK ADA .daemon() karena Virtual Thread SELALU daemon
      Thread thread = Thread.ofVirtual()
          .name("eko-" + i)    // Nama tetap bisa di-set untuk debugging
          .unstarted(() -> {
            try {
              Thread.sleep(Duration.ofSeconds(2)); // JVM akan "unmount" thread saat ini!
              System.out.println("Hello " + Thread.currentThread() + "!");
            } catch (InterruptedException e) {
              throw new RuntimeException(e);
            }
          });

      thread.start();
    }

    System.in.read(); // Tunggu input agar main thread tidak langsung selesai
    // (Virtual Thread adalah daemon, jadi tanpa ini JVM langsung exit)
  }
}
// ✅ AMAN: 10.000 Virtual Thread hanya memakai memori ~10MB total!
// Virtual Thread dikelola JVM di atas sejumlah kecil "carrier thread" (OS Thread)
Bagaimana Virtual Thread Bekerja di Balik Layar

Konsep kunci yang perlu dipahami: Virtual Thread bukan OS Thread. Mereka berjalan di atas Carrier Thread (Platform Thread) yang jumlahnya terbatas (biasanya = jumlah CPU core).

Arsitektur: Virtual Thread di atas Carrier Thread
JVM Layer — Virtual Threads (jutaan bisa ada)
VT-0 🟢 run
VT-1 ⏸️ wait I/O
VT-2 🟢 run
VT-3 ⏸️ wait DB
VT-4 ⏸️ wait HTTP
VT-5 🟢 run
VT-6 ⏸️ wait I/O
... 9993 lainnya
⬇️ JVM Scheduler (ForkJoinPool) — hanya mount VT yang aktif ke Carrier Thread
OS Layer — Carrier Threads (= jumlah CPU core, misal 8)
CT-0 menjalankan VT-0
CT-1 menjalankan VT-2
CT-2 menjalankan VT-5
CT-3 idle (semua VT menunggu I/O)

VT yang sedang menunggu I/O (⏸️) di-unmount dari Carrier Thread. Carrier Thread bebas menjalankan VT lain. Saat I/O selesai, VT di-mount kembali ke Carrier Thread yang tersedia.

Bedah Baris per Baris
KodePenjelasanPerbedaan dari Platform Thread
Thread.ofVirtual() Static factory method untuk Virtual Thread. Mengembalikan Thread.Builder.OfVirtual. API-nya hampir identik dengan ofPlatform() — itulah keindahan desainnya. Bukan OS Thread — thread object yang ringan dikelola JVM.
Tidak ada .daemon() Virtual Thread selalu daemon — ini tidak bisa diubah. Artinya JVM bisa keluar meskipun masih ada Virtual Thread yang berjalan. Platform Thread bisa non-daemon. Itulah mengapa perlu System.in.read() di contoh ini — untuk mencegah main thread (dan JVM) langsung exit.
Thread.sleep(Duration.ofSeconds(2)) Pada Virtual Thread, sleep() tidak memblokir OS Thread! JVM akan unmount Virtual Thread dari Carrier Thread saat sleep, dan Carrier Thread bebas menjalankan Virtual Thread lain. Pada Platform Thread, sleep memblokir OS Thread sepenuhnya selama durasi sleep.
System.in.read() Ini adalah trik untuk menjaga main thread tetap hidup. Karena Virtual Thread adalah daemon, JVM akan exit setelah semua non-daemon thread selesai. Main thread adalah non-daemon — dengan menunggu input, kita cegah JVM exit prematur. Di PlatformThreadApp tidak perlu ini karena Platform Thread bisa non-daemon (.daemon(false)).
✅ Kekuatan Virtual Thread: Mount/Unmount

Saat Virtual Thread memanggil operasi blocking I/O (sleep, baca DB, HTTP call), JVM secara otomatis unmounts Virtual Thread dari Carrier Thread. Carrier Thread bebas menjalankan Virtual Thread lain. Saat I/O selesai, Virtual Thread di-mount kembali ke Carrier Thread yang tersedia. Ini terjadi transparan — kode kamu tetap ditulis secara blocking, tapi JVM yang handle non-blocking-nya.

🔗 Analogi: Karyawan vs Tugas Menunggu

Bayangkan kamu punya 8 karyawan (= 8 Carrier Thread / CPU core). Ada 10.000 tugas yang perlu diselesaikan, tapi 90% waktu setiap tugas adalah menunggu (I/O). Tanpa Virtual Thread: setiap tugas mendapat satu karyawan eksklusif, dan karyawan hanya duduk menunggu — sangat tidak efisien. Dengan Virtual Thread: jika karyawan sedang menunggu untuk satu tugas, tugas itu "diletakkan di meja" dan karyawan mengambil tugas lain. Saat tugas pertama sudah bisa dilanjutkan, karyawan mana saja bisa mengambilnya. Inilah scheduling yang dilakukan JVM secara otomatis.

🖥️ Platform Thread — Mahal
// Setiap thread = 1 OS Thread = ~1MB RAM
Thread t = Thread.ofPlatform()
    .name("worker-" + i)
    .daemon(false)
    .unstarted(task);
t.start();
// 10.000 thread = ~10GB RAM ← berbahaya!
⚡ Virtual Thread — Ringan
// Setiap thread = JVM-managed = ~1KB memori
Thread t = Thread.ofVirtual()
    .name("worker-" + i)
    // tidak ada .daemon() — selalu daemon
    .unstarted(task);
t.start();
// 10.000 thread = ~10MB RAM ✅ aman!

Chapter 4
🏭 ExecutorService + Virtual Thread

ExecutorService adalah antarmuka standar Java untuk menjalankan task secara asynchronous. Dengan Executors.newVirtualThreadPerTaskExecutor(), setiap task mendapat Virtual Thread baru — cara paling idiomatis dan production-ready untuk menggunakan Virtual Thread.

Kode — ExecutorServiceVirtualThreadApp.java
// ExecutorServiceVirtualThreadApp.java
package belajar.virtual.thread;

import java.io.IOException;
import java.time.Duration;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ExecutorServiceVirtualThreadApp {

  public static void main(String[] args) throws IOException {

    // Membuat ExecutorService yang membuat 1 Virtual Thread baru per task
    // Berbeda dengan fixed thread pool — tidak ada batas jumlah thread!
    ExecutorService executorService = Executors.newVirtualThreadPerTaskExecutor();

    for (int i = 0; i < 10_000; i++) {
      executorService.execute(() -> { // submit task → ExecutorService buat VT baru
        try {
          Thread.sleep(Duration.ofSeconds(2));
          System.out.println("Hello " + Thread.currentThread() + "!");
        } catch (InterruptedException e) {
          throw new RuntimeException(e);
        }
      });
    }

    System.in.read(); // Tunggu agar main thread tidak exit duluan
  }
}
Ekosistem ExecutorService — Semua Pilihan

Java menyediakan berbagai factory method di kelas Executors. Pelajari semuanya agar bisa memilih yang tepat:

// Perbandingan semua ExecutorService factory methods

// ─── LAMA / Thread Pool based ──────────────────────────────────────────────
// Fixed size: maks N thread berjalan bersamaan, sisanya antri
ExecutorService fixed = Executors.newFixedThreadPool(10);

// Single thread: hanya 1 thread, semua task dieksekusi secara serial
ExecutorService single = Executors.newSingleThreadExecutor();

// Cached: buat thread baru jika semua sibuk, idle 60s → dihapus
ExecutorService cached = Executors.newCachedThreadPool();

// Scheduled: untuk task yang perlu dijalankan berkala atau terjadwal
ScheduledExecutorService scheduled = Executors.newScheduledThreadPool(5);

// ─── BARU (Java 21) / Virtual Thread based ────────────────────────────────
// 1 Virtual Thread per task — DIREKOMENDASIKAN untuk I/O-bound tasks
ExecutorService virtual = Executors.newVirtualThreadPerTaskExecutor();

// ─── Cara submit task ─────────────────────────────────────────────────────
// execute(): fire and forget, tidak mengembalikan hasil
executorService.execute(() -> System.out.println("task!"));

// submit(): mengembalikan Future — bisa mendapat hasil atau status
Future<String> future = executorService.submit(() -> "hasil task");
String result = future.get(); // Blocking wait untuk hasil

// ─── PENTING: Selalu shutdown setelah selesai ──────────────────────────────
executorService.shutdown();         // Tunggu task yang ada selesai, lalu shutdown
executorService.shutdownNow();      // Interrupt semua task, langsung shutdown

// Atau gunakan try-with-resources (Java 19+, implements AutoCloseable)
try (ExecutorService es = Executors.newVirtualThreadPerTaskExecutor()) {
  es.execute(task1);
  es.execute(task2);
} // Otomatis shutdown saat keluar blok try
Bedah Baris per Baris
KodePenjelasanKapan Digunakan
Executors.newVirtualThreadPerTaskExecutor() Factory method baru Java 21. Setiap task yang di-submit mendapat satu Virtual Thread baru. Tidak ada pooling — VT sangat murah sehingga tidak perlu di-pool. Thread langsung dibuang setelah task selesai. Aplikasi I/O-bound: web server, service yang banyak query DB / HTTP call ke service lain.
executorService.execute(Runnable) Submit task tanpa menunggu hasil. Runnable = Functional Interface dengan method run(): void. Lambda bisa langsung dipakai. Cocok untuk task yang tidak perlu mengembalikan nilai. Task fire-and-forget: logging, kirim notifikasi, update cache.
Thread.currentThread() Mengembalikan objek Thread yang sedang berjalan. Pada Virtual Thread, output-nya akan menampilkan info bahwa ini Virtual Thread, termasuk nama dan carrier thread-nya: VirtualThread[#123,eko-1]/runnable@ForkJoinPool... Debugging: untuk tahu thread apa yang menjalankan kode ini.
System.in.read() Memblokir main thread sampai ada input dari keyboard. Teknik sederhana untuk mencegah program keluar sebelum semua Virtual Thread selesai. Di produksi, kamu tidak butuh ini — aplikasi Spring Boot punya lifecycle management sendiri. Hanya untuk demo/testing standalone. Jangan gunakan di produksi.
💡 Mengapa Tidak Perlu Thread Pool untuk Virtual Thread?

Thread pool hadir karena membuat/menghancurkan Platform Thread itu mahal (system call ke OS). Virtual Thread jauh lebih murah — overhead pembuatannya mirip membuat objek biasa. Oleh karena itu, pola "1 VT per task" lebih baik dari pool: tidak ada antrian, tidak ada thread yang idle memakan memori, dan tidak ada batas kapasitas buatan.

🔗 Analogi Laravel Queue

Di Laravel, kamu pakai dispatch(new ProcessJob($data)) untuk mengirim job ke queue. ExecutorService.execute(task) bekerja mirip — kamu submit task, framework yang handle eksekusinya. Bedanya: Laravel Queue adalah asynchronous lintas proses (biasanya Redis/database sebagai broker), sedangkan ExecutorService adalah asynchronous dalam satu JVM process. Untuk konkurensi dalam satu aplikasi, ExecutorService lebih ringan dan langsung.

🖥️ Fixed Thread Pool — Kapasitas Terbatas
// Hanya 200 task bisa berjalan bersamaan
// Task ke-201 ANTRI sampai ada slot
ExecutorService pool = Executors.newFixedThreadPool(200);
for (int i = 0; i < 10_000; i++) {
  pool.execute(task); // 9800 task mengantri!
}
⚡ Virtual Thread Per Task — Tidak Ada Batas
// Semua 10.000 task langsung mendapat VT-nya sendiri
// Tidak ada antrian, tidak ada batas kapasitas!
ExecutorService es = Executors.newVirtualThreadPerTaskExecutor();
for (int i = 0; i < 10_000; i++) {
  es.execute(task); // Semua langsung mulai! ✅
}

B. Karena Virtual Thread secara otomatis di-pool oleh JVM
C. Karena overhead pembuatan Virtual Thread sangat kecil, sehingga membuat baru per task lebih efisien daripada mengelola pool

Chapter 5
⚖️ Platform Thread vs Virtual Thread

Perbandingan mendalam antara Platform Thread dan Virtual Thread dari berbagai aspek: performa, use case, keterbatasan, dan kapan harus memilih masing-masing.

Tabel Perbandingan Lengkap

Pembuatan (creation)Mahal — system call ke OSMurah — seperti membuat objek biasa
Context SwitchMahal — OS yang handleMurah — JVM yang handle (user-space scheduling)
DaemonBisa daemon atau non-daemonSelalu daemon (tidak bisa diubah)

⚠️ Pinning — Keterbatasan Virtual Thread di Java 21

Di Java 21, ada satu situasi di mana Virtual Thread tidak bisa di-unmount dari Carrier Thread: ketika berada di dalam synchronized block/method atau memanggil native method. Ini disebut pinning. Saat pinned, Virtual Thread berperilaku seperti Platform Thread — Carrier Thread ikut blocking. Solusi: ganti synchronized dengan ReentrantLock dari java.util.concurrent.locks. Masalah ini diperbaiki di Java 24.

// ⚠️ PINNING — hindari synchronized dengan VT di Java 21

// MASALAH: synchronized menyebabkan pinning
synchronized (lock) {
  Thread.sleep(Duration.ofSeconds(1)); // VT PINNED! Carrier Thread ikut blocking
}

// ✅ SOLUSI: Gunakan ReentrantLock
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
  Thread.sleep(Duration.ofSeconds(1)); // VT bisa di-unmount ✅
} finally {
  lock.unlock();
}

Bahasa lain sudah punya solusi ini lebih lama: Node.js pakai event loop (single-threaded tapi non-blocking), Python punya asyncio, PHP modern punya Swoole/ReactPHP. Java Virtual Thread mengambil pendekatan berbeda: kode ditulis secara blocking seperti biasa, tapi JVM yang mengoptimalkan di belakang layar. Ini adalah keunggulan besar — kamu tidak perlu belajar pola pemrograman baru seperti async/await atau callback hell. Kode Java yang sudah ada (blocking) langsung mendapat manfaat konkurensi tinggi hanya dengan menggantinya ke Virtual Thread.

// ✅ ReentrantLock → tidak pinning
private final ReentrantLock lock = new ReentrantLock();

private void updateCache(String key, String val) throws InterruptedException {
  lock.lock();
  try {
    Thread.sleep(Duration.ofMillis(10)); // VT bisa unmount ✅
    cache.put(key, val);
  } finally {
    lock.unlock(); // WAJIB di finally!
  }
}

Virtual Thread hanya unggul saat ada waktu menunggu (blocking I/O). Jika task kamu adalah murni CPU (sorting 10 juta data, enkripsi, kalkulasi matematika), Virtual Thread tidak memberi keuntungan — bahkan overhead scheduling-nya bisa sedikit lebih tinggi. Untuk CPU-bound, tetap gunakan Platform Thread dengan jumlah = jumlah CPU core, atau pakai ForkJoinPool dengan parallelStream.

Rangkuman Akhir
📋 Arsitektur Java Virtual Thread

Gambaran lengkap dari konsep, implementasi, hingga penerapan Virtual Thread di aplikasi produksi.

Peta Konsep Virtual Thread
😵
Masalah: Platform Thread + Blocking I/O Platform Thread = OS Thread = ~1MB RAM. Untuk aplikasi web yang I/O-bound, sebagian besar waktu thread dihabiskan untuk menunggu (blocking), bukan komputasi. Membuat ribuan Platform Thread tidak praktis dan tidak efisien.
⚡
Solusi: Virtual Thread (Java 21) Thread ringan yang dikelola JVM di atas sejumlah kecil Carrier Thread (Platform Thread). Saat Virtual Thread blocking (sleep, I/O), JVM unmount VT dari Carrier Thread — Carrier bebas menjalankan VT lain. Kode ditulis blocking seperti biasa, JVM yang handle scheduling non-blocking.
🖥️
Platform Thread API (Java 21) Thread.ofPlatform().name().daemon().unstarted(task). Builder pattern baru. Setiap instance = 1 OS Thread. Cocok untuk CPU-bound tasks. JVM tidak exit selama ada non-daemon Platform Thread aktif.
⚡
Virtual Thread API (Java 21) Thread.ofVirtual().name().unstarted(task). API hampir identik dengan Platform Thread. Selalu daemon. Ringan (~1KB). Saat blocking I/O → auto unmount. System.in.read() atau Spring Boot lifecycle mencegah JVM exit prematur.
🏭
ExecutorService + Virtual Thread Executors.newVirtualThreadPerTaskExecutor() — cara production-ready. Setiap task mendapat VT baru. Tidak perlu pooling. Gunakan execute() untuk fire-and-forget, submit() untuk mendapat Future. Gunakan try-with-resources (Java 19+) untuk auto-shutdown.
⚠️
Keterbatasan: Pinning (Java 21) Virtual Thread tidak bisa di-unmount saat berada dalam synchronized block atau native method. Solusi: ganti synchronized dengan ReentrantLock. Diperbaiki di Java 24.
🚀
Spring Boot 3.2 Integration Aktifkan dengan satu baris: spring.threads.virtual.enabled=true. Seluruh HTTP request handling otomatis menggunakan Virtual Thread. Tidak perlu ubah kode existing sama sekali.

🏆 Checklist Penguasaan Java Virtual Thread
  • ✅Paham mengapa Platform Thread tidak efisien untuk I/O-bound tasks (blocking = waste OS Thread)
  • ✅Tahu konsep mount/unmount: Virtual Thread di-unmount dari Carrier Thread saat blocking, Carrier Thread bebas menjalankan VT lain
  • ✅Bisa membuat Virtual Thread dengan Thread.ofVirtual().name().unstarted(task)
  • ✅Tahu perbedaan: .unstarted() vs .start(), daemon vs non-daemon, Platform vs Virtual Thread
  • ✅Bisa menggunakan Executors.newVirtualThreadPerTaskExecutor() untuk production use case
  • ✅Paham mengapa Virtual Thread tidak perlu di-pool (overhead pembuatan sangat kecil)
  • ✅Tahu masalah pinning di Java 21 dan solusinya (ReentrantLock vs synchronized)
  • ✅Ingat kapan Virtual Thread cocok (I/O-bound) vs tidak (CPU-bound)
  • ✅Bisa mengaktifkan Virtual Thread di Spring Boot 3.2+ dengan spring.threads.virtual.enabled=true
  • ✅Tahu keterbatasan ThreadLocal dengan banyak Virtual Thread dan alternatifnya (ScopedValue)
