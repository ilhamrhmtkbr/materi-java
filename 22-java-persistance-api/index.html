🗄️ Belajar Java Persistence API (JPA)

ORM standar Java — petakan object Java ke tabel database tanpa SQL manual. Panduan untuk developer PHP/Laravel dengan analogi Eloquent ORM.

Apa itu JPA?
JPA = Eloquent-nya Java

Java Persistence API (JPA) adalah standar ORM (Object-Relational Mapping) di ekosistem Java. Implementasi paling populer adalah Hibernate — yang digunakan di balik Spring Data JPA. JPA memungkinkan kamu bekerja dengan database lewat object Java, tanpa menulis SQL secara manual.

Chapter 1
🏭 EntityManagerFactory & EntityManager
Dua komponen inti JPA. EntityManagerFactory adalah singleton — dibuat sekali untuk satu database. EntityManager adalah per-request/per-operation — seperti "koneksi" ke database yang kamu buka dan tutup setiap melakukan operasi.
// JpaUtil.java — Singleton Factory
public class JpaUtil {
    private static EntityManagerFactory entityManagerFactory = null;

    public static EntityManagerFactory getEntityManagerFactory() {
        if (entityManagerFactory == null) {
            // "BELAJAR" = nama persistence unit di persistence.xml
            entityManagerFactory = Persistence.createEntityManagerFactory("BELAJAR");
        }
        return entityManagerFactory;
    }
}

// Cara pakai di setiap test/service
EntityManagerFactory emf = JpaUtil.getEntityManagerFactory();
EntityManager em = emf.createEntityManager();        // buka session
EntityTransaction tx = em.getTransaction();

try {
    tx.begin();                   // mulai transaksi
    // ... operasi database ...
    tx.commit();                  // simpan perubahan
} catch (Throwable t) {
    tx.rollback();                // batalkan jika error
} finally {
    em.close();                   // SELALU tutup EntityManager!
}
Penjelasan Baris per Baris
Persistence.createEntityManagerFactory("BELAJAR")
Membaca konfigurasi dari persistence.xml — nama persistence unit, koneksi database, dialect, dll. Mahal secara resource — buat sekali (Singleton pattern).
emf.createEntityManager()
Membuat satu session kerja ke database. Ringan, bisa dibuat banyak. Di aplikasi web biasanya satu EntityManager per HTTP request. WAJIB di-close setelah selesai.
em.getTransaction()
JPA menggunakan resource-local transaction secara eksplisit. begin() memulai, commit() menyimpan, rollback() membatalkan semua perubahan dalam transaksi.
⚡ Tidak seperti Eloquent!
Di Eloquent, kamu cukup User::create($data) dan selesai. Di JPA, kamu harus eksplisit: buka EntityManager → begin transaction → persist → commit → close. Lebih verbose tapi memberikan kontrol penuh atas kapan data benar-benar disimpan.
EntityManagerFactory ≈ koneksi database Laravel (config/database.php). EntityManager ≈ satu "sesi" query, mirip DB::connection() tapi lebih stateful. Transaction JPA ≈ DB::transaction(function() { ... }) di Laravel.
🧠 Mini Quiz

Mengapa EntityManagerFactory harus dibuat sebagai Singleton (sekali saja), sedangkan EntityManager dibuat setiap kali diperlukan?

A.Karena EntityManagerFactory gratis secara resource, sedangkan EntityManager mahal.
B.EntityManagerFactory mahal (baca konfigurasi, buat connection pool). EntityManager ringan dan tidak thread-safe — satu per operasi/request.
C.Tidak ada perbedaan, keduanya bisa dibuat berkali-kali.
Chapter 2
💾 CRUD Operations
Empat operasi dasar JPA: persist() (insert), find() (select by id), merge() (update), remove() (delete). Semua harus dilakukan di dalam transaksi yang aktif.
// INSERT — persist()
Customer customer = new Customer();
customer.setId("1");
customer.setName("Eko");
entityManager.persist(customer);  // object masuk ke "managed" state
// SQL: INSERT INTO customers (id, name) VALUES ('1', 'Eko')

// SELECT BY ID — find()
Customer found = entityManager.find(Customer.class, "1");
// SQL: SELECT * FROM customers WHERE id = '1'
// Jika tidak ditemukan → mengembalikan null (bukan exception!)

// UPDATE — merge()
Customer toUpdate = entityManager.find(Customer.class, "1");
toUpdate.setName("Eko Kurniawan");
entityManager.merge(toUpdate);
// SQL: UPDATE customers SET name = 'Eko Kurniawan' WHERE id = '1'
// Catatan: jika entity sudah "managed" (dari find), update OTOMATIS saat commit!

// DELETE — remove()
Customer toDelete = entityManager.find(Customer.class, "1");
entityManager.remove(toDelete);
// SQL: DELETE FROM customers WHERE id = '1'
// toDelete harus dalam "managed" state dulu (hasil find)
Penjelasan Penting
persist() vs merge()
persist() untuk INSERT — object yang belum pernah disimpan. merge() untuk UPDATE — object yang sudah ada di database atau sudah di-detach. Kalau ragu, gunakan merge() tapi pastikan ID sudah di-set.
find() vs getReference()
find() langsung eksekusi SQL SELECT. getReference() mengembalikan proxy tanpa SELECT — SQL baru dieksekusi saat kamu benar-benar mengakses field-nya (lazy). Gunakan getReference() jika kamu hanya butuh object untuk di-assign sebagai foreign key.
Managed Entity = Auto-Save!
Setelah find(), object dalam status "managed". Kamu cukup toUpdate.setName("baru") tanpa panggil merge() — JPA secara otomatis tracking perubahan (dirty checking) dan akan UPDATE saat commit. Ini yang membuat JPA "magical"!
✅ Urutan yang benar: Selalu lakukan find() terlebih dahulu sebelum remove(). remove() hanya bisa dilakukan pada object yang dalam state "managed", bukan object yang baru dibuat (new Customer()).
Eloquent: User::create($data) ≈ persist(). User::find($id) ≈ find(). $user->update($data) ≈ merge(). $user->delete() ≈ remove(). Perbedaan besar: Eloquent menjalankan SQL langsung saat method dipanggil, JPA mengumpulkan perubahan dan flush saat commit.
🧠 Mini Quiz

Setelah memanggil entityManager.find(Customer.class, "1"), kamu mengubah customer.setName("baru"). Apakah kamu perlu memanggil entityManager.merge(customer) agar perubahan tersimpan?

A.Ya, selalu harus memanggil merge() agar perubahan disimpan.
B.Tidak perlu. Object hasil find() dalam status "managed" — JPA otomatis tracking perubahan (dirty checking) dan akan UPDATE saat commit.
C.Kamu harus memanggil entityManager.flush() secara manual.
Chapter 3
🗂️ Column Mapping & @Transient
JPA memetakan field Java ke kolom database secara otomatis (nama field = nama kolom). Gunakan @Column untuk kustomisasi dan @Transient untuk field yang TIDAK mau disimpan ke database.
// Customer.java
@Entity
@Table(name = "customers")  // petakan ke tabel "customers"
public class Customer {

    @Id
    @Column(name = "id")   // kolom "id" di tabel
    private String id;

    @Column(name = "name")
    private String name;

    @Column(name = "primary_email")  // nama kolom beda dari field Java
    private String primaryEmail;

    private Boolean married;   // kolom: married (otomatis)
    private Byte age;          // kolom: age (otomatis)

    @Enumerated(EnumType.STRING)  // simpan nama enum ("PREMIUM"), bukan ordinal (1)
    private CustomerType type;

    @Transient    // TIDAK disimpan ke database!
    private String fullName;

    // getter/setter ...
}

// CustomerType.java
public enum CustomerType { REGULAR, PREMIUM, VIP }

// Cara pakai:
Customer c = new Customer();
c.setId("3");
c.setName("Joko");
c.setType(CustomerType.PREMIUM);   // disimpan sebagai string "PREMIUM"
c.setFullName("Joko Susilo");      // TIDAK disimpan — @Transient
entityManager.persist(c);
Penjelasan Baris per Baris
@Table(name = "customers")
Jika nama class berbeda dari nama tabel, gunakan @Table. Tanpa annotation ini, JPA otomatis menggunakan nama class sebagai nama tabel (case-sensitive di beberapa database).
@Column(name = "primary_email")
Mapping field primaryEmail (camelCase Java) ke kolom primary_email (snake_case SQL). Konvensi SQL menggunakan underscore, Java menggunakan camelCase — gunakan @Column untuk menjembataninya.
@Enumerated(EnumType.STRING)
Menyimpan enum sebagai String ("PREMIUM") bukan ordinal (angka urutan). Selalu gunakan EnumType.STRING! Jika kamu menggunakan ordinal dan menambahkan nilai baru di tengah enum, semua data lama akan salah.
@Transient
Field ini tidak di-mapping ke kolom manapun. JPA mengabaikannya — tidak SELECT, tidak INSERT. Berguna untuk computed field seperti fullName yang dihitung dari field lain.
🚨 Jangan gunakan @Enumerated(EnumType.ORDINAL)!
ORDINAL menyimpan angka (0, 1, 2). Jika kamu menambahkan GUEST di posisi pertama enum, semua yang tadinya REGULAR (0) menjadi GUEST, PREMIUM (1) menjadi REGULAR, dan seterusnya. Bug data yang sangat berbahaya!
Di Laravel, kamu mendefinisikan kolom di migration dan Eloquent otomatis map. Di JPA, mapping dilakukan langsung di class dengan annotation. @Table(name="customers") ≈ nama tabel di migration. @Column ≈ definisi kolom. @Transient ≈ field yang tidak ada di $fillable dan tidak di-cast.
🧠 Mini Quiz

Mengapa SANGAT disarankan menggunakan @Enumerated(EnumType.STRING) dibandingkan EnumType.ORDINAL?

A.Karena STRING lebih cepat diproses oleh database.
B.Karena ORDINAL menyimpan posisi angka enum — jika urutan enum berubah (tambah/hapus nilai di tengah), semua data lama akan salah mapping dan tidak bisa dikembalikan.
C.Karena ORDINAL tidak didukung oleh semua database.
Chapter 4
📅 Data Types, Enum & Date/Time
JPA mendukung berbagai tipe data Java. Yang paling perlu perhatian adalah penanganan Date dan Time — ada dua pendekatan: Legacy (java.util.Calendar + @Temporal) dan Modern (java.time.LocalDateTime langsung tanpa annotation).
// Category.java — tanggal/waktu
@Entity
@Table(name = "categories")
public class Category {

    // ... id, name, description ...

    @Temporal(TemporalType.TIMESTAMP)  // pendekatan LAMA
    @Column(name = "created_at")
    private Calendar createdAt;        // java.util.Calendar

    @Column(name = "updated_at")
    private LocalDateTime updatedAt;   // pendekatan MODERN — tidak perlu @Temporal!
}

// Image.java — tipe data besar
@Entity
@Table(name = "images")
public class Image {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    private String name;

    @Lob  // Large Object — untuk TEXT / BLOB
    private String description;  // disimpan sebagai TEXT/CLOB

    @Lob
    private byte[] image;        // disimpan sebagai BLOB/BYTEA

}

// DataTypeTest.java — contoh tipe primitif wrapper
Customer customer = new Customer();
customer.setAge((byte) 30);     // Byte (bukan primitive byte)
customer.setMarried(true);      // Boolean (wrapper, bisa null)
Penjelasan Baris per Baris
@Temporal(TemporalType.TIMESTAMP)
Diperlukan untuk tipe java.util.Date atau java.util.Calendar agar JPA tahu format penyimpanannya (DATE, TIME, atau TIMESTAMP). Ini adalah API lama — hindari jika memungkinkan.
LocalDateTime updatedAt
Tipe dari package java.time (Java 8+) sudah dikenali JPA/Hibernate secara langsung — tidak perlu @Temporal. Gunakan LocalDate, LocalTime, LocalDateTime, atau ZonedDateTime untuk kode modern.
@Lob
Large Object — untuk data besar. String dengan @Lob disimpan sebagai TEXT/CLOB (tidak terbatas 255 karakter). byte[] dengan @Lob disimpan sebagai BLOB/BYTEA untuk file binary.
Byte vs byte
JPA merekomendasikan tipe wrapper (Boolean, Byte, Integer) bukan tipe primitif (boolean, byte, int) agar field bisa bernilai null di database — tipe primitif tidak bisa null.
💡 Gunakan java.time (modern): LocalDate, LocalTime, LocalDateTime, ZonedDateTime — tidak butuh @Temporal. Hindari java.util.Date dan Calendar yang sudah deprecated di banyak kasus modern.
Di Laravel, tipe kolom ditentukan di migration ($table->timestamp(), $table->text()). Di Eloquent, field created_at dan updated_at otomatis menggunakan Carbon. Di JPA, kamu harus eksplisit mendeklarasikan tipe Java yang sesuai. @Lob ≈ $table->text() atau $table->binary().
🧠 Mini Quiz

Kamu punya field private LocalDateTime createdAt di entity JPA. Annotation apa yang harus ditambahkan agar field ini ter-mapping dengan benar ke database?

A.@Temporal(TemporalType.TIMESTAMP) wajib ditambahkan.
B.Tidak perlu annotation tambahan — LocalDateTime sudah dikenali JPA/Hibernate secara otomatis.
C.@Column(type="timestamp") harus ditambahkan.
Chapter 5
🔑 Generated Value & Primary Key (@Id)
JPA menyediakan beberapa strategi auto-generate primary key. Pilihan strategi bergantung pada database yang digunakan dan kebutuhan aplikasi.
// Strategi 1: AUTO — JPA pilih sendiri (biasanya SEQUENCE atau TABLE)
@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;

// Strategi 2: IDENTITY — gunakan AUTO_INCREMENT database
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Integer id;          // cocok untuk MySQL, PostgreSQL SERIAL
// Category, Image, Member, Wallet menggunakan strategi ini

// Strategi 3: SEQUENCE — gunakan sequence database
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE,
    generator = "my_seq")
@SequenceGenerator(name = "my_seq", sequenceName = "my_sequence")
private Long id;             // cocok untuk PostgreSQL, Oracle

// Strategi 4: TABLE — simulasi sequence dengan tabel khusus
@Id
@GeneratedValue(strategy = GenerationType.TABLE)
private Long id;             // portable tapi lambat

// Manual ID (tanpa @GeneratedValue)
@Id
private String id;           // Brand, Customer, Product — kamu set sendiri

// Cara pakai IDENTITY
Category category = new Category();
category.setName("Gadget");
// id belum ada (null)!
entityManager.persist(category);
// setelah persist(), id sudah terisi otomatis dari database
System.out.println(category.getId());  // tidak null lagi!
Penjelasan Baris per Baris
GenerationType.IDENTITY
Database yang mengurus auto-increment (AUTO_INCREMENT MySQL, SERIAL PostgreSQL). Hibernate menjalankan INSERT lalu query balik ID yang baru dibuat. Paling sederhana untuk MySQL.
GenerationType.SEQUENCE
Lebih efisien dari IDENTITY karena Hibernate bisa pre-fetch batch ID sebelum INSERT (tanpa query balik). Direkomendasikan untuk PostgreSQL dan Oracle. Tidak didukung MySQL versi lama.
Manual ID (String)
Jika tidak ada @GeneratedValue, kamu yang bertanggung jawab mengisi ID sebelum persist(). Cocok untuk ID yang punya arti (slug, UUID yang kamu generate sendiri).
category.getId() setelah persist()
Setelah persist(), entity dalam managed state dan JPA sudah mengisi field ID dari database. Ini yang ditest di GeneratedValueTest: Assertions.assertNotNull(category.getId()).
💡 UUID sebagai ID
Di aplikasi modern, sering menggunakan UUID sebagai ID: @Id private String id = UUID.randomUUID().toString(); — tidak perlu @GeneratedValue, ID di-generate di sisi Java sebelum persist. Aman untuk distributed system dan tidak ada urutan yang bisa ditebak.
@GeneratedValue(IDENTITY) ≈ $table->id() di migration Laravel (auto increment). Manual String ID ≈ $table->string("id") dengan UUID. Di Eloquent, $incrementing = false dan $keyType = "string" untuk UUID. Di JPA tidak perlu config tambahan — cukup tidak pasang @GeneratedValue.
🧠 Mini Quiz

Apa yang terjadi setelah memanggil entityManager.persist(category) jika category menggunakan @GeneratedValue(strategy = GenerationType.IDENTITY)?

A.ID masih null — harus memanggil entityManager.find() dulu untuk mendapatkan ID.
B.ID otomatis terisi setelah persist() — JPA meminta ID dari database dan langsung mengisi field @Id.
C.ID terisi setelah entityTransaction.commit() bukan setelah persist().
Chapter 6
📦 Embedded & EmbeddedId
@Embedded memungkinkan kamu memecah kolom-kolom dalam satu tabel ke dalam beberapa class Java. Kolom tetap berada di satu tabel, tapi representasi Java-nya lebih terstruktur. @EmbeddedId digunakan untuk composite primary key.
// Name.java — @Embeddable: bisa di-embed ke entity lain
@Embeddable
public class Name {
    private String title;

    @Column(name = "first_name")
    private String firstName;

    @Column(name = "middle_name")
    private String middleName;

    @Column(name = "last_name")
    private String lastName;
    // getter/setter ...
}

// Member.java — memakai @Embedded
@Entity
@Table(name = "members")
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    private String email;

    @Embedded   // kolom title, first_name, middle_name, last_name di tabel members
    private Name name;
}

// DepartmentId.java — Composite Primary Key
@Embeddable
public class DepartmentId implements Serializable {
    @Column(name = "company_id")
    private String companyId;

    @Column(name = "department_id")
    private String departmentId;
    // getter/setter ...
}

// Department.java — menggunakan @EmbeddedId
@Entity
@Table(name = "departments")
public class Department {
    @EmbeddedId
    private DepartmentId id;   // PK terdiri dari 2 kolom

    private String name;
}

// Cara pakai EmbeddedId
DepartmentId id = new DepartmentId();
id.setCompanyId("pzn");
id.setDepartmentId("tech");

Department dept = new Department();
dept.setId(id);
dept.setName("Teknologi");
entityManager.persist(dept);

// Find by composite key
Department found = entityManager.find(Department.class, id);
Penjelasan Baris per Baris
@Embeddable
Class ini bisa di-embed ke dalam entity. Class tidak punya tabel sendiri — semua field-nya akan menjadi kolom di tabel entity yang meng-embed-nya. Seperti Value Object di DDD.
@Embedded pada field Member.name
Semua kolom Name (title, first_name, middle_name, last_name) akan berada di tabel members. Di database, tidak ada tabel names — semuanya di satu tabel. Di Java, kamu bisa akses via member.getName().getFirstName().
@EmbeddedId — Composite Primary Key
Ketika primary key terdiri dari lebih dari satu kolom, gunakan class terpisah annotated @Embeddable yang implement Serializable, lalu field di entity di-annotate @EmbeddedId. entityManager.find() menggunakan object ID ini sebagai key.
⚡ @EmbeddedId harus Serializable!
Class composite key (seperti DepartmentId) WAJIB mengimplementasikan java.io.Serializable. Ini karena JPA menyimpan key di cache dan perlu serialisasi. Lupa implement ini akan menyebabkan runtime error yang membingungkan.
@Embedded mirip konsep $casts di Eloquent untuk Value Object, atau penggunaan accessor/mutator untuk memecah data JSON. Composite primary key di Laravel/Eloquent bisa dilakukan dengan meng-override $primaryKey jadi array, tapi lebih jarang dipakai dibanding JPA.
🧠 Mini Quiz

Jika kamu memiliki @Embeddable class Name dan meng-embed-nya ke entity Member dengan @Embedded, berapa tabel yang akan dibuat di database?

A.Dua tabel: members dan names.
B.Satu tabel: members. Semua kolom dari Name (title, first_name, dll) menjadi kolom di tabel members.
C.Tergantung konfigurasi — bisa satu atau dua tabel.
Chapter 7
🔗 Entity Relationships
JPA mendukung semua tipe relasi antar tabel: OneToOne, OneToMany/ManyToOne, dan ManyToMany. Setiap tipe memiliki annotation yang berbeda dan konsep "owning side" yang penting dipahami.
// === ONE-TO-ONE ===
// User.java — sisi yang punya foreign key (owning side)
@Entity @Table(name = "users")
public class User {
    @Id private String id;

    // PK Join: kolom "id" di users = kolom "id" di credentials
    @OneToOne
    @PrimaryKeyJoinColumn(name = "id", referencedColumnName = "id")
    private Credential credential;

    // Wallet punya FK ke users (mappedBy = "user")
    @OneToOne(mappedBy = "user")
    private Wallet wallet;
}

// Wallet.java — sisi yang punya FK (owning side untuk relasi ke User)
@Entity @Table(name = "wallet")
public class Wallet {
    @OneToOne
    @JoinColumn(name = "user_id", referencedColumnName = "id")
    private User user;
}

// === ONE-TO-MANY / MANY-TO-ONE ===
// Brand.java — satu Brand punya banyak Product
@Entity @Table(name = "brands")
public class Brand extends AuditableEntity<String> {
    @OneToMany(mappedBy = "brand")  // Brand tidak punya FK — Product yang punya
    private List<Product> products;
}

// Product.java — banyak Product milik satu Brand
@Entity @Table(name = "products")
public class Product {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "brand_id", referencedColumnName = "id")
    private Brand brand;  // kolom brand_id di tabel products
}

// === MANY-TO-MANY ===
// User.java — owning side (yang punya @JoinTable)
@ManyToMany
@JoinTable(
    name = "users_like_products",           // nama tabel pivot
    joinColumns = @JoinColumn(name = "user_id", referencedColumnName = "id"),
    inverseJoinColumns = @JoinColumn(name = "product_id", referencedColumnName = "id")
)
private Set<Product> likes;

// Product.java — inverse side
@ManyToMany(mappedBy = "likes")  // mengacu field "likes" di User
private Set<User> likedBy;
Penjelasan Konsep Kunci
Owning Side vs Inverse Side
Sisi yang punya foreign key di database disebut "owning side". Owning side menggunakan @JoinColumn atau @JoinTable. Inverse side menggunakan mappedBy yang mengacu ke nama field di owning side. Perubahan relasi hanya disimpan melalui owning side!
@PrimaryKeyJoinColumn
Relasi OneToOne di mana kedua tabel share PK yang sama (bukan FK biasa). User id = Credential id. Ini natural join — tidak ada kolom tambahan di tabel users.
@JoinTable untuk ManyToMany
Membuat tabel pivot (junction table) users_like_products dengan kolom user_id dan product_id. Ini adalah pendekatan standar untuk ManyToMany di relational database.
Set vs List untuk ManyToMany
Gunakan Set untuk ManyToMany (bukan List). Set memastikan tidak ada duplikat dan lebih efisien. Lihat EntityRelationshipTest.manyToManyInsert() — digunakan HashSet.
⚡ Aturan Emas Relasi JPA: Perubahan relasi hanya persisten jika dilakukan melalui owning side. Jika kamu menambahkan Product ke brand.getProducts() (inverse side), itu TIDAK akan disimpan. Harus via product.setBrand(brand) (owning side — yang punya @JoinColumn).
Laravel Eloquent: hasOne() ≈ @OneToOne (inverse). belongsTo() ≈ @ManyToOne (owning side). hasMany() ≈ @OneToMany. belongsToMany() ≈ @ManyToMany. Di Eloquent, kamu bisa attach dari kedua sisi karena Eloquent yang mengurus. Di JPA, harus melalui owning side.

A.Ya — JPA menyinkronkan kedua sisi secara otomatis.
B.Tidak — perubahan relasi hanya disimpan melalui owning side (user.getLikes()). Inverse side (likedBy) hanya untuk navigasi baca.

📡 Fetch Type & Lazy Loading
JPA menyediakan dua strategi loading data relasi: EAGER (langsung dimuat bersama entity) dan LAZY (dimuat hanya saat diakses). Default berbeda per tipe relasi — dan ini sering menjadi sumber masalah performa.
// Product.java — LAZY loading untuk ManyToOne
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "brand_id", referencedColumnName = "id")
private Brand brand;  // Brand TIDAK langsung di-load saat Product di-find

// EntityRelationshipTest.java — demonstrasi lazy loading
@Test

    Product product = entityManager.find(Product.class, "p1");
    // SQL: SELECT * FROM products WHERE id = 'p1'
    // Brand BELUM di-load!

    Brand brand = product.getBrand();
    // masih belum ada SQL untuk Brand...

    brand.getName();  // saat ini baru ada SQL: SELECT * FROM brands WHERE id = 'samsung'
    Assertions.assertNotNull(brand);
}

// JPQL join fetch — paksa eager loading dalam query
TypedQuery<User> query = entityManager.createQuery(
    "select u from User u join fetch u.likes p where p.name = :product",
    User.class

// SQL: SELECT u.*, p.* FROM users u
//      JOIN users_like_products ulp ON u.id = ulp.user_id
//      JOIN products p ON ulp.product_id = p.id
//      WHERE p.name = 'Samsung Galaxy 1'
// likes langsung ter-load bersama User!

LAZY loading bekerja dengan Proxy
Saat Product di-find dengan Brand LAZY, JPA membuat proxy object untuk Brand. Proxy terlihat seperti Brand biasa tapi SQL baru dieksekusi saat kamu memanggil method (seperti brand.getName()). Ini disebut "N+1 problem" jika kamu iterasi banyak Product masing-masing dengan Branch-nya.
join fetch — solusi N+1
Di JPQL, gunakan join fetch untuk memaksa load relasi dalam satu query SQL. Ini lebih efisien dari N+1 individual queries. Sama seperti with() di Eloquent Laravel.
🚨 LazyInitializationException!
Jika kamu akses lazy property SETELAH EntityManager ditutup (em.close()), JPA akan throw LazyInitializationException. Ini error paling umum di JPA. Solusi: gunakan join fetch, ubah ke EAGER, atau pastikan entity diakses sebelum EM ditutup.
join fetch di JPQL ≈ eager loading dengan with() di Eloquent: Product::with('brand'). FetchType.LAZY default di Eloquent untuk semua relasi. N+1 problem ada di keduanya — Laravel punya with(), JPA punya join fetch atau @BatchSize.

A.Sebuah bug di mana N+1 record tersimpan duplikat di database.
B.1 query untuk fetch daftar entity, lalu N query tambahan (satu per item) untuk fetch relasi lazy-nya. Untuk 100 Product dengan Brand LAZY, itu 1+100 = 101 SQL queries!
C.JPA membatasi maksimum N+1 relasi per entity.

🎧 Entity Listener & Lifecycle Callback
JPA menyediakan hook/callback yang dipanggil secara otomatis saat terjadi event pada entity (sebelum/sesudah persist, update, delete, load). Bisa ditempatkan langsung di entity atau di class listener terpisah.
// UpdatedAtAware.java — interface penanda
public interface UpdatedAtAware {
    void setUpdatedAt(LocalDateTime updatedAt);
}

// UpdatedAtListener.java — listener terpisah
public class UpdatedAtListener {

    @PrePersist    // dipanggil SEBELUM INSERT
    @PreUpdate     // dipanggil SEBELUM UPDATE
    public void setLastUpdatedAt(UpdatedAtAware object) {
        object.setUpdatedAt(LocalDateTime.now());
    }
}

// Category.java — menggunakan listener external
@Entity
@Table(name = "categories")
@EntityListeners({ UpdatedAtListener.class })  // daftarkan listener
public class Category implements UpdatedAtAware {
    // ...
    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    @Override
    public void setUpdatedAt(LocalDateTime updatedAt) {
        this.updatedAt = updatedAt;
    }
}

// Semua lifecycle callback JPA:
// @PrePersist   — sebelum INSERT
// @PostPersist  — setelah INSERT
// @PreUpdate    — sebelum UPDATE
// @PostUpdate   — setelah UPDATE
// @PreRemove    — sebelum DELETE
// @PostRemove   — setelah DELETE
// @PostLoad     — setelah entity di-load dari database

// Member.java — @PostLoad langsung di entity
@Entity
public class Member {
    @Transient
    private String fullName;

    @PostLoad  // dipanggil setelah find() atau query berhasil
    public void postLoad() {
        fullName = name.getTitle() + ". " + name.getFirstName()
                + " " + name.getMiddleName() + " " + name.getLastName();
    }
}
// Setelah entityManager.find(Member.class, 1)
// fullName otomatis terisi: "Mr. Eko Kurniawan Khannedy"
Penjelasan Baris per Baris
@EntityListeners({UpdatedAtListener.class})
Daftarkan satu atau lebih class listener ke entity. Listener akan menerima event lifecycle entity tersebut. Listener class tidak perlu annotation khusus — cukup method dengan annotation lifecycle.
@PrePersist dan @PreUpdate pada Listener
Satu method bisa punya banyak lifecycle annotation. Di sini, setLastUpdatedAt dipanggil baik sebelum INSERT maupun sebelum UPDATE — memastikan updated_at selalu ter-update.
@PostLoad langsung di entity
Callback bisa langsung di dalam entity (bukan class terpisah). @PostLoad dipanggil setelah entity di-load dari database — cocok untuk menghitung field @Transient seperti fullName dari data yang sudah ada.
✅ Pattern Terbaik: UpdatedAtAware Interface
Pattern di project ini sangat elegan: listener menggunakan interface UpdatedAtAware. Ini berarti listener bisa digunakan untuk entity apapun yang implement interface tersebut — reusable dan tidak coupling ke class spesifik.
Laravel Eloquent punya event serupa: creating, created, updating, updated, saving, saved, deleting, deleted. Di Eloquent, didaftarkan via static::creating(fn() => ...) di boot() method, atau via $dispatchesEvents. JPA lebih eksplisit dengan annotation terpisah per callback type.

A.@PostUpdate — setelah update selesai, update field updatedAt.
B.@PreUpdate — sebelum UPDATE SQL dieksekusi, set updatedAt = now(). Perubahan ini akan ikut disimpan.
C.@PrePersist saja sudah cukup.

🧬 Inheritance Strategies
JPA mendukung tiga strategi pemetaan inheritance class hierarchy ke tabel database. Setiap strategi memiliki trade-off antara performa query, normalisasi data, dan kemudahan penggunaan.
// ===== STRATEGY 1: SINGLE TABLE =====
// Semua subclass dalam SATU tabel, dibedakan oleh discriminator column
@Entity
@Table(name = "employees")
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "type")         // kolom pembeda
@DiscriminatorValue("EMPLOYEE")             // nilai untuk class ini
public class Employee {
    @Id private String id;
    private String name;
}

@Entity
@DiscriminatorValue("MANAGER")
public class Manager extends Employee {
    @Column(name = "total_employee")
    private Integer totalEmployee;
}

@Entity
@DiscriminatorValue("VP")
public class VicePresident extends Employee {
    @Column(name = "total_manager")
    private Integer totalManager;
}
// SQL: SELECT * FROM employees WHERE type = 'MANAGER'

// ===== STRATEGY 2: JOINED =====
// Setiap class punya tabel sendiri, JOIN saat query
@Entity
@Table(name = "payments")
@Inheritance(strategy = InheritanceType.JOINED)
public class Payment {
    @Id private String id;
    private Long amount;
}

@Entity
@Table(name = "payments_credit_card")
public class PaymentCreditCard extends Payment {
    @Column(name = "masked_card") private String maskedCard;
    private String bank;
}
// SQL find PaymentCreditCard:
// SELECT * FROM payments p JOIN payments_credit_card cc ON p.id = cc.id WHERE p.id = 'cc1'

// ===== STRATEGY 3: TABLE PER CLASS =====
// Setiap class punya tabel LENGKAP sendiri (duplikasi kolom parent)
@Entity
@Table(name = "transactions")
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public class Transaction {
    @Id private String id;
    private Long balance;
    @Column(name = "created_at") private LocalDateTime createdAt;
}

@Entity
@Table(name = "transactions_debit")
public class TransactionDebit extends Transaction {
    @Column(name = "debit_amount") private Long debitAmount;
}
// transactions_debit punya kolom: id, balance, created_at, debit_amount

JOINED — query parent
Di InheritanceTest.joinedTableFindParent(): entityManager.find(Payment.class, "gopay1") — JPA tahu ini sebenarnya PaymentGopay dan otomatis JOIN ke tabel yang benar. Magic!
Di Laravel/Eloquent, tidak ada built-in inheritance strategy. Biasanya dilakukan dengan Single Table Inheritance manual (satu tabel, ada kolom type) menggunakan package seperti Parental, atau Polymorphic Relations. JPA menyediakan ini sebagai fitur bawaan dengan annotation yang bersih.

🏛️ MappedSuperclass
@MappedSuperclass memungkinkan kamu berbagi field dan mapping yang sama ke banyak entity — tanpa membuat tabel sendiri. Berbeda dengan Inheritance, @MappedSuperclass tidak membuat hierarki query — hanya berbagi definisi field.
// AuditableEntity.java — superclass tanpa tabel sendiri
@MappedSuperclass  // bukan @Entity! tidak ada tabel "auditable_entities"
public abstract class AuditableEntity<T extends Serializable> {

    @Id
    private T id;   // generic ID — subclass tentukan tipe konkretnya

    @Column(name = "created_at")
    private LocalDateTime createdAt;

    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    // getter/setter ...
}

// Brand.java — extends AuditableEntity dengan ID bertipe String
@Entity
@Table(name = "brands")
public class Brand extends AuditableEntity<String> {
    // Brand otomatis punya kolom: id (String), created_at, updated_at
    // PLUS field brand sendiri:
    private String name;
    private String description;

    @OneToMany(mappedBy = "brand")
    private List<Product> products;

    @Version  // untuk Optimistic Locking
    private Long version;
}

// Cara pakai
Brand brand = new Brand();
brand.setId("xiaomi");
brand.setName("Xiaomi");
brand.setCreatedAt(LocalDateTime.now());  // dari AuditableEntity
brand.setUpdatedAt(LocalDateTime.now());  // dari AuditableEntity
entityManager.persist(brand);
// SQL: INSERT INTO brands (id, name, description, created_at, updated_at, version)
Penjelasan Baris per Baris
@MappedSuperclass vs @Entity
@MappedSuperclass = class template yang field-nya di-copy ke subclass. TIDAK ada tabel sendiri, TIDAK bisa di-query langsung (entityManager.find(AuditableEntity.class, id) akan error). @Entity = class yang punya tabel sendiri dan bisa di-query.
Generic T extends Serializable
AuditableEntity menggunakan generics agar tipe ID fleksibel. Brand extends AuditableEntity<String> → ID bertipe String. Jika ada entity lain dengan Long ID, bisa extends AuditableEntity<Long>.
@Version — Optimistic Locking
Field version di Brand adalah counter yang dikelola JPA. Setiap UPDATE, version di-increment. Jika dua transaksi mencoba update Brand yang sama secara bersamaan, yang kedua akan gagal dengan OptimisticLockException karena version sudah berubah.
✅ Pattern DRY terbaik di JPA: Gunakan @MappedSuperclass untuk field audit yang dipakai banyak entity: id, createdAt, updatedAt, createdBy, updatedBy. Di Spring Boot, ada @EnableJpaAuditing + @CreatedDate + @LastModifiedDate yang mengisi field ini otomatis.
Di Eloquent, field created_at dan updated_at otomatis ada di setiap model yang menggunakan timestamps ($timestamps = true). Di JPA murni, harus manual lewat @MappedSuperclass atau EntityListener. Di Spring Data JPA, ada @EntityListeners(AuditingEntityListener.class) yang setara dengan Eloquent timestamps.

B.@MappedSuperclass TIDAK membuat tabel — field-nya di-copy ke tabel subclass. @Entity (Inheritance) membuat tabel dan bisa di-query secara polimorfik.

📝 JPQL — Java Persistence Query Language
JPQL adalah query language mirip SQL tapi bekerja dengan nama entity dan field Java, bukan nama tabel dan kolom SQL. JPA yang akan menerjemahkan JPQL ke SQL yang sesuai dengan database yang digunakan.
// Basic SELECT
TypedQuery<Brand> query = entityManager.createQuery(
    "select b from Brand b",   // "Brand" = nama class Java, bukan tabel!
    Brand.class
);
List<Brand> brands = query.getResultList();

// WHERE dengan named parameter
TypedQuery<Member> query2 = entityManager.createQuery(
    "select m from Member m where m.name.firstName = :firstName " +
    "and m.name.lastName = :lastName",  // m.name.firstName = field dalam @Embedded!
    Member.class
);
query2.setParameter("firstName", "Eko");
query2.setParameter("lastName", "Khannedy");

// JOIN antar entity
TypedQuery<Product> query3 = entityManager.createQuery(
    "select p from Product p join p.brand b where b.name = :brand",
    Product.class
);
query3.setParameter("brand", "Samsung");

// ORDER BY dan LIMIT/OFFSET
TypedQuery<Brand> query4 = entityManager.createQuery(
    "select b from Brand b order by b.name desc",
    Brand.class
);
query4.setFirstResult(10);   // OFFSET — mulai dari record ke-10
query4.setMaxResults(10);    // LIMIT — ambil 10 record

// SELECT field tertentu (bukan full entity)
TypedQuery<Object[]> query5 = entityManager.createQuery(
    "select b.id, b.name from Brand b where b.name = :name",
    Object[].class
);

// SELECT dengan constructor (DTO)
TypedQuery<SimpleBrand> query6 = entityManager.createQuery(
    "select new programmerzamannow.jpa.entity.SimpleBrand(b.id, b.name) " +
    "from Brand b where b.name = :name",
    SimpleBrand.class
);

// UPDATE dan DELETE (non-query)
Query update = entityManager.createQuery(
    "update Brand b set b.name = :name where b.id = :id"
);
update.setParameter("name", "Samsung Updated");
update.setParameter("id", "samsung");
int affected = update.executeUpdate();
Penjelasan Baris per Baris
"select b from Brand b" — bukan SQL!
JPQL menggunakan nama class Java (Brand), bukan nama tabel (brands). Field juga menggunakan nama field Java (b.name), bukan nama kolom SQL. JPA yang menerjemahkan ke SQL sesuai database — berganti database tidak perlu ubah JPQL!
m.name.firstName — navigasi @Embedded
JPQL bisa navigasi field yang di-embed. m.name.firstName artinya: field name dari Member (yang bertipe Name @Embedded), lalu field firstName dari Name. Di SQL: WHERE first_name = ?.
setFirstResult() + setMaxResults() — pagination
setFirstResult(10) = OFFSET (mulai dari record ke-11). setMaxResults(10) = LIMIT (ambil 10). JPA translate ke SQL yang sesuai per database (LIMIT/OFFSET di MySQL, ROWNUM di Oracle, dll).
select new FullClassName(field1, field2) — DTO projection
Langsung membuat object non-entity dari hasil query. Jauh lebih bersih dari menggunakan Object[]. Class yang digunakan (SimpleBrand) harus punya constructor yang matching. Ini adalah pattern DTO Query di JPA.
executeUpdate() — bukan SELECT
JPQL juga bisa UPDATE dan DELETE. Mengembalikan jumlah record yang terpengaruh (bukan entity). Ini bypass dirty checking — langsung SQL tanpa melalui managed entity lifecycle.
JPQL ≈ Eloquent query builder tapi berbasis nama class Java. Brand::orderBy("name", "desc") ≈ "select b from Brand b order by b.name desc". ->offset(10)->limit(10) ≈ setFirstResult(10)->setMaxResults(10). Eloquent lebih ringkas, JPQL lebih eksplisit tapi portable antar database.

📊 Aggregate Query & Named Query
JPQL mendukung fungsi agregat (MIN, MAX, AVG, COUNT, SUM) dengan GROUP BY dan HAVING, mirip SQL. Named Query adalah query JPQL yang didefinisikan di level class entity — compile-time checked dan bisa di-cache.
// Aggregate query — sederhana
TypedQuery<Object[]> query1 = entityManager.createQuery(
    "select min(p.price), max(p.price), avg(p.price) from Product p",
    Object[].class
);
Object[] result = query1.getSingleResult();
System.out.println("Min: " + result[0] + ", Max: " + result[1] + ", Avg: " + result[2]);

// GROUP BY + HAVING
TypedQuery<Object[]> query2 = entityManager.createQuery(
    "select b.id, min(p.price), max(p.price), avg(p.price) " +
    "from Product p join p.brand b " +
    "group by b.id " +
    "having min(p.price) > :min",
    Object[].class
);
query2.setParameter("min", 500_000L);

// ===== Named Query =====
// Didefinisikan di level class dengan annotation:
@Entity
@Table(name = "brands")
@NamedQueries({
    @NamedQuery(
        name = "Brand.findAll",
        query = "select b from Brand b"
    ),
    @NamedQuery(
        name = "Brand.findAllByName",
        query = "select b from Brand b where b.name = :name"
    )
})
@NamedNativeQueries({
    @NamedNativeQuery(
        name = "Brand.native.findAll",
        query = "select * from brands",   // SQL asli, bukan JPQL!
        resultClass = Brand.class
    )
})
public class Brand extends AuditableEntity<String> { ... }

// Cara memanggil Named Query
TypedQuery<Brand> namedQuery = entityManager.createNamedQuery(
    "Brand.findAllByName",  // nama yang didaftarkan di @NamedQuery
    Brand.class
);
namedQuery.setParameter("name", "Xiaomi");
List<Brand> brands = namedQuery.getResultList();

// Named Native Query
Query nativeQuery = entityManager.createNamedQuery("Brand.native.findAll", Brand.class);
List<Brand> allBrands = nativeQuery.getResultList();
Penjelasan Baris per Baris
getSingleResult() vs getResultList()
getSingleResult() mengharapkan tepat satu result — throw NoResultException jika tidak ada, NonUniqueResultException jika ada lebih dari satu. Gunakan untuk aggregate yang pasti menghasilkan satu baris (seperti COUNT, MIN tanpa GROUP BY). getResultList() selalu aman — mengembalikan list kosong jika tidak ada.
@NamedQueries dan @NamedQuery
Named Query di-parse dan divalidasi saat aplikasi start (bukan saat dipanggil). Jika JPQL salah, aplikasi langsung gagal start — error lebih cepat terdeteksi. Ini juga memudahkan caching query plan oleh JPA provider.
Konvensi nama: "Brand.findAllByName"
Konvensi standar JPA: prefix nama class + titik + nama query. Ini untuk menghindari konflik nama antar entity yang berbeda. Di Spring Data JPA, ini diadopsi sebagai konvensi nama method (findAllByName).
@NamedNativeQuery — SQL asli
Jika JPQL tidak cukup ekspresif (query sangat kompleks, pakai fitur spesifik database), gunakan Named Native Query dengan SQL asli. Perlu resultClass agar hasil di-map ke entity.
Eloquent: Product::min("price"), ::max(), ::avg(). Untuk GROUP BY: Product::selectRaw("brand_id, min(price) as min_price")->groupBy("brand_id")->having("min_price", ">", 500000). Named Query tidak ada padanannya langsung di Eloquent — paling dekat adalah Scope method di Eloquent.
🧠 Mini Quiz

Apa keuntungan utama menggunakan @NamedQuery dibanding membuat JPQL string secara inline di setiap method?

A.@NamedQuery lebih cepat secara performa karena dikompilasi ke bytecode.
B.@NamedQuery divalidasi saat aplikasi start — JPQL yang salah langsung terdeteksi, bukan saat method dipanggil. Juga memungkinkan caching query plan.
C.@NamedQuery bisa menggunakan SQL asli (native), sedangkan inline JPQL tidak bisa.

List<Brand> brands = nativeQuery.getResultList();

// Gunakan saat butuh: window functions, CTE, JOIN LATERAL,
// atau syntax yang tidak tersedia di JPQL

// TIDAK memuat entity ke memory — langsung SQL
Query jpqlUpdate = entityManager.createQuery(

);
jpqlUpdate.setParameter("name", "Samsung Updated");
jpqlUpdate.setParameter("id", "samsung");

// Entity-based (lewat managed entity):
Brand brand = entityManager.find(Brand.class, "samsung"); // 1 SELECT

// saat commit: 1 UPDATE (hanya brand ini)

// Direct JPQL UPDATE:
// "update Brand b set b.name = :name" tanpa WHERE → UPDATE ALL RECORDS!
// Tidak perlu load entity ke memory — sangat efisien untuk bulk update
Penjelasan Penting
createNativeQuery() vs createQuery()
createNativeQuery() menerima SQL asli — langsung dikirim ke database tanpa transformasi. createQuery() menerima JPQL — ditransformasi ke SQL oleh JPA. Gunakan native hanya jika JPQL tidak mencukupi.
executeUpdate() — mengembalikan int
Non-query (UPDATE/DELETE) menggunakan executeUpdate() yang mengembalikan jumlah row yang terpengaruh. Bypass managed entity lifecycle — @PreUpdate dan dirty checking tidak berjalan!
Hati-hati UPDATE tanpa WHERE
JPQL Update tanpa WHERE clause akan mengupdate SEMUA record di tabel. JPA tidak memproteksi ini. Selalu verifikasi query sebelum eksekusi — terutama di production!
⚡ @PreUpdate tidak berjalan pada JPQL UPDATE!
Ketika kamu menjalankan "update Brand b set b.name = :name", JPA bypass lifecycle callback. UpdatedAtListener yang punya @PreUpdate TIDAK akan dipanggil. Jika perlu, update updatedAt secara manual dalam query itu sendiri.
Laravel: DB::statement("SELECT ...") atau DB::select() untuk native query. Brand::where("id", "samsung")->update(["name" => "Samsung Updated"]) untuk bulk update via Eloquent — tanpa memuat entity. Di JPA, pola yang sama dengan JPQL Update. Eloquent otomatis mengisi updated_at saat update via model (tapi bukan via DB::).

A.Ya — JPA selalu menjalankan lifecycle callback sebelum operasi apapun.
B.Tidak — JPQL Update/Delete bypass lifecycle callback dan dirty checking. Listener @PreUpdate hanya berjalan untuk perubahan melalui managed entity.
C.Tergantung konfigurasi Hibernate.

🔬 Criteria API
Criteria API adalah cara membuat query JPA secara programmatic dan type-safe menggunakan Java code — bukan string JPQL. Cocok untuk query dinamis di mana kondisi WHERE-nya bergantung pada input user.
// CriteriaTest.java — semua contoh

// ===== 1. Basic SELECT =====
CriteriaBuilder builder = entityManager.getCriteriaBuilder();

CriteriaQuery<Brand> criteria = builder.createQuery(Brand.class);
Root<Brand> b = criteria.from(Brand.class);
criteria.select(b);  // setara: "select b from Brand b"

TypedQuery<Brand> query = entityManager.createQuery(criteria);
List<Brand> brands = query.getResultList();

// ===== 2. SELECT dengan WHERE =====
CriteriaQuery<Brand> criteria2 = builder.createQuery(Brand.class);
Root<Brand> b2 = criteria2.from(Brand.class);
criteria2.select(b2);
criteria2.where(
    builder.equal(b2.get("name"), "Xiaomi"),       // AND
    builder.isNotNull(b2.get("createdAt"))
);
// JPQL setara: "select b from Brand b where b.name = 'Xiaomi' and b.createdAt is not null"

// ===== 3. WHERE dengan OR =====
criteria2.where(
    builder.or(
        builder.equal(b2.get("name"), "Xiaomi"),
        builder.equal(b2.get("name"), "Samsung")
    )
);

// ===== 4. JOIN =====
CriteriaQuery<Product> criteria3 = builder.createQuery(Product.class);
Root<Product> p = criteria3.from(Product.class);
Join<Product, Brand> brand = p.join("brand");   // join ke relasi "brand"
criteria3.select(p);
criteria3.where(builder.equal(brand.get("name"), "Samsung"));
// JPQL: "select p from Product p join p.brand b where b.name = 'Samsung'"

// ===== 5. Named Parameter =====
ParameterExpression<String> brandParam = builder.parameter(String.class, "brand");
criteria3.where(builder.equal(brand.get("name"), brandParam));
TypedQuery<Product> q3 = entityManager.createQuery(criteria3);
q3.setParameter(brandParam, "Xiaomi");

// ===== 6. Aggregate =====
CriteriaQuery<Object[]> criteria4 = builder.createQuery(Object[].class);
Root<Product> p4 = criteria4.from(Product.class);
Join<Product, Brand> b4 = p4.join("brand");
criteria4.select(builder.array(
    b4.get("id"),
    builder.min(p4.get("price")),
    builder.max(p4.get("price")),
    builder.avg(p4.get("price"))
));
criteria4.groupBy(b4.get("id"));
criteria4.having(builder.greaterThan(builder.min(p4.get("price")), 500_000L));

// ===== 7. CriteriaUpdate (non-query) =====
CriteriaUpdate<Brand> updateCriteria = builder.createCriteriaUpdate(Brand.class);
Root<Brand> bu = updateCriteria.from(Brand.class);
updateCriteria.set(bu.get("name"), "Apple Updated");
updateCriteria.set(bu.get("description"), "Apple Company");
updateCriteria.where(builder.equal(bu.get("id"), "apple"));
Query updateQuery = entityManager.createQuery(updateCriteria);
int affected = updateQuery.executeUpdate();

// ===== 8. SELECT constructor (non-entity DTO) =====
CriteriaQuery<SimpleBrand> criteria5 = builder.createQuery(SimpleBrand.class);
Root<Brand> b5 = criteria5.from(Brand.class);
criteria5.select(builder.construct(SimpleBrand.class, b5.get("id"), b5.get("name")));
Penjelasan Baris per Baris
CriteriaBuilder — factory untuk semua komponen
entityManager.getCriteriaBuilder() mengembalikan factory yang bisa membuat predicate, expression, function, dll. Semua building block Criteria API dibuat lewat builder ini.
Root<Brand> b = criteria.from(Brand.class)
Root adalah titik awal FROM clause — mirip alias dalam SQL. Dari root ini kamu bisa navigasi ke field (b.get("name")) atau join ke relasi (b.join("products")).
criteria.where(builder.equal(...), builder.isNotNull(...))
Multiple predicate di where() = AND secara default. Untuk OR, gunakan builder.or(...). Untuk NOT, gunakan builder.not(...). Bisa dikombinasikan secara nested.
CriteriaUpdate — bulk update type-safe
builder.createCriteriaUpdate(Brand.class) untuk UPDATE. updateCriteria.set(field, value) untuk set nilai. Tidak ada setara CriteriaDelete yang eksplisit — gunakan JPQL Delete untuk kasus tersebut.
💡 Kapan pakai Criteria API vs JPQL?
Gunakan JPQL untuk query statis yang sudah diketahui strukturnya. Gunakan Criteria API untuk query dinamis (misalnya: filter pencarian produk di mana user bisa pilih filter mana saja). Criteria API lebih verbose tapi compile-time safe dan dynamic-friendly.
Criteria API tidak ada padanan langsungnya di Eloquent yang semantiknya sama. Paling mirip adalah DB::table()->when($condition, fn($q) => $q->where(...)) untuk query dinamis di Laravel, atau Laravel Scout untuk pencarian. Untuk type-safe query builder di Java modern, banyak tim beralih ke QueryDSL yang lebih ergonomis dari raw Criteria API.
🧠 Mini Quiz

Kapan Criteria API lebih cocok digunakan dibandingkan JPQL string biasa?

A.Criteria API selalu lebih baik karena lebih cepat.
B.Untuk query dinamis — di mana kondisi WHERE bergantung pada input runtime (misal: form filter dengan banyak pilihan opsional). Criteria API memungkinkan build query secara programmatic.
C.JPQL tidak mendukung JOIN, jadi Criteria API harus digunakan untuk query dengan JOIN.

🧩 Collection Mapping (@ElementCollection)
@ElementCollection digunakan untuk memetakan koleksi nilai sederhana (String, Integer) atau embeddable ke tabel terpisah, tanpa membuat entity baru. Cocok untuk hobbies, tags, skills, dll.
// Member.java — koleksi List dan Map
@Entity
@Table(name = "members")
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    private String email;

    @Embedded
    private Name name;

    // === List of String ===
    @ElementCollection
    @CollectionTable(
        name = "hobbies",              // nama tabel terpisah
        joinColumns = @JoinColumn(name = "member_id", referencedColumnName = "id")
    )
    @Column(name = "name")            // nama kolom nilai
    private List<String> hobbies;

    // === Map<String, Integer> — key-value ===
    @ElementCollection
    @CollectionTable(
        name = "skills",
        joinColumns = @JoinColumn(name = "member_id", referencedColumnName = "id")
    )
    @MapKeyColumn(name = "name")      // kolom key
    @Column(name = "value")           // kolom value
    private Map<String, Integer> skills;
}

Penjelasan Baris per Baris
@ElementCollection + @CollectionTable
Membuat tabel baru (hobbies) yang terhubung ke tabel member via FK (member_id). Berbeda dari @OneToMany — tidak ada entity class terpisah. Nilai (name) adalah kolom sederhana, bukan ID entity lain.
@MapKeyColumn + @Column untuk Map
Untuk Map, ada dua kolom: satu untuk key (@MapKeyColumn) dan satu untuk value (@Column). Hasilnya: tabel skills dengan kolom member_id, name (key), value (value).
Update collection = DELETE + INSERT ulang
Saat kamu mengupdate koleksi (tambah/hapus item) dan merge, JPA menghapus SEMUA baris lama untuk member tersebut lalu INSERT ulang semuanya. Ini tidak efisien untuk koleksi besar! Pertimbangkan entity terpisah untuk kasus seperti ini.
⚡ @ElementCollection = Owned Collection
Koleksi ini sepenuhnya "dimiliki" oleh entity induknya. Tidak ada ID sendiri, tidak ada lifecycle sendiri. Jika Member dihapus, semua hobinya otomatis terhapus (cascade delete). Untuk koleksi yang lebih kompleks atau perlu query tersendiri, buat entity terpisah dengan @OneToMany.
Di Laravel, pola yang paling mirip adalah JSON column: $table->json("hobbies") dengan $casts = ["hobbies" => "array"]. Atau tabel pivot tanpa model (DB::table("hobbies")->insert(...)). @ElementCollection di JPA lebih terstruktur — ada tabel relasional yang proper, bukan JSON.

🔄 Managed Entity & Entity Lifecycle
Entity di JPA memiliki empat status: New (baru dibuat), Managed (dilacak oleh EntityManager), Detached (tidak dilacak tapi masih ada datanya), dan Removed (akan dihapus). Memahami ini adalah kunci menghindari bug JPA.
// ManagedEntityTest.java

// ===== NEW → MANAGED via persist() =====
Brand brand = new Brand();         // status: NEW (transient)
brand.setId("apple");
brand.setName("Apple");
entityManager.persist(brand);      // status: MANAGED
brand.setName("Apple International");  // perubahan otomatis di-track!
// saat commit → UPDATE brand SET name='Apple International' (tanpa perlu merge!)

// ===== find() langsung mengembalikan MANAGED =====
Brand managed = entityManager.find(Brand.class, "apple");  // status: MANAGED
managed.setName("Apple Indonesia");   // cukup ini saja, tidak perlu merge()!
entityTransaction.commit();           // → UPDATE otomatis!

// ===== DETACH — lepas dari tracking =====
Brand brand2 = entityManager.find(Brand.class, "apple");  // MANAGED
entityManager.detach(brand2);          // status: DETACHED
brand2.setName("Apple Test");          // perubahan ini TIDAK di-track JPA
entityTransaction.commit();            // TIDAK ada UPDATE!

// ===== DETACHED setelah EntityManager ditutup =====
Brand brand3 = entityManager.find(Brand.class, "apple");  // MANAGED
entityTransaction.commit();
entityManager.close();                 // brand3 sekarang DETACHED!
brand3.setName("Apple Indonesia");     // safe — perubahan tidak tersimpan ke DB
// Untuk simpan perubahan di entity detached:
// entityManager2.merge(brand3);       // attach lagi ke EM baru

// ===== Diagram Status =====
// new Brand() → [NEW]
// persist()   → [MANAGED] ←→ merge() dari DETACHED
// detach()    → [DETACHED]
// remove()    → [REMOVED] → commit → terhapus dari DB
// find()      → langsung [MANAGED]
Penjelasan Baris per Baris
NEW vs MANAGED
Saat kamu baru buat object (new Brand()), status-nya NEW — JPA tidak tahu tentang object ini. Setelah persist(), status berubah ke MANAGED — JPA mulai tracking semua perubahan (dirty checking).
Dirty Checking — Magic JPA
EntityManager menyimpan snapshot state awal entity saat di-load atau di-persist. Saat commit, JPA membandingkan state saat ini dengan snapshot. Jika ada perbedaan → otomatis generate UPDATE SQL. Ini kenapa kamu tidak perlu selalu memanggil merge() untuk entity yang sudah managed.
entityManager.detach(brand)
Melepaskan entity dari tracking. Perubahan setelah detach TIDAK akan disimpan saat commit. Berguna untuk mencegah perubahan tidak sengaja tersimpan, atau untuk melepas entity yang kamu mau return ke layer lain tanpa takut ada side effect.
Entity DETACHED setelah EM ditutup
Setelah entityManager.close(), semua entity yang dimuat oleh EM tersebut otomatis menjadi DETACHED. Untuk menyimpan perubahan pada entity detached, gunakan newEntityManager.merge(detachedEntity).
🚨 Jangan Simpan Entity sebagai Field Class!
Jangan simpan managed entity sebagai field instance di Service atau Controller class (singleton). Setelah request selesai dan EM ditutup, entity tersebut DETACHED. Perubahan berikutnya tidak tersimpan dan bisa menyebabkan bug yang sangat sulit dilacak.
Konsep Managed Entity tidak ada di Eloquent — Eloquent model adalah "dumb" object, perubahan langsung ke database saat kamu memanggil save() atau update(). Di JPA, ada layer abstraksi "Unit of Work" — semua perubahan dikumpulkan dulu, baru di-flush ke database saat commit. Ini membuat JPA lebih efisien (batch operation) tapi lebih kompleks dipahami.
🧠 Mini Quiz

Kamu melakukan entityManager.find(Brand.class, "apple"), lalu brand.setName("Apple New"), lalu entityTransaction.commit() TANPA memanggil entityManager.merge(brand). Apa yang terjadi?

🔐 Locking: Optimistic & Pessimistic
Locking digunakan untuk menangani konkurensi — apa yang terjadi jika dua transaksi mencoba mengupdate data yang sama secara bersamaan. JPA menyediakan dua strategi: Optimistic (asumsi jarang konflik) dan Pessimistic (langsung kunci data).
// ===== OPTIMISTIC LOCKING =====
// Brand.java — tambahkan field @Version
@Entity
@Table(name = "brands")
public class Brand extends AuditableEntity<String> {
    // ...
    @Version    // JPA yang mengurus increment secara otomatis
    private Long version;
}

// Skenario konflik:
// Thread 1: find Nokia (version = 0)
// Thread 2: find Nokia (version = 0)
// Thread 2: update → commit → version jadi 1
// Thread 1: update → commit → GAGAL! version di DB sudah 1, tapi di object masih 0
//           → throw OptimisticLockException

// LockingTest.java
void optimisticLockingDemo1() throws InterruptedException {
    Brand brand = entityManager.find(Brand.class, "nokia");
    brand.setName("Nokia Demo 1");
    Thread.sleep(10 * 1000L);  // simulasi transaksi lama
    entityManager.persist(brand);
    entityTransaction.commit();  // GAGAL jika Demo2 sudah commit lebih dulu!
}

void optimisticLockingDemo2() throws InterruptedException {
    Brand brand = entityManager.find(Brand.class, "nokia");
    brand.setName("Nokia Demo 2");
    entityManager.persist(brand);
    entityTransaction.commit();  // sukses — version naik dari 0 ke 1
}

// ===== PESSIMISTIC LOCKING =====
// Lock langsung saat read — tidak ada thread lain yang bisa update

void pessimisticLockingDemo1() throws InterruptedException {
    // PESSIMISTIC_WRITE = SELECT ... FOR UPDATE
    // Baris di-lock di database — thread lain yang coba select FOR UPDATE akan BLOCK
    Brand brand = entityManager.find(Brand.class, "nokia",
            LockModeType.PESSIMISTIC_WRITE);
    brand.setName("Nokia Demo 1");
    Thread.sleep(10 * 1000L);   // thread lain yang mau lock Nokia akan menunggu!
    entityManager.persist(brand);
    entityTransaction.commit();  // release lock
}

void pessimisticLockingDemo2() throws InterruptedException {
    // Thread ini akan BLOCK saat Thread 1 sedang memegang lock
    Brand brand = entityManager.find(Brand.class, "nokia",
            LockModeType.PESSIMISTIC_WRITE);  // tunggu Thread 1 selesai...
    brand.setName("Nokia Demo 2");
    entityManager.persist(brand);
    entityTransaction.commit();
}

🧠 Mini Quiz

A.Transaksi A berhasil commit — JPA otomatis merge perubahan dari kedua transaksi.
B.Transaksi A gagal dengan OptimisticLockException — version di object A (0) tidak cocok dengan version di database (1). Aplikasi bisa menangkap exception ini dan retry.
C.Transaksi A menimpa perubahan Transaksi B — yang terakhir commit menang.
