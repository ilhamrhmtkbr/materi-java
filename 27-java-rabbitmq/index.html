🐰 Java RabbitMQ Course

🐰 Java RabbitMQ

Modul pembelajaran interaktif untuk developer PHP/Laravel yang migrasi ke Java.
Materi: AMQP Protocol, ConnectionFactory, Channel, Producer & Consumer, Exchange, Routing Key, Message Properties, dan Acknowledgement.

AMQP 0-9-1 RabbitMQ Java Client ConnectionFactory Channel Exchange & Queue DeliverCallback basicPublish / basicConsume

RabbitMQ adalah message broker — perantara yang menerima pesan dari satu aplikasi (Producer) dan meneruskannya ke aplikasi lain (Consumer). Ini memungkinkan komunikasi asinkron antar service tanpa kedua pihak harus online secara bersamaan.

Empat Konsep Inti yang Harus Dipahami Dulu
📤 Producer
Aplikasi yang mengirim pesan ke RabbitMQ. Di project ini: ProducerApp.java. Producer tidak tahu siapa yang akan menerima pesan — ia hanya mengirim ke exchange.
🔁 Exchange
Router pesan. Menerima pesan dari Producer dan memutuskan ke queue mana pesan diteruskan — berdasarkan routing key dan tipe exchange (direct, fanout, topic, headers).
📬 Queue
Antrian pesan — tempat penyimpanan sementara sebelum dikonsumsi. Pesan tersimpan di queue sampai Consumer mengambilnya. Queue bersifat persistent — bisa survive restart RabbitMQ.
📥 Consumer
Aplikasi yang menerima dan memproses pesan dari queue. Di project ini: ConsumerApp.java. Consumer bisa berjalan terus (long-running) atau ambil satu-satu.
Alur Lengkap: Producer → Exchange → Queue → Consumer
ProducerApp │ channel.basicPublish(exchange, routingKey, props, body) │ ▼ Exchange: "notification" (type: direct / fanout / topic) │ binding: routingKey = "whatsapp" → queue "whatsapp" │ binding: routingKey = "email" → queue "email" │ ▼ Queue: "whatsapp" (pesan tersimpan, menunggu consumer) │ ▼ ConsumerApp channel.basicConsume("whatsapp", autoAck, deliverCallback, cancelCallback)

Tanpa message broker, service A harus langsung memanggil service B (HTTP/REST). Masalahnya:

  • Coupling ketat: Jika service B down, service A ikut gagal
  • Kecepatan terbatas: A harus menunggu B selesai memproses
  • Scale susah: Jika B lambat, A terbebani

Dengan RabbitMQ: A cukup kirim pesan ke broker dan lanjut. B memproses kapan saja saat siap. Keduanya decoupled — tidak saling bergantung secara langsung.

AMQP 0-9-1 adalah protokol wire-level yang digunakan RabbitMQ. URI koneksinya berbentuk:
amqp://username:password@host:port/vhost

Default credentials: guest:guest, port 5672, vhost /. Port 15672 adalah RabbitMQ Management UI (browser). Library Java yang digunakan: com.rabbitmq:amqp-client — official RabbitMQ Java client.

⚡ Analogi Laravel

RabbitMQ di Java ≈ Laravel Queue dengan driver rabbitmq (via package vladimir-yuldashev/laravel-queue-rabbitmq). ProducerApp.java ≈ dispatch(new SomeJob(...)) di Laravel. ConsumerApp.java ≈ php artisan queue:work yang terus berjalan mendengarkan queue. Bedanya: di Java kamu berinteraksi langsung dengan AMQP protocol level, tanpa abstraksi tinggi seperti Laravel Queue yang menyembunyikan detail tersebut.

Chapter 01
⚙️ Setup Koneksi — ConnectionFactory, Connection, Channel
Tiga layer abstraksi AMQP yang wajib dipahami

Untuk berkomunikasi dengan RabbitMQ, ada tiga layer abstraksi yang harus dibuat secara berurutan: ConnectionFactory → Connection → Channel. Ketiganya punya peran dan lifecycle yang berbeda.

Kode Setup (digunakan di Producer maupun Consumer)
// Langkah 1: Konfigurasi factory
ConnectionFactory factory = new ConnectionFactory();  // (1)
factory.setUri("amqp://guest:guest@localhost:5672/"); // (2)
factory.setVirtualHost("/");                          // (3)

// Langkah 2: Buat koneksi TCP
Connection connection = factory.newConnection();      // (4)

// Langkah 3: Buat channel (virtual connection)
Channel channel = connection.createChannel();          // (5)
(1) ConnectionFactory Konfigurasi template untuk membuat koneksi. Satu factory bisa menghasilkan banyak Connection. Menyimpan semua setting: host, port, credentials, virtual host, connection timeout, heartbeat, dll. Perlu dikonfigurasi sekali dan bisa di-reuse.
(2) setUri() Cara cepat mengset semua parameter sekaligus via URI AMQP. Format: amqp://user:pass@host:port/vhost. Alternatif: set satu per satu via setHost(), setPort(), setUsername(), setPassword().
(3) setVirtualHost("/") Virtual host di RabbitMQ adalah namespace isolasi — seperti database yang berbeda dalam satu server. Default adalah / (root). Dalam production, biasanya tiap aplikasi punya vhost sendiri untuk isolasi.
(4) factory.newConnection() Koneksi TCP nyata ke RabbitMQ server. Mahal untuk dibuat — butuh TCP handshake dan AMQP negotiation. Sebaiknya dibuat sekali dan di-reuse selama aplikasi berjalan. Di production, gunakan connection pool.
(5) connection.createChannel() Virtual connection di atas satu TCP connection. Ringan untuk dibuat — AMQP menggunakan multiplexing sehingga ribuan channel bisa berbagi satu TCP connection. Semua operasi AMQP (publish, consume, declare queue) dilakukan lewat channel. Channel tidak thread-safe — satu channel per thread.
Hierarki Layer Koneksi
ConnectionFactory ← template konfigurasi, buat sekali └──▶ Connection ← TCP socket ke RabbitMQ, mahal, reuse ├──▶ Channel #1 ← virtual, ringan, 1 per thread, publish/consume ├──▶ Channel #2 └──▶ Channel #N ← satu connection bisa ribuan channel
⚠️ Channel Tidak Thread-Safe!
Satu Channel tidak boleh digunakan dari beberapa thread secara bersamaan. Untuk aplikasi multi-threaded: buat satu channel per thread (bukan satu channel global). Atau gunakan pool channel. Ini adalah kesalahan paling umum yang menyebabkan bug intermittent di production.
❌ Salah — Satu Channel untuk Semua Thread
// Channel dibuat sekali secara global
Channel channel = connection.createChannel();

// Thread A menggunakan channel yang sama
executor.submit(() -> channel.basicPublish(...));
// Thread B juga — RACE CONDITION!
executor.submit(() -> channel.basicPublish(...));
// → Data corrupt / exception acak
✅ Benar — Channel per Thread
// Buat channel baru di setiap thread
executor.submit(() -> {
    Channel ch = connection.createChannel(); // ← per thread
    ch.basicPublish(...);
    ch.close();
});
// Atau gunakan ThreadLocal<Channel>
⚡ Analogi Laravel

ConnectionFactory ≈ konfigurasi koneksi di config/queue.php. Connection ≈ koneksi database yang dibuat oleh Laravel saat startup. Channel ≈ PDO statement handle — objek yang kamu gunakan untuk menjalankan operasi aktual, dan tidak boleh di-share antar request tanpa isolation.

Chapter 02
📤 Producer — Mengirim Pesan
ProducerApp.java · basicPublish · loop publish · close

Producer adalah sisi pengirim — membuat koneksi, mempublish pesan ke exchange, lalu menutup koneksi. Dalam skenario nyata, producer biasanya adalah service backend yang menerima request lalu melempar task ke queue.

Kode Lengkap: ProducerApp.java
public class ProducerApp {
  public static void main(String[] args) throws Exception {

    // 1. Setup koneksi
    ConnectionFactory factory = new ConnectionFactory();
    factory.setUri("amqp://guest:guest@localhost:5672/");
    factory.setVirtualHost("/");

    Connection connection = factory.newConnection();
    Channel    channel    = connection.createChannel();

    // 2. Publish 10 pesan
    for (int i = 0; i < 10; i++) {
      String message = "Whatsapp " + i;                    // (A)

      AMQP.BasicProperties properties =
          new AMQP.BasicProperties().builder()
              .headers(Map.of("sample", "value"))           // (B)
              .build();

      channel.basicPublish(
          "notification",   // (C) nama exchange
          "whatsapp",        // (D) routing key
          properties,          // (E) message properties
          message.getBytes()  // (F) body = byte[]
      );
    }

    // 3. Tutup resource — WAJIB untuk producer
    channel.close();                                        // (G)
    connection.close();                                     // (H)
  }
}
(A) Body sebagai String Pesan dibuat sebagai String biasa. Di dunia nyata, ini biasanya JSON yang di-serialize dari object (objectMapper.writeValueAsString(dto)). RabbitMQ tidak peduli format isi — ia hanya melihat bytes.
(B) headers(Map.of(...)) Menambahkan header key-value ke pesan — metadata tambahan yang tidak mengubah body. Header bisa digunakan untuk routing (pada header exchange) atau untuk memberikan context kepada consumer (misal: x-retry-count, source-service, content-type).
(C) Exchange "notification" Nama exchange yang sudah dikonfigurasi di RabbitMQ. Producer tidak mengirim langsung ke queue — ia mengirim ke exchange. Exchange yang menentukan queue tujuan berdasarkan routing key dan binding.
(D) Routing Key "whatsapp" Kunci routing — string yang digunakan exchange untuk memutuskan ke queue mana pesan diteruskan. Pada direct exchange: harus cocok persis dengan binding key. Pada topic exchange: bisa menggunakan wildcard (*, #).
(E) properties Metadata pesan — selain header, bisa berisi: contentType, correlationId, replyTo, expiration, messageId, timestamp, priority, dan deliveryMode (persistent atau tidak). Dibahas detail di Chapter 5.
(F) message.getBytes() Body pesan selalu berupa byte[] di AMQP — bukan String. Konversi String ke bytes menggunakan encoding default JVM (sebaiknya eksplisit: message.getBytes(StandardCharsets.UTF_8)).
(G-H) close() channel & connection Producer wajib close channel dan connection setelah selesai — berbeda dengan Consumer yang biasanya membiarkan connection terbuka (long-running). Urutan tutup: channel dulu, baru connection.
⚠️ getBytes() Tanpa Encoding Eksplisit
message.getBytes() menggunakan encoding default JVM — bisa berbeda di environment yang berbeda. Untuk konsistensi lintas platform, selalu gunakan:
message.getBytes(StandardCharsets.UTF_8)
Dan di consumer, konversi balik dengan encoding yang sama: new String(message.getBody(), StandardCharsets.UTF_8)
❌ Salah — Kirim langsung ke queue (bypass exchange)
// String kosong = default exchange
channel.basicPublish(
    "",          // ← empty = default exchange
    "whatsapp",  // ← routing key = nama queue
    null,
    msg.getBytes()
);
// Ini bisa bekerja, tapi:
// - Tidak bisa routing ke banyak queue
// - Tidak bisa fanout / topic pattern
// - Tidak fleksibel untuk production
✅ Benar — Gunakan named exchange
// Named exchange = fleksibel dan scalable
channel.basicPublish(
    "notification", // ← named exchange
    "whatsapp",     // ← routing key
    properties,
    msg.getBytes()
);
// Exchange bisa route ke banyak queue
// berdasarkan routing key ✓
⚡ Analogi Laravel

channel.basicPublish("notification", "whatsapp", props, body) ≈ dispatch((new WhatsappJob($data))->onQueue('whatsapp')) di Laravel. Tapi di Java kamu eksplisit menyebut exchange dan routing key — tidak ada abstraksi yang menyembunyikannya. AMQP.BasicProperties ≈ job options di Laravel seperti ->delay(), ->withChain(), dll — tapi lebih low-level dan detail.

🧪 Mini Quiz — Chapter 2

Q: Kenapa body pesan di basicPublish() bertipe byte[], bukan String?

A. Karena RabbitMQ hanya mendukung binary data, tidak bisa teks
B. AMQP adalah binary protocol — semua data dikirim sebagai bytes, memungkinkan pengiriman format apapun (JSON, XML, Protobuf, gambar, dll) tanpa terikat satu format
C. Karena String di Java tidak bisa diserialisasi lewat network
D. Untuk alasan keamanan agar pesan tidak bisa dibaca langsung
Chapter 03
📥 Consumer — Menerima & Memproses Pesan
ConsumerApp.java · basicConsume · DeliverCallback · CancelCallback

Consumer adalah sisi penerima — mendengarkan queue secara terus-menerus dan memproses setiap pesan yang masuk. Berbeda dengan Producer yang bersifat fire-and-forget, Consumer biasanya berjalan sebagai proses long-running.

Kode Lengkap: ConsumerApp.java
public class ConsumerApp {
  public static void main(String[] args) throws Exception {

    // 1. Setup koneksi (sama seperti Producer)
    ConnectionFactory factory = new ConnectionFactory();
    factory.setUri("amqp://guest:guest@localhost:5672/");
    factory.setVirtualHost("/");

    Connection connection = factory.newConnection();
    Channel    channel    = connection.createChannel();

    // 2. Definisikan callback saat pesan tiba
    DeliverCallback deliverCallback = (consumerTag, message) -> { // (A)
      System.out.println(message.getEnvelope().getRoutingKey()); // (B)
      System.out.println(new String(message.getBody()));         // (C)
    };

    // 3. Definisikan callback jika consumer dibatalkan
    CancelCallback cancelCallback = consumerTag -> {              // (D)
      System.out.println("Consumer is canceled");
    };

    // 4. Mulai listen — NON-BLOCKING!
    channel.basicConsume(
        "whatsapp",      // (E) nama queue
        true,             // (F) autoAck
        deliverCallback,
        cancelCallback
    );

    // CATATAN: channel & connection TIDAK ditutup!
    // Consumer terus hidup, menunggu pesan berikutnya
//  channel.close();
//  connection.close();
  }
}
(A) DeliverCallback Functional interface — lambda yang dipanggil setiap kali ada pesan baru masuk dari queue. Parameter: consumerTag (identifier consumer ini) dan message (object Delivery berisi envelope + body + properties). Dipanggil di thread yang berbeda dari thread utama.
(B) getEnvelope().getRoutingKey() Envelope berisi metadata routing pesan: routing key yang digunakan saat publish, exchange asal, dan delivery tag (identifier unik pesan untuk ACK). Berguna untuk consumer yang terdaftar di beberapa queue atau routing key.
(C) new String(message.getBody()) Mengkonversi body bytes kembali ke String. Harus menggunakan encoding yang sama dengan Producer. Best practice: new String(message.getBody(), StandardCharsets.UTF_8). Untuk JSON: objectMapper.readValue(message.getBody(), MyDto.class).
(D) CancelCallback Dipanggil saat consumer dibatalkan oleh broker (bukan oleh kode kita) — misalnya queue dihapus, atau broker memutus consumer karena idle timeout. Tempat yang tepat untuk logging dan cleanup.
(E) "whatsapp" — nama queue Consumer mendengarkan langsung pada queue, bukan exchange. Queue harus sudah ada (dibuat sebelumnya via RabbitMQ Management UI atau channel.queueDeclare() di kode).
(F) autoAck = true Auto-acknowledgement. Nilai true berarti RabbitMQ langsung menandai pesan sebagai "terproses" begitu pesan dikirim ke consumer — tanpa menunggu consumer selesai memproses. Jika consumer crash di tengah proses, pesan hilang. Dibahas detail di Chapter 6.
💡 basicConsume() adalah Non-Blocking
Setelah channel.basicConsume() dipanggil, method ini langsung return — tidak blocking. RabbitMQ client library membuat background thread yang mendengarkan pesan masuk dan memanggil deliverCallback setiap kali ada pesan. Itulah mengapa kita tidak boleh close channel dan connection setelah basicConsume() — consumer harus tetap hidup untuk menerima pesan.
Visualisasi: Thread Model Consumer
main() thread ├── factory.newConnection() → membuka TCP ke RabbitMQ ├── connection.createChannel() → membuat channel ├── channel.basicConsume(...) → mendaftarkan consumer, LANGSUNG RETURN └── main() selesai? (JVM tetap hidup karena ada background thread) Consumer Thread (dibuat oleh RabbitMQ client library) ├── Pesan masuk → deliverCallback("tag", delivery) dipanggil ├── Pesan masuk → deliverCallback("tag", delivery) dipanggil └── ... (terus loop sampai connection ditutup)
❌ Salah — Close connection setelah basicConsume
channel.basicConsume("whatsapp", true,
    deliverCallback, cancelCallback);

channel.close();    // ← consumer mati!
connection.close(); // ← tidak ada pesan yang diterima

// Consumer terdaftar tapi langsung disconnect
// → 0 pesan pernah diproses
✅ Benar — Biarkan tetap hidup
channel.basicConsume("whatsapp", true,
    deliverCallback, cancelCallback);

// JANGAN close! Biarkan proses berjalan.
// Untuk graceful shutdown, gunakan shutdown hook:
Runtime.getRuntime().addShutdownHook(
    new Thread(() -> {
        channel.close();
        connection.close();
    })
);
⚡ Analogi Laravel

channel.basicConsume() ≈ Queue::before() / Queue::after() listener di Laravel, atau lebih tepat seperti command yang dijalankan oleh php artisan queue:work. DeliverCallback ≈ method handle() di Job class Laravel — dipanggil otomatis saat ada job di queue. Perbedaan besar: di Laravel, semua ini dikelola oleh framework; di Java, kamu menulis thread model-nya sendiri.

🧪 Mini Quiz — Chapter 3

Q: Setelah channel.basicConsume() dipanggil, kenapa JVM tidak langsung exit meski main() sudah selesai?

A. Karena basicConsume() adalah blocking method yang menahan main thread
B. RabbitMQ client library membuat background thread non-daemon untuk mendengarkan pesan — JVM tidak exit selama ada non-daemon thread yang masih hidup
C. Karena Connection object masih ada di memori dan mencegah garbage collection
D. Java selalu menunggu semua method selesai sebelum exit
Chapter 04
🔁 Exchange & Routing Key
Direct · Fanout · Topic · Headers — 4 tipe exchange RabbitMQ

Exchange adalah komponen terpenting yang menentukan bagaimana pesan didistribusikan ke queue. Ada 4 tipe exchange, masing-masing dengan strategi routing yang berbeda. Memilih tipe exchange yang tepat adalah kunci arsitektur messaging yang scalable.

Empat Tipe Exchange
🎯 Direct Exchange
Routing key harus cocok persis dengan binding key queue. Pesan dengan routing key "whatsapp" hanya masuk ke queue yang binding key-nya juga "whatsapp".

Use case: Notifikasi yang harus ke channel spesifik.
📢 Fanout Exchange
Mengabaikan routing key — pesan dikirim ke semua queue yang terikat ke exchange ini.

Use case: Broadcast event ke semua service (misal: event "user.registered" perlu diterima oleh email service, analytics service, dll).
🎯 Topic Exchange
Routing key menggunakan pattern matching dengan wildcard: * = satu kata, # = nol atau lebih kata. Contoh: "order.#" cocok dengan "order.created", "order.updated.status", dll.

Use case: Event yang bersifat hierarkis.
🏷️ Headers Exchange
Routing berdasarkan header message, bukan routing key. Binding mendefinisikan pasangan header yang harus cocok. Bisa menggunakan logika all (AND) atau any (OR).

Use case: Routing kompleks berdasarkan metadata pesan.
Contoh Project: Direct Exchange
// Producer mengirim ke exchange "notification" dengan routing key "whatsapp"
channel.basicPublish("notification", "whatsapp", props, body);

// Di RabbitMQ Management UI, binding yang sudah dikonfigurasi:
// Exchange: "notification" (type: direct)
//   Binding: routingKey="whatsapp" → Queue: "whatsapp"
//   Binding: routingKey="email"    → Queue: "email"
//   Binding: routingKey="sms"      → Queue: "sms"

// Consumer mendengarkan queue "whatsapp" — hanya menerima pesan
// yang routing key-nya persis "whatsapp"
channel.basicConsume("whatsapp", true, deliverCallback, cancelCallback);
Topic Exchange — Pattern Matching
// Exchange "events" type: topic
// Binding: "payment.#"   → Queue: "all-payment-events"
// Binding: "payment.ok"  → Queue: "payment-success"
// Binding: "*.failed"    → Queue: "all-failures"

channel.basicPublish("events", "payment.ok", props, body);
// → masuk ke: "all-payment-events" DAN "payment-success"

channel.basicPublish("events", "payment.failed", props, body);
// → masuk ke: "all-payment-events" DAN "all-failures"

channel.basicPublish("events", "email.failed", props, body);
// → masuk ke: "all-failures" saja
Declare Queue via Kode (opsional)
// Jika queue belum dibuat di RabbitMQ, bisa declare via Java:
channel.queueDeclare(
    "whatsapp",  // (1) nama queue
    true,         // (2) durable — survive restart
    false,        // (3) exclusive — hanya satu connection
    false,        // (4) autoDelete — hapus saat consumer disconnect
    null          // (5) arguments — TTL, max length, dll
);

// Bind queue ke exchange:
channel.queueBind("whatsapp", "notification", "whatsapp");
//              queue       exchange          routingKey
✅ idempotent: queueDeclare() Aman Dipanggil Berulang
queueDeclare() adalah operasi idempotent — jika queue sudah ada dengan parameter yang sama, tidak ada yang terjadi. Jika parameter berbeda (misal: durable berbeda), akan throw exception. Aman untuk dipanggil setiap kali aplikasi startup sebagai "ensure queue exists".
⚡ Analogi Laravel

Exchange Types di Java/AMQP ≈ berbagai driver queue di Laravel: Direct ≈ queue bernama spesifik (->onQueue('whatsapp')). Fanout ≈ Event broadcasting ke banyak listener. Topic ≈ event pattern matching yang tidak ada padanan langsung di Laravel standar. Di Laravel, routing ke queue ini tersembunyi di balik abstraksi Job — di Java, kamu eksplisit mengonfigurasinya di AMQP level.

🧪 Mini Quiz — Chapter 4

Q: Kamu ingin satu event "order.created" diterima oleh TIGA service sekaligus: email service, SMS service, dan analytics service. Exchange tipe apa yang paling tepat?

A. Direct Exchange — binding key "order.created" ke tiga queue berbeda
B. Fanout Exchange — otomatis broadcast ke semua queue yang terikat, tanpa perlu routing key

Chapter 05
📨 Message Properties
AMQP.BasicProperties · headers · deliveryMode · contentType · correlationId

Setiap pesan AMQP membawa dua bagian: body (payload data) dan properties (metadata). AMQP.BasicProperties adalah tempat menyimpan metadata tersebut — penting untuk reliability, routing, dan tracing pesan.

Semua Properties yang Tersedia
AMQP.BasicProperties properties =
    new AMQP.BasicProperties().builder()
        // Dari ProducerApp.java
        .headers(Map.of("sample", "value"))            // (A) key-value metadata

        // Properties penting lainnya (tidak ada di kode, tapi wajib diketahui)
        .contentType("application/json")              // (B) format body
        .deliveryMode(2)                               // (C) 1=transient, 2=persistent
        .correlationId(UUID.randomUUID().toString())  // (D) untuk request-reply pattern
        .replyTo("response-queue")                   // (E) queue balasan
        .messageId(UUID.randomUUID().toString())     // (F) ID unik pesan
        .timestamp(new Date())                       // (G) kapan pesan dibuat
        .expiration("60000")                          // (H) TTL dalam milidetik (String!)
        .priority(5)                                   // (I) prioritas 0-9
        .appId("payment-service")                     // (J) identifier aplikasi pengirim
        .build();
(A) headers Key-value metadata bebas. Digunakan untuk headers exchange routing, atau informasi konteks tambahan bagi consumer. Contoh: "x-retry-count", "source-service", "trace-id".
(B) contentType MIME type body pesan. RabbitMQ tidak mewajibkan ini, tapi consumer yang baik harus memeriksa ini sebelum mem-parse body. Standard: "application/json" untuk JSON, "application/octet-stream" untuk binary.
(C) deliveryMode = 2 Property terpenting untuk reliability. Mode 1 = transient (pesan hilang jika RabbitMQ restart). Mode 2 = persistent (pesan disimpan ke disk, survive restart). Untuk production, selalu gunakan mode 2 pada queue yang juga dideklarasikan sebagai durable.
(D) correlationId & (E) replyTo Digunakan bersama untuk RPC pattern via RabbitMQ: Producer mengirim pesan dengan replyTo = nama queue balasan dan correlationId = ID request. Consumer memproses dan mengirim response ke queue replyTo dengan correlationId yang sama. Producer mencocokkan response berdasarkan correlationId.
(H) expiration TTL (Time-To-Live) pesan dalam milidetik sebagai String. Pesan dihapus dari queue jika belum dikonsumsi setelah waktu ini. Jangan lupa tipe datanya String, bukan int — kesalahan umum yang menyebabkan pesan tidak pernah expire.
Membaca Properties di Consumer
DeliverCallback deliverCallback = (consumerTag, message) -> {
    AMQP.BasicProperties props = message.getProperties();

    System.out.println("ContentType: " + props.getContentType());
    System.out.println("CorrelationId: " + props.getCorrelationId());
    System.out.println("Headers: " + props.getHeaders());

    // Body
    String body = new String(message.getBody(), StandardCharsets.UTF_8);
    System.out.println("Body: " + body);
};
🚨 Pesan Hilang Tanpa deliveryMode = 2!
Jika kamu menggunakan deliveryMode = 1 (atau tidak set sama sekali, karena defaultnya adalah 1) dan RabbitMQ server restart, semua pesan yang belum dikonsumsi akan hilang permanen. Untuk production: selalu set deliveryMode(2) di properties dan durable = true di queueDeclare.
⚡ Analogi Laravel

AMQP.BasicProperties ≈ property-property Job di Laravel: deliveryMode(2) ≈ $this->queue = 'persistent-queue' dengan driver yang mendukung persistence. correlationId ≈ UUID yang digunakan untuk tracing job di Laravel. expiration ≈ $this->timeout di Job. Di Laravel, semua ini dikelola framework; di Java, kamu set secara eksplisit.

Chapter 06
✅ Acknowledgement & Reliability
autoAck · basicAck · basicNack · basicReject · Dead Letter Queue

Acknowledgement (ACK) adalah mekanisme konfirmasi bahwa consumer telah berhasil memproses pesan. Ini adalah fondasi dari at-least-once delivery — jaminan bahwa pesan tidak akan hilang begitu saja.

autoAck = true vs false
❌ autoAck = true
RabbitMQ langsung hapus pesan dari queue begitu dikirim ke consumer. Jika consumer crash di tengah proses → pesan hilang permanen. Hanya cocok untuk data yang boleh hilang (log, metrics non-kritis).
✅ autoAck = false (Manual ACK)
RabbitMQ menahan pesan di queue sampai menerima konfirmasi dari consumer. Jika consumer crash → pesan dikembalikan ke queue dan akan dikirim ulang ke consumer lain. Wajib untuk production.
Implementasi Manual ACK
// Consumer dengan manual ACK
channel.basicConsume("whatsapp", false, // ← autoAck = FALSE
    (consumerTag, message) -> {
        try {
            // Proses pesan
            String body = new String(message.getBody());
            processMessage(body);

            // ACK: beritahu RabbitMQ bahwa pesan berhasil diproses
            channel.basicAck(
                message.getEnvelope().getDeliveryTag(), // (A) ID pesan
                false                                    // (B) multiple = false
            );

        } catch (Exception e) {
            // NACK: gagal proses, kembalikan ke queue
            channel.basicNack(
                message.getEnvelope().getDeliveryTag(),
                false,  // (C) multiple
                true   // (D) requeue = true → dikembalikan ke queue
            );
        }
    },
    consumerTag -> System.out.println("Canceled")
);
(A) getDeliveryTag() Nomor urut pengiriman — identifier unik pesan dalam scope satu channel. Digunakan di basicAck(), basicNack(), dan basicReject() untuk memberi tahu RabbitMQ pesan mana yang dikonfirmasi.
(B) multiple = false Jika true: ACK semua pesan dengan delivery tag ≤ yang diberikan (batch ACK). Jika false: ACK hanya pesan ini. Batch ACK lebih efisien untuk throughput tinggi tapi berisiko kehilangan ACK lebih banyak jika crash.
(C-D) basicNack(tag, multiple, requeue) requeue = true → pesan dikembalikan ke queue (akan dikirim ulang). requeue = false → pesan dibuang (atau dikirim ke Dead Letter Exchange jika dikonfigurasi). Hati-hati dengan requeue = true jika error bersifat permanen → bisa infinite loop!
basicReject vs basicNack
// basicReject — tolak SATU pesan saja (tidak ada opsi multiple)
channel.basicReject(
    message.getEnvelope().getDeliveryTag(),
    false  // requeue: false = buang, true = kembalikan ke queue
);

// basicNack — tolak SATU atau BANYAK pesan (ada opsi multiple)
// Gunakan basicNack jika ingin reject batch pesan sekaligus
Dead Letter Queue — Penampung Pesan Gagal
// Queue dengan Dead Letter Exchange (DLX) dikonfigurasi
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "dlx");      // (1)
args.put("x-dead-letter-routing-key", "failed"); // (2)
args.put("x-message-ttl", 60000);               // (3) TTL 60 detik

channel.queueDeclare("whatsapp", true, false, false, args);
// Pesan yang di-reject dengan requeue=false → otomatis ke DLX
(1) x-dead-letter-exchange Exchange tujuan untuk pesan yang ditolak (basicReject/basicNack dengan requeue=false) atau yang expired. Pesan "mati" dikirim ke sini alih-alih dibuang.
(2) x-dead-letter-routing-key Routing key yang digunakan saat mengirim ke DLX. Jika tidak diset, routing key asli pesan digunakan.
(3) x-message-ttl Semua pesan di queue ini akan expire setelah waktu ini (milidetik). Pesan expired dikirim ke DLX — bisa digunakan untuk delayed retry pattern.
💡 Pola Retry yang Aman — Exponential Backoff via DLQ
  1. Consumer gagal → basicNack(tag, false, false) → pesan ke DLX
  2. DLX route ke "retry-queue" dengan TTL (misal 30 detik)
  3. Setelah 30 detik, pesan expired dari retry-queue → kembali ke DLX asli → kembali ke queue utama
  4. Consumer mencoba lagi — dengan penambahan x-retry-count di header
  5. Setelah max retry → kirim ke "dead-queue" untuk manual review
❌ Salah — autoAck=true untuk proses kritis
// Proses pembayaran dengan autoAck=true
channel.basicConsume("payment", true, // ← bahaya!
    (tag, msg) -> {
        // Pesan langsung dihapus dari queue
        // SEBELUM proses pembayaran selesai!
        processPayment(msg.getBody());
        // Jika crash di sini → pesan hilang
        // Pembayaran tidak diproses tapi pesan sudah gone
    }, ...
);
✅ Benar — Manual ACK untuk proses kritis
// Proses pembayaran dengan manual ACK
channel.basicConsume("payment", false, // ← manual
    (tag, msg) -> {
        try {
            processPayment(msg.getBody());
            channel.basicAck(  // ← konfirmasi SETELAH selesai
                msg.getEnvelope().getDeliveryTag(), false);
        } catch (Exception e) {
            channel.basicNack(  // ← kembalikan jika gagal
                msg.getEnvelope().getDeliveryTag(), false, true);
        }
    }, ...
);
⚡ Analogi Laravel

Manual ACK di Java ≈ Laravel Job yang memanggil $this->fail($exception) atau $this->release() (kembalikan ke queue dengan delay). basicNack(..., true, true) ≈ $this->release(30). basicNack(..., true, false) ≈ $this->fail(). Dead Letter Queue ≈ Laravel's failed_jobs table + php artisan queue:retry. Di Java, semua ini dikonfigurasi di level AMQP, bukan di framework level.
